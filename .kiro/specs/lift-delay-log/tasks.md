# Implementation Plan — 麺揚げ遅延ログ

2026-09-12改訂。best-effort console収集を実装する。実装・配備は未着手。[共通タスク](../operation-history-log/tasks.md)の前段1〜7のローカル検証後に着手し、本番合流はoperation単独の実環境確認後とする。共通タスク8でTail・遅延dataset・CLIを接続する。

## Tasks

- [ ] 1. record・開始文脈の契約を固定する
  - [ ] 1.1 原時刻・識別子・canonical形式・eventId・不明理由・相関属性の公開候補名を揃える。旧OperationRecordの形式を維持する。
  - [ ] 1.2 既存snapshotの任意文脈属性とshellでの付加／復元を設計し、全Persist入口を一覧化する。別キー・transaction・配送状態は追加しない。
  - [ ] 1.3 毎回の書込み予定snapshotから残余を評価する方法・保存サイズの上界根拠・key／overhead／安全余裕・評価不能時の全省略を決める。固定の1 Timer／全体byte枠だけで付加を許可しない。業務版13を上げない制約、文脈内部版、旧reader／writerの扱い、有効化の構成を固定する。文脈なしで厨房操作を継続できる契約を固定する。
  - 完了条件: 共通Tailと識別形式が一致し、実サイズによる残余判定・評価不能時の全省略・業務版不変・切戻しの検証方針と、各失敗の成否表が揃う。数値上界の未検証を保存許可へ読み替えない。
  - _Requirements: 1–5_

- [ ] 2. 原事実の純粋導出・canonical codec
  - [ ] 2.1 adjustedEndTimeとpendingOrdersを再利用し、開始直前と完了直前の時点を分ける。
  - [ ] 2.2 早め／0／正の遅延、取消、旧Timer、複数スロット、64件超の未着手、提案群不明、ウェイト未導入をfixtureで検証する。
  - [ ] 2.3 安定eventId、識別子・payload版・canonical往復、不正・未知版の分類を実装する。永続採番は作らない。
  - 完了条件: L1・L5。原時刻から差を再現でき、不明を0へ変換しない。
  - _Requirements: 1–2, 5.1–5.2, 5.4_

- [ ] 3. 開始文脈とbest-effort consoleをshellへ接続する
  - [ ] 3.1 既存snapshot putへ任意文脈を付加し、Persist成功後だけメモリを更新する。全保存経路で残余を再評価して維持・終端時に整理する。収まらなければ既存文脈も任意キー全体を外す。
  - [ ] 3.2 文脈の導出・decode・byte上限失敗は不明として継続する。長い日本語／絵文字・100 Timer・業務単独なら収まる上限境界・注文追加での残余減少・評価不能を検証する。新writer→固定した変更前reader／writer→新readerの復元、任意キー欠落、不正文脈でも業務版が不変であることをテストする。
  - [ ] 3.3 完了直前のrecord候補を保持し、Persistと後続作用の通常完了後に同期consoleを1回試す。業務例外を観測catchへ巻き込まない。
  - [ ] 3.4 console例外・直列化失敗・Persist失敗・後続作用失敗・Persist後停止・重複完了を注入し、成否表に一致することを確認する。
  - 完了条件: L2〜L4。厨房の新たな拒否条件がなく、ログ用network／Alarm／専用起動がない。
  - _Requirements: 4, 7.2–7.3, 7.6_

- [x] 4. 一括完了の相関は実装しない（2026-09-16の決定）
  - 端末の相関申告を採らない。注文由来の群は開始recordの提案同群品目数で足り、手動ゆでには群という事実が無く申告を解釈できない。価値と確からしさが逆を向く。
  - wireの `complete` へ観測用の任意属性を足さない。client・server・検証済み契約はいずれも変更しない。終端recordから `completionAction` を削除済み。
  - 代わりに要約はTimer単位の件数で出し、独立した観測ではないことを表示する。近接完了の件数は**推測と明示した診断値**に留め、標本の統合に使わない（要件 3.3）。
  - 実データでの規模: 本番の完了31件のうち70%が1秒以内に他の完了と並んでいた（2026-09-16計測）。この数字自体が推測である。
  - _Requirements: 3_
