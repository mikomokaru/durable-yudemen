      | 全件同着（最悪・全比較が第 2 の鍵の文字列比較へ落ちる） | 0.352 ms | **0.397 ms** | 0.432 ms | 0.570 ms | 354 ms |

    - 実測（2026-09-08・レビュー反映）：`tests/core/order-item-bound.example.test.ts` に 1 件。通す口は 2 つ——**状態遷移は `decide`**（`OrderArrived` / `StartOrderItem` / `Complete` / `Cancel` / `OrderCancelled` / `PlanArrived` の 6 種）、**hydration は永続の公開境界**（`toSnapshot` → `migrate` → `fromSnapshot`・遷移ではないので `decide` を通らない）。
      **上限の検査は各 `decide` の直後と各 hydration の直後**に置く（周回の末尾ではない）——末尾でだけ見ると、途中で超えて後続の `OrderCancelled` で減って戻る不具合を見逃す。**拒否は握り潰さない**：`step` は `outcome.ok` を要求し、6 種すべてが少なくとも一度は成功したことを最後に主張する。当初は拒否を無視して状態を据え置いており、実際 round 0 で `Complete` 済みの Timer に同じ id で `Cancel` を送って拒否されていた（レビュー指摘）——完了と取消は別の Timer に当てるよう直し、開始も空き釜（`occupiedSlotsOf`）と未調理の品目が在るときだけ送る。
      `PlanArrived` は Requirement 5.9 の「外部計画の受領」。**engine の正本から組む**——「未調理」は `pendingOrders`（期限内 ∧ unstarted）、卓の括りは `tableKeyOf`、対象集合は **`placeableTargets`（置ける計画対象）**。`planTargets` ではないのは、**Acceptance_Gate が `isStale` に渡すのがこちらだから**である（`admit.ts:140` / `commit.ts:73`）——現在の fixture では麺種はプリセット内・`slotSpan` は 1 なので両者は一致するが、未知麺種や過大な `slotSpan` が混ざればずれ、テスト側の「非 stale」の判定が本番のゲートと食い違う（レビュー指摘）。当初は「未調理」を手作業で再実装しており期限判定を欠いていた（レビュー指摘・同じ概念は一箇所）。
      一片は**その卓の計画対象の全件**にする。`isStale` は「一片の配置集合＝その卓の計画対象」を要求するので、1 件だけの一片は同じ卓に他の対象が在れば必ず失効し、採否を語る前に土俵に乗らない。**届ける一片が非 stale であることを `isStale` で検証してから送り**、非 stale な一片を実際に届けた回数が 0 でないことも主張する。
