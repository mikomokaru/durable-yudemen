# モデルの修正（2026-09-13）— **arms+2 をハードに／モデルのダイエット**

**すべて未配備。** 配備は別途諮る。

## 1. `arms + HELPER_ARMS` をハード制約にした

### なぜ

engine（`src/engine/lift.ts:9-11`）は `arms` をソフト（超過は手伝いの費用）、
**`arms + HELPER_ARMS` をハード**（`withinLiftCap`・ゲート (f) と合成）としている。
CP-SAT モデル（`tuning/schedule.ts`）は**両方を値段**にしていた。

```ts
const severe = b.positive([...loadTerms, [b.constant(h.arms + 2), -1]], 1000);
b.cost(b.conditional(severe, leader), p.severeLiftOverflowCost * 10);
```

目的関数が得と判断すればハード上限を超える配置を出し、ゲートがそれを丸ごと棄却する。
**2026-09-13 の掃引で採用 0 件だった本体がこれである。**

### どう直したか

```ts
b.linear(loadTerms, -INF, h.arms + 2);                      // ハード
const excess = b.positive([...loadTerms, [b.constant(h.arms), -1]], 2);
b.cost(b.conditional(excess, leader), p.liftOverflowCost * 10);  // arms はソフトのまま
```

**engine の条件より弱くない。** 長さ L のどの窓 W についても、W に入る計画上がりのうち
最遅を t\* とすれば、W の点はすべて `(t*−L, t*]` に入る（t\* < x+L より t\*−L < x）。
ゆえに右端を各上がりに固定した検査が、任意の窓を覆う。

### 効果（15 分窓・30 局面・同一局面で新旧比較）

| 形 | 上限 | 成功 | 被覆成立 | **`liftCap` 棄却** | **採用** |
|---|---:|---:|---:|---:|---:|
| 旧（値段） | 6 | 30/30 | 2 | 0 | 0 |
| 旧（値段） | 16 | 30/30 | 21 | **19** | **0** |
| 旧（値段） | 24 | 28/30 | 27 | **25** | **0** |
| **新（ハード）** | 6 | **30/30** | 2 | **0** | 0 |
| **新（ハード）** | 16 | 14/30 | 12 | **0** | **2** |
| **新（ハード）** | 24 | 13/30 | 13 | **0** | **2** |

- `liftCap` 棄却が **19→0・25→0**。モデルが engine のハード制約を守るようになった。
- **掃引を始めて以来はじめて採用が出た**（各 2 件）。
- **上限 6（本番の値）では失敗ゼロ。** ハード制約そのものは現行運用で安全である。

### 代償に見えたもの——**実は hint の欠陥だった（2026-09-13 訂正）**

以下は hint を直す**前**の測定である。当時これを「ハードにした制約の性質」と読んだが、
**主因は hint が制約を破っていたこと**だった（§13.4）。hint は釜の空き順で貪欲に組むだけで
上げ窓を見ておらず、さらに `helped = 0` を渡すのにソフト側の容量を超えていた。hint を実行可能に
したところ、**既定予算のままで上限 24 が 0/12 → 12/12** になった。制約の性質ではなく hint の
欠陥である。**この節の数字は「hint が壊れていたときの記録」として残す。**

### 上限を上げると予算切れになる（hint を直す前の測定）

上限 16 で 16/30 が失敗した。文言は `Invalid CP-SAT solution` の一語だったので**理由を
付けるようにした**（`validate.ts`）——予算切れ・実行不能・モデルの誤りが 1 つの失敗に
潰れていて、どれを直せばよいか分からなかった。結果は **`status=UNKNOWN`**＝実行不能では
なく、**最初の実行可能解に届く前に探索予算が尽きている**。

| 予算（決定的時間） | 成功 | UNKNOWN | solve ms p50/max | 採用 |

> クラウドで測り直す必要がある。

## 2. 釜選択のダイエット（`eq` 経由 → 釜ごとの bool 1 個）

旧い形は釜ごとに `eq(slot, s)` を作っていた。`eq` は内部で `gt` を 2 回呼ぶので、
**1 釜あたり補助変数 4 個・線形制約 4 本**（釜 12 なら 1 占有あたり 48 変数）。

新しい形は釜ごとに bool 1 個を置き、線形 2 本で閉じる。

```ts
b.linear(presence.map(v => [v, 1]), 1);                      // ちょうど 1 つ
b.linear([...presence.map((v, s) => [v, s]), [slot, -1]], 0); // slot と連動
```

`unavailableSlots` の禁止と `slotChangeCost` の一致判定も、新たに `eq` を作らず
この presence を引く。

### 等価性（R9.9）

**両方が OPTIMAL に到達した 15 局面すべてで、ソルバーの報告最適値が一致した（15/15）。**

`sum p_s = 1` かつ `sum s·p_s = slot` なら p は slot の指示子に一意に定まるので、
解集合は同一である。最適値の一致はその実測での裏づけである。

| | 旧（eq 経由） | 新（bool 1 個） |
|---|---:|---:|
| 変数 中央（上限 6） | 832 | **552（−34%）** |
| 変数 中央（上限 16） | 2,406 | **1,875（−22%）** |
| solve ms 中央（予算 1.0・上限 6） | 2,195 | **1,974（−10%）** |

**FEASIBLE どまりの局面では報告目的値が食い違う**（64 局面中 53）。多くは新しい形のほうが
良い（最大 −8,392）。予算内でより遠くまで探索できるためで、**等価でないことの証拠ではない**
——等価性は最適解どうしで見るべきものである。

副作用として、同じ局面で別の暫定解が返るので**採用の件数も揺れる**（2 → 0）。採用は
「真に改善」の刃の上にあり、この水準では標本の揺れに埋もれる。

## 7. モデルとは独立の容量検査（R4.4）

`planCpsat` が復号した計画に、**engine 自身の述語**（`withinLiftCap`——`admit` のゲート (f) と
確定計画の合成が読むのと同じ関数）を当てる。規則の写しを書かないので、engine が式を変えれば
この検査も追随する。

```ts
if (!withinLiftCap(initialLifts(request.running), liftsOf(placements), params))
  throw new Error("CP-SAT plan exceeds the lift capacity (arms + HELPER_ARMS)");
```

**走行中の上がりは engine 側の集合で数える。** `initialLifts(request.running)` は boiled も含めて
全走行中を載せるが、モデルが載せるのは `boiledAt === null && 実効 endTime > now` に絞った部分集合
である。**この食い違いはここで初めて露わになる**（§5 に挙げた不整合）。出たら送らない——送っても
`admit` が同じ述語で落とすだけで、その棄却は「計画が悪い」と見分けが付かない。

### 実測（15 分窓・30 局面）

| 形 | 上限 | 結果 |
|---|---:|---|
| 旧（値段） | 6 | ok 26・**容量超過 4** |
| 旧（値段） | 16 | ok 4・**容量超過 26** |
| **新（ハード）** | 6 | **ok 30**（超過 0） |
| **新（ハード）** | 16 | ok 13・解なし 17（**超過 0**） |

**旧い形は上限 6（本番の値）でも 4/30 が上限を破った計画を送っていた。** 新しい形では独立検査が
一度も鳴らない——モデルと検査が同じ規則を見て一致している。

## 9. `eq` を 3 変数から 2 変数へ

旧い形は `v` に加えて `gt` を 2 回呼び、**1 回あたり 3 変数**だった。向きの補助 `d` を 1 つ置いて
強制リテラルを 2 つ並べれば 2 変数で厳密に書ける（符号化は `when` を repeated で書くので可能）。

```ts
this.linear(difference, 0, 0, [v]);                    // v => a == b
this.linear(difference, 1, INF, [-v - 1, d]);          // !v & d  => a > b
this.linear(difference, -INF, -1, [-v - 1, -d - 1]);   // !v & !d => a < b
```

### 等価性（R9.9）

**両方が OPTIMAL に到達した 16 局面すべてで報告最適値が一致（16/16）。** 記録：
`cpsat-model-eq-equiv-20260913.json`

| 予算 1.0 固定・上限 6 | 旧（3 変数） | 新（2 変数） |
|---|---:|---:|
| 変数 中央 | 552 | **536** |
| solve ms 中央 | 1,974 | **1,842** |
| OPTIMAL 到達（30 局面中） | 17 | **21** |

n=16 では `pair` が 1,175 → 1,012（**−14%**）、全体 2,956 → 2,806（−5%）。

### 予算の式が痩身を打ち消す（設計上の匂い）

既定の予算は `min(0.2, 0.04 + 変数数/50000)`。**変数を減らすと予算も減る。** 実測でも、既定予算の
まま上限 16 を回すと成功が 5 → 2 に下がった。固定予算で比べれば新しい形のほうが厳密に良い
（上表）ので、**これはモデルの劣化ではなく予算規則の副作用である。** 予算は「難しさ」で決めるべき
であって「変数の数」で決めると、良い定式化ほど時間をもらえなくなる。R6 の予算規則の再設計に回す。

## 10. `end` の下限を締めた

旧い形は非走行の品目の `end` 下限を `now + 1` に置いていた（茹で 7 分の麺でも「1 秒後に上がる」を
境界に残していた）。`end = start + size` と `start ≥ now`・`size ≥ 茹で時間 − 許容` から
`end ≥ now + 茹で時間 − 許容` が従うので、**解集合は変わらない**（伝播に効くだけ）。

## 11. `cumulative` について——**単独では痩せない**

上げ窓の負荷を `cumulative` 1 本で表す案は、**ハード制約としては正しく、かつ安い**。
区間 `[end_i, end_i + L)`・需要 `slotSpan_i`・容量 `arms + 2` とすれば、時刻 t を覆う区間の集合は
`end_i ∈ (t − L, t]` の杯そのものなので、望む制約と厳密に一致する（n 区間・制約 1 本）。

**しかし変数は減らない。** `inWindow`（768／n=16）は**ソフトの E1**（`max(0, L − arms)` を
クラスタごとに 1 回）が要求しており、ハード制約を `cumulative` へ移してもそのままである。
E1 を安く書くには**定式化そのものを変える**必要がある（例：杯ごとに「手伝いを頼んだ」bool を置き、
容量 `arms` の `cumulative` でその杯の需要を落とす形。O(n) になるが、窓が重なるときの数え方が
現在の「クラスタごとの和」と一致しない）。

**これは E1 の定義変更であり、requirements・design に書かれた評価量を動かす。** モデル側の判断で
行わない。**ご判断を仰ぐ。**

## 12. 距離の刈り込みについて——**このコーパスでは効かない**

「同じクラスタになり得ない組を落とす」には、`end` の取り得る範囲が組ごとに重ならないことが要る。
`end` の下限を締めた後でも、**同じ麺種の杯は下限も上限も同一**なので必ず重なる。本コーパスは
麺種が 4 種で、1 局面のほとんどが同一麺種である。走行中の杯（`end` の幅が狭い）との組では効くが、
**いまのコーパスは `running` が空**なので出番が無い。

効かせるには別の材料が要る（例：`end` の上限を「この杯を最も遅らせてよい時刻」で締める）。
それは業務上の判断を含むので、ここでは行わない。

## 13. `cumulative` と E1 の再定義（2026-09-13・ユーザー判断で本線）

### 13.1 符号化に `cumulative` を足した——**効いていることを先に確かめた**

`Model` に制約種 `cumulative`（容量・区間・需要）を足し、`protobuf.ts` が
`ConstraintProto.cumulative`（field 22・`CumulativeConstraintProto` は capacity=1・intervals=2・
demands=3）へ書く。`LinearExpressionProto.offset`（field 3）も足した（需要と容量に定数が要る）。

**field 番号を取り違えた符号化は、静かに無視されて解が返る。** それは「制約を書いたつもりで
書けていない」という最悪の形なので、**制約が無ければ通る解を用意して、通らないことを見た**
（`experiments/cpsat-workers/quality/probe-cumulative.mjs`）。**この手順は恒久の回帰試験にした**
——`tests/cpsat-cumulative-encoding.example.test.ts`（`tools` project）。符号化や OR-Tools の版が
動いたときに、静かな無視を捕まえる唯一の網である。

| 仕掛け（3 区間・長さ 10・需要 1・開始の和を最小化） | 結果 |
|---|---|
| 制約なし（対照） | objective **0** |
| 容量 3（緩い） | objective **0** |
| 容量 2 | objective **10** |
| 容量 1 | objective **30** |

容量で最適値が動いた＝制約は効いている。`validate.ts` にも独立の検査を足した（返った解の上で、
各区間の開始時刻における負荷が容量以下か）。

### 13.2 E1 の再定義

**旧：** クラスタごとの `max(0, 負荷 − arms)` の和。**新：** その瞬間に要る手伝いの手の数。

区間を `[上がり時刻, 上がり時刻 + L)` に取ると、時刻 t を覆う区間の集合は「`(t − L, t]` に上がる杯」
そのものになる。**ハードとソフトを同じ骨格に乗せる。**

| 資源 | 容量 | 需要 | 意味 |
|---|---|---|---|
| ソフト | `arms` | 手伝わなかった分 `span·(1−helped)` | `arms` を超える分は必ず手伝う |
| ハード | `HELPER_ARMS`（2） | 手伝った分 `span·helped` | 手は 2 本まで＝合計 `arms + 2` |

費用は `liftOverflowCost × span × helped` の和。**窓が重なるとき、旧は同じ超過を複数のクラスタで
数えうるが、新は手を 1 回だけ数える。** 手伝いは瞬間に要る手の数で決まるので、新しい定義のほうが
厨房の負荷に近い（ユーザー判断・2026-09-13）。

**値段と禁止が別の構造を見ていたことが、engine の `withinLiftCap` と食い違った原因だった。**
同じ骨格に乗せたことで、その食い違いは構造から消えた。

### 13.3 予算を変数数から切り離した（段 c）

```ts
// 旧: min(0.2, 0.04 + 変数数/50000)   ← 良い定式化ほど時間をもらえない
b.model.budget = Math.min(1, 0.05 + jobs.length * 0.02);
```

杯数はモデルの書き方に依らず、engine が求解の前に知っている値でもある（要求の同一性に入れられる）。
上限 1.0 は CP-SAT の決定的時間が (0, 1] しか受け付けないため（実測で 3 は拒否された）。

### 13.4 **hint を実行可能にした——これが決定打だった**

ハード化のあと `status=UNKNOWN`（予算内に実行可能解なし）が増えた主因は、**hint が制約を
破っていた**ことだった。旧い hint は釜の空き順で貪欲に組むだけで上げ窓を見ておらず、
さらに `helped = 0` を渡すのにソフト側の容量（`arms`）を超えていた。

hint の上がりを `arms` に収まるまで後ろへ送り（engine の `firstFit` と同じ考え方）、
送った分だけ `start` も動かす（`end = start + size` を保つ）。**これは制約ではなく手がかりなので、
解集合は変わらない。**

### 13.6 質と採否（15 分窓・30 局面・被覆が成立する条件）

| モデル | 上限 | 成功 | 被覆 | 合成に残った | 採用 |

| **+cumulative/E1 再定義** | 24 | **30** | **28** | 28 | 2 |

（最良の局面で −389 → **−978**）。**しかし採用は 2 のまま**——残る閂は「真に改善」の刃であり、
規模とは独立の問題である（`admit` の改善判定を CP-SAT モードでどう扱うか）。

### 13.7 64 件に届かない理由——**残りは対の項である**

上限 32 以上は変数の防壁（8,192）に当たる。内訳を見ると、上げ窓を畳んだいま、**残る 2 乗は
`pair` ブロック**（E4 距離・E7 逆転・E8 分断、および `equal`）である。1 組あたり距離が約 5 変数、
`equal` が 2、逆転が 1。上限 64 なら組は 2,016 で、これだけで 1 万を超える。

**定数倍の削減（例：距離を element 引きにして 5→3）では届かない。** 届かせるには対の項の
扱いそのものを変えることになり、それは E4・E7・E8 の定義に触れる。距離の刈り込み（段 b）は
別途書いたとおり、このコーパスでは `end` の到達可能域が重なるため効かない。

## 14. E4・E7・E8 の改訂（2026-09-13・ユーザー判断）

### 14.1 判断と記録

design 第 7.4.1 節に三項の採否と理由を、requirements の評価項目表と状態行に日付・契機を記録した。
検証の形（同値性ではなく**順位相関**）は design 第 7.4.2 節。

**E8 の依存を明記した。** 全組の距離生成を要求していたのは E8 ではなく E4 である。生成を同一注文に
絞ると E4 が注文をまたぐ組の距離を失うので、**E8 単独では効き幅が出ず、出たとしてもそれは E4 の
定義を黙って変えた成果になる。** §7.4 の E8 行にこの依存を書いた。

### 14.2 E7（隣接組の逆転）——**入った。既定 true**

購入順に並べ、隣り合う 2 杯の上がりが逆転した数を数える。O(杯数)。

| | 上限 6 | 上限 16 | 上限 24 | 上限 32 |
|---|---|---|---|---|
| 旧（全組） | 12/12・変数 415 | 12/12・2,262 | 12/12・4,686 | **7/12**・7,377 |
| **新（隣接）** | 12/12・**405** | 12/12・**2,157** | 12/12・**4,434** | **9/12**・**7,282** |

変数は 5%、solve はわずかに速い。**上限 32 の成功が 7/12 → 9/12 に増えた**（防壁の手前に収まる
局面が増えたため）。

### 14.3 E4（クラスタの広がり）第 1 案（`elementVars`）——**落ちた。採らない**

クラスタ番号を持たせ、「自分のクラスタの最大・最小」を `elementVars` で 1 変数ずつ引く形を実装した。
クラスタ時刻を狭義単調増加に置くので**同じクラスタ番号 ⟺ 同じ上がり時刻**であり、クラスタの意味は
旧い形と同じである。

**対の項は狙いどおり縮んだ。**

| 上限 | 旧 pair | 新 pair |
|---:|---:|---:|
| 16 | 1,184 | **554** |
| 24 | 2,672 | **1,024** |
| 32 | 4,319 | **1,608** |

**しかしソルバーが落ちる。** `std::bad_alloc` / `RuntimeError: Aborted` / `_malloc` 失敗が、
上限 6 でも 12 局面中 5 件出た。

**原因は proto のバイト数ではない。** `elementVars` 1 本はクラスタ数ぶんの式を持つので、
最初は proto の肥大を疑った。ところが**クラスタ数の上限を 8・16 に絞ると失敗が増えた**
（上限 16 で成功 3/12 → 1/12、メモリ失敗 5 → 7〜10）。proto は小さくなっているので、
**落ちているのはソルバー内部の展開**である。クラスタ時刻の定義域が広い（地平線まで約 27,000）
ことと、変数を引く element の組み合わせが疑わしいが、**特定していない。**

**既定を false にした。** 定義としては採用が決まっているが、実装が使える状態にない。既定を
壊さないために false で置き、掃引でだけ true にする（`--fat-pairs` の逆で、既定が旧い形）。

**順位相関の検証は行っていない。** 新定義の計画が安定して得られないので、比べる対象が揃わない。

### 14.4 いま到達している形

既定（ハード化＋累積資源＋釜 bool＋`eq` 2 変数＋`end` 下限＋実行可能 hint＋E7 隣接）で：

| 上限 | 成功 | 変数 p50 | solve ms p50 |
|---:|---:|---:|---:|
| 6 | 12/12 | 405 | 443 |
| 16 | 12/12 | 2,157 | 1,036 |
| **24** | **12/12** | 4,434 | 1,967 |
| 32 | 9/12 | 7,282 | 2,018 |
| 48・64 | — | 防壁 | — |

**64 件には届いていない。** 残る閂は、E4 を畳めないこと、および E2（クラスタ数）・E3（間隔）が
まだ `equal`（組あたり 2 変数）と `next`（組あたり 2 変数）で全組を作っていることである。
**この 2 つはクラスタ番号があれば畳めるが、E4 が動かない限り同じ壁に当たる。**

### 14.5 新しい原語（`elementVars`）

変数を引く element を `Model`・符号化・検査に足した。`cumulative` と同じく、**無視されていない
ことを先に確かめてから使った**——`probe-cumulative.mjs` に添字 0／1／2 で最適値が 7／11／28 に
動くことを足し、恒久試験（`tests/cpsat-cumulative-encoding.example.test.ts`）にも入れた。

### 14.6 最小再現——**定義域の幅という読みは支持されなかった**

`elementVars` が「添字の値ごとに定義域の広い整数の等式へ展開され、bool 符号化が幅に比例して増える」
という読みを、1 回で確かめた（`experiments/cpsat-workers/quality/probe-elementvars-domain.mjs`。
記録：`cpsat-model-elementvars-repro-20260913.json`）。骨格だけを抜き出し、**幅だけを動かす。**

| 幅 | 杯 16 / クラスタ 16 | 杯 24 / 24 | 杯 32 / 32 |
|---:|---|---|---|
| 27,000 | OPTIMAL・32 MiB | OPTIMAL・32 MiB | OPTIMAL・32 MiB |
| 2,700 | OPTIMAL・32 MiB | OPTIMAL・32 MiB | OPTIMAL・32 MiB |
| 270 | OPTIMAL・32 MiB | OPTIMAL・32 MiB | OPTIMAL・32 MiB |

**落ちない。** `elementVars` 単独では、幅を 100 倍にしても杯 32・クラスタ 32 まで通る。
実モデルでの破綻は他の構造との組み合わせであり、**幅が原因という読みは支持されない。**
原語（`elementVars`）は符号化に残す——別の用途で使える形であり、回帰試験も持っている。

### 14.7 第 2 案（所属 bool ＋ enforcement literal）——**これが通った。既定 true**

element を使わず、**enforcement literal 付きの線形だけ**で同じ意味を書く。

| 要素 | 形 |
|---|---|
| 所属 | `x[i][k]`（杯 i がクラスタ k）。杯ごとに「ちょうど 1 つ」を線形 1 本 |
| 時刻の一致 | `x[i][k] ⇒ end_i = T_k`（enforcement literal 付き線形 1 本） |
| 対称性 | `T_k` は狭義単調増加（**同じクラスタ番号 ⟺ 同じ上がり時刻**） |
| E4 広がり | `x[i][k] ⇒ minX_k ≤ 座標 ≤ maxX_k`。費用は `10·max(幅x,幅y) + 4·min(…)` |
| E2 個数 | `used_k`。クラスタごとに 1 本（`Σ_i x[i][k] ≤ n·used_k`） |
| E3 間隔 | `T_{k+1} − T_k` の不足を `used_{k+1}` の条件つきで費用に |

**メモリ破綻は消えた。** そして `equal`（全組）・`next`（全組）・element がすべて消え、
**E2・E3 も同じ骨格に乗った**——累積資源でハードとソフトを同じ資源に乗せたのと同じ考え方である。

**hint はクラスタまで通す。** 所属だけ渡して時刻を渡さないと `x ⇒ end = T_k` を満たさず、
手がかりにならない（**累積資源のときと同じ失敗を繰り返した**）。hint が置いた上がり時刻の相異なる値を
そのままクラスタ時刻に据える。これで上限 32 が 4/12 → **12/12** になった。

**クラスタ数は hint が要した数 ＋ 4 に寄せる。** 所属 bool は杯数 × クラスタ数だけ制約を作るので、
ここが proto のバイト数を決める（上限 64 で 1 MiB を超えていた）。**これはモデルの制限である**
——「相異なる上がり時刻は高々 K 個」を強いるので、それより細かく割る解は除かれる。E2 がクラスタ数を
罰するので最適解は少ない側に寄るが、除外は除外である。
