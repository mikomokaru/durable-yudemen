## 2. engine との食い違い（原因）

engine の `withinLiftCap` → `loadWith(t, span)` は **t を含む窓だけ**を見て `既存 + span ≤ cap` を課す。

> 走行中だけ・過去の boiled だけで既に上限を超えている窓は開始後の事実であって、
> **それを含まない配置を落とす理由にならない**（`src/engine/lift.ts`・AC 9.4）

**engine は「既に超えている窓へ足すこと」だけを拒む。** モデルは走行中を固定需要として累積資源に
載せていたので、**固定分だけで超えると全体が実行不能**になっていた。

## 3. 直し（①）——固定分の負荷を容量で頭打ちにする

固定の上がり時刻は求解前に定数として分かるので、負荷 `F(t)` は階段関数として計算できる。
帯ごとに **`min(F(t), 容量)`** を需要として載せる。

| 帯 | 載せる需要 | 自由な杯の余地 | engine |
|---|---|---|---|
| `F < 容量` | `F`（そのまま） | `容量 − F` | `既存 F + span ≤ cap` と同じ |
| `F ≥ 容量` | `容量` | 0 | 「何も足せない」と同じ |

**緩くなる帯は無い。**

**資源は 2 つに分ける。** ソフト側の頭打ちを `arms` にするだけでは、`arms < F < cap` の帯で
緩くなる（arms 2・F 3・cap 4 で engine は自由 1 本までなのに、モデルは 2 本許す）。

| 資源 | 容量 | 固定分の需要 | 自由な杯の需要 | 役割 |
|---|---|---|---|---|
| **ハード** | `arms + HELPER_ARMS` | `min(F, cap)` | `span` | **engine の `withinLiftCap` と同値** |
| ソフト（E1） | `arms` | `min(F, arms)` | `span × (1 − helped)` | 手伝いの費用。既に済んだ手伝いを再び数えない |

> **「定義域に穴を空ける」案は採らない。** 杯ごとの禁止では**自由な杯どうしの合算を見られない**
> ——cap 4・固定分 3 の窓に span 1 が 2 つ来ると、どちらも単独では 3+1≤4 で通り、合わせて 5 になる。
> engine は「既存」に他の計画済みの杯も含めるので拒む。**単独では engine と同値にならない。**

### 効果（修正後）

| 走行中（同じ窓） | 修正前 | **修正後** | 容量違反 |
|---:|---:|---:|---:|
| 4 | 6/6 | 6/6 | 0 |
| **5** | **0/6** | **6/6** | 0 |
| **6** | **0/6** | **6/6** | 0 |
| **8** | — | **6/6** | 0 |

**独立の容量検査（engine の `withinLiftCap` を復号した計画に当てる）は一度も鳴っていない。**
緩めた結果として engine に落とされる計画を作っていない、という直接の確認である。

## 4. 残り（②）——予算が走行中を捉えていない

**走行中が釜を別々の時刻まで塞ぐと、同じ杯数でも格段に難しくなる。** 現行式
`0.004 + 杯数 × 0.007` は杯数だけを難しさの代理にしており、これを捉えない。

| 予算 | 成功（走行中 4 本・分散・上限 24） | ローカル solve ms p50/max |

| 0.214（現行式） | **0/6** | — |
| 0.3 | 1/6 | 562 |
| **0.5** | **6/6** | 1,180/1,324 |
| 1.0 | 6/6 | 3,522/4,174 |

**1 点で直線を引かない**（それは `0.02` で踏んだ失敗である）。走行中 2・4・6 の 3 点で決めた。

| 項目 | 値 |
|---|---|
| **式** | `min(1, 0.004 + 杯数 × 0.007 + min(走行中, 4) × 0.082)` |
| **`cpu_ms`** | 10,000 → **20,000** |
| **2.4 の閾値** | CPU 比で **10,000 合格・16,000 停止** へ置き直す |
| **費用** | **月 $15〜17**（21 店舗・予算増ぶんを含む） |

### 2.4 の閾値の置き直しについて——**注意を残す**

現行は CPU 5,000 合格・8,000 停止。`cpu_ms` を 2 倍にしたので CPU 比で 10,000/16,000 とした。
**これは「測って決めた値」ではなく「上限に合わせて動かした値」である。**

見込み p50 5,000 に対し合格 10,000 は倍の余裕だが、**停止 16,000 は見込み max 13,300 を
わずかに上回るだけで、停止が実質的に機能しない水準**である。配備後の実測で見込みを置き換え、
そのときに閾値の意味を測り直す必要がある。

### 見込み CPU の導き方

クラウドの実測は**校正後の窓（予算 0.172）で CPU p50 1,731 ms・max 4,571 ms**。
CP-SAT は決定的時間の予算まで探索を続けるので **CPU は予算にほぼ比例する**と置く。

`見込み CPU ≒ 実測 × (予算 / 0.172)`

**これは外挿である。** 配備後の実測で更新する前提で表に載せる。
