# CP-SAT の知見を TS 自前計画へ還元（2026-09-15）

参照した知見は [hint の上げ窓修正](hint-lift-window-fix-20260915.md) と
[修正後の再検証](valid-hint-followup-20260915.md)。CP-SAT の係数を TS へ移植せず、
TS の実装と独立の検査を照合して、適用箇所を分けた。

## 還元したもの

| CP-SAT で得た知見 | TS の現状と変更 |
|---|---|
| 候補時刻より後の走行中の上げも、候補を含む窓の容量を消費する | `loadWith` は既に正しい。窓ごとの全件再走査を、左右の添字で負荷を増減する走査へ変更した |
| 実行可能でも、候補の作り方が余分な待ち・追越しを作る | `placeWithLifts` に残り容量で先頭を切る候補を追加。列の本数が腕以内でも、既存負荷で全列が遅れる場合に試す |
| 丸めたモデルで成立しても返却配置で成立するとは限らない | TS のミリ秒精度を保つ。44.226 秒の間隔を 45 秒と扱わない具体例と、独立のミリ秒差分検査を追加した |
| 同じ誤りを共有する検査は反証にならない | `firstFit` の総当たり参照から本体の `loadWith` 呼び出しを除去。各窓を独立に列挙して数える参照へ変えた |
| 目的値の報告・別物の採点だけでは改善を判定できない | 生成した配置を既存 `scoreSchedule` で再採点。局所費用の改善と完成計画の改善を分けて記録する |

TS は既に保持候補 R と生成候補 F を同じ `scoreSchedule` で比較し、同点では R を残す。
この機構を維持する。CP-SAT の orderedHint の床、逆転係数 480/960、Head の釜変更倍率は追加しない。
TS の列の順序や、近傍変更費用をこれらの係数で置き換える根拠は今回の検証にはない。

## 分割候補と具体例

ハード上限は従来どおり `arms + HELPER_ARMS`。腕数・上げ間隔・費用式は変更しない。
上限以下の列について、従来の pack と arms で切る split を残し、
`min(arms, 候補を含む全窓の残り容量)` で切る split も比較する。
空・全列・重複する接頭辞は除外し、不可分の品目は切らない。
pack が候補時刻に入る場合は残り容量の検査を省く。
同費用なら保持候補、pack、残り容量の split、従来の split の優先順。
列の順は元の茹で時間・同値の正準順序であり、全店の FIFO をハード制約にしたものではない。

試験の場面：腕 2、窓 45 秒、別卓の走行中 3 杯が 300 秒に上がる。
8 秒時点で、同卓・別伝票の未着手を 270 秒茹でたい。未着手の最早提供は 278 秒。
同時提供の重み 0 で比較した。

| 未着手 | 修正前の提供時刻（列順） | 修正後 | 完成計画の総費用差（後 − 前） |
|---|---|---|---:|
| 2 杯 | 345, 345 秒 | 278, 323 秒 | −44 秒相当 |
| 3 杯 | 345, 345, 278 秒 | 278, 345, 345 秒 | 0（末尾の追越しを除去） |

2 杯では Σ待ちを 89 秒短縮し、手伝いの費用が 45 秒増えるため、差は −44 秒相当。
278 と 323 はちょうど 45 秒離れており、同じ半開窓に入らない。
すべての上げ時刻を起点に独立に数えて上限 4 を守ることも試験する。
同時提供の重みが 2 なら分割の遅れの費用が上回り、345, 345 秒の pack を選ぶ。

## 完成計画では単調改善を保証しない

[合成比較の全結果](ts-transfer-20260915.json) は seed 20260915 の 1,000 局面。
6/12/18 釜、未着手 1〜64 品、腕 1〜4、上げ間隔 5〜120 秒、同時提供・伝票同期の重み 0〜4、
走行中 0〜7 本（各別釜）、大盛を含む。前回提案なし。実店舗の頻度分布ではない。
両実装へ同じ入力を渡し、完成した配置を同じ `scoreSchedule` で採点した。

| 指標 | 件数 |
|---|---:|
| 配置が変化 | 47 / 1,000 |
| 総費用が改善 | 32 |
| 総費用が悪化 | 14 |
| 配置が変化して総費用は同値 | 1 |
| 上げ窓のハード上限違反 | 0 |

最大の相対悪化は局面 958 の 9,002 → 9,428（+4.73%）。平均や改善件数でこの悪化を隠さない。
局所比較は完成計画の目的関数そのものではなく、後続卓の配置への影響も比較しないため、
候補を増やしても完成計画の総費用が旧生成器以下になる保証はない。
また、今回の比較は前回提案なしであり、実運用の変更頻度・待ち時間分布の改善を示すものではない。

**この差分は候補生成の改善であり、全局面で品質改善を保証する変更ではない。**
完成計画での非悪化も必要なら、旧候補生成による完成計画を比較対象に残して、同一目的式で選別する追加設計が必要になる。
その場合は計画を追加で生成する CPU 費用と、同値のときに順序改善を採る規則も合わせて評価する。

## 上げ窓の計算量と計測

`loadWith` の一回の検査は、候補起点の列挙と窓の左右の走査で O(n) になった。
`firstFit` は依然として複数の候補時刻を試すため、全体を O(n) にしたとは主張しない。
返す判定と `liftOverflow` の費用定義は変わらない。

128 件の密な上げ表の試験では、旧版は時刻を 16,900 回読んで計算量の上限試験に失敗した。
修正後は 16 × 128 回以下。時間を試験の合否には使用しない。

Node v26.7.0、各条件を暖機後に前後交互で 7 回測定した中央値：

| 処理（128 件、1 ms 間隔） | 前 | 後 |
|---|---:|---:|
| `loadWith` 一回 | 7.04 µs | 0.51 µs |
| `firstFit` 一回 | 40.84 µs | 36.74 µs |

計画全体は分割候補を増やしたため、上の合成 1,000 局面を通す時間が
218.93 → 230.91 ms（5 回の中央値、約 +5.5%）だった。
「窓の検査が速いので計画全体も速い」とは結論しない。
Node の単一環境の計測であり、本番 Worker の CPU 時間ではない。
