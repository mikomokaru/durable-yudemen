`plan-quality-evaluation-plan-20260913.md` の要領で、コーパスを**本番の取り込み経路**へ
流し、同じ局面を TS と CP-SAT に解かせた。

結論は 2 つである。

1. **段 A（画面に出る全体）は測れない。** CP-SAT の接頭辞は 199 局面中 196 で合成に
   1 つも残らない。残った 3 局面は `pending ≤ 6` の局面**ちょうど 3 件**であり、
   偶然ではなく構造で決まっている（下記「なぜ落ちるか」）。評価計画 §6 の停止条件
   「6 件上限により比較対象が計画対象の一部にしかならない局面が半数を超えたら止める」に
   当たるので、段 A はここで止める。
2. **段 B（先頭 6 件だけ）は「TS の目的関数による採点」である。** `scoreSchedule` は
   TS 計画器自身の目的関数なので、この表は **TS の物差しで CP-SAT を測った**結果である。
   CP-SAT が別の目的で解いている以上、199 局面中 195 で劣るのは構造上ほぼ必然であり、
   **合意した評価項目（R4.3 の E1〜E9・R4.7 の待ちと各ペナルティ）での良し悪しはまだ測れていない。**
   独立の費用関数の実装は 7-B の残作業である（§「残作業」）。

3. 本番でも同じ条件が成立している。→ [`cpsat-adoption-20260913.md`](./cpsat-adoption-20260913.md)

### 取り込みは本番の関数だけを通る

`plu_no` → `OrderItem` の翻訳を再生側に一切書いていない。経路は次のとおりで、置き換えたのは
**宛先解決だけ**である（局面ごとに別の DO を使うため。翻訳には関わらない）。

```
コーパス行 {path,payload}
  → arrival_timestamp_ms / sequence_number を付与（上流が観測から付ける 2 値。payload は不変）
  → toRecordOutcome（src/ingress/outcome.ts・Worker の classifyRecords が 1 件ずつ呼ぶ関門）
  → StoreTimerDO.receiveRecords（本番 RPC・内側の toReceivedOrders が唯一の翻訳）
  → engine が RequestPlan を出す → shell が PlanRequest を組んで SOLVER へ送る
  → ハーネスが**その本番のボディをそのまま**受け取る ＝ 局面
```

局面（`PlanRequest`）は DO が組んだものであり、計画対象の選択規則（R2.3・`PLAN_TARGET_LIMIT`）
も `shownPlan` も本番のままである。翻訳の健全性は観測で裏づけられている——
`unknownNoodleType` は全局面で 0、`doDedupeSkipped` も 0 である。

## 段 A が成立しない理由——**卓の完全被覆**

`isStale`（`src/engine/schedule.ts:1095`）は一片について次を要求する。

```ts
const group = targets.filter((order) => tableKeyOf(order) === slice.tableKey);
if (group.length !== slice.placements.length) return true;  // 陳腐化
```

**一片はその Table_Group の計画対象を 1 つ残らず置いていなければならない。** 一方
`cpsatTargets`（`src/cpsat/request.ts:12`）は待ち行列を**先頭 6 件**に切る。ゆえに
「その卓の計画対象が 7 件以上ある」局面では、CP-SAT の一片は必ず陳腐化し、合成
（`committedSchedule` の `livePrefix`）でも受理（`admit` の段 1）でも落ちる。

コーパスは `table_no` が全 1,919 行で `1` なので、卓は常に 1 つである。したがって
`pending ≤ 6` の局面でしか接頭辞は残らない。実測がそのとおりになっている。

| 窓 | 比較できた局面 | 接頭辞が残った局面 | `pending ≤ 6` の局面 |
|---|---|---|---|
| 20 分 | 199 | **3** | **3** |
| 60 分 | 200 | **0** | 0 |

残った 3 局面でも合成後の総和は改善していない（6245→7040、7294→8972、5923→5923）。
`admit` は真の改善だけを採るので、**どれも採用されない**。

> これは「CP-SAT が悪い」という話ではなく、**6 件上限と卓の完全被覆が噛み合っていない**
> という配線の話である。卓が分かれていて 1 卓 6 件以下に収まる店舗では事情が違いうる。
> 本コーパスではそれを確かめられない（卓が不明）。

## この記録が言わないこと

- **クラウドの証拠ではない。** ローカル workerd での再生である。
- **釜が走っている局面を含まない。** コーパスに開始・完了の履歴が無いので `running` は常に空。
- **卓が分からない。** `table_no` は全行 `1`。`tableLag`・`orderSync` は卓の構造に効くので、
  この評価の卓関連の項は実態を代表しない。段 A が成立しない理由そのものが卓に由来する。
- **`pending` の作り方は窓の長さで決まる。** 完了が起きないので、窓を延ばせば件数が増える。
  60 分窓で p50 52.5・max 64（上限到達）となり本番の分布（p50 64・min 26）に近づくが、
  **本番のあの分布自体が、誰も操作していない dev 環境で待ち行列が上限に張り付いた形である。**
  厨房の実態と同じものではない。両方の窓で結論が変わらないことだけを主張する。
- **厨房での良し悪しではない。** 費用関数の上での差であり、費用関数が厨房の価値を正しく
  写しているかは別の問い（7-D）である。

## 残作業（7-B は閉じない）

### R-1. E1〜E9 を両方の計画に当てられる独立の費用関数

段 B は `scoreSchedule`＝**TS 計画器自身の目的関数**で採点している。合意した評価項目
（R4.3 の E1〜E9・R4.7 の待ちと各ペナルティ）での比較はまだ無い。

`experiments/cpsat-workers/tuning/schedule.ts` の `formulate` はモデルを組む側であって、
**任意の計画を採点する関数ではない**。両方の計画（TS の全体／CP-SAT の 6 件）を同じ E 項目で
採点できる関数を新たに書く必要がある。書く場所は engine ではなく評価側である
（engine の費用関数は 1 つのままにする）。

**`tableLag` が CP-SAT モデルに無いという事実の読みは、この関数ができるまで保留する。**
E 項目のどれかに対応するなら実のモデルの欠落、対応しないなら TS 固有の好みで、扱いが正反対である。
評価項目の表（R4.3）で決まる。

### R-2. 段 A を成立させる設計判断

**`isStale` の完全被覆を緩める案は採らない。** あれは plan-stability の不変条件であり、
CP-SAT のために崩せば TS 側の保証も動く。残る 2 案は測定なしには選べない。

| 案 | 効く条件 | 代償 |
|---|---|---|
| `cpsatTargets` を**卓単位**で切る（卓の対象をまるごと、上限まで） | 卓が分かれていて、卓ごとの対象が上限以下 | 卓が 1 つで 7 件以上なら、その店舗では CP-SAT が使えない |
| 上限を対象全件（最大 64）へ上げる | 卓構造に依存しない | モデルが最大 10 倍。CPU p50 949ms（本番実測）が大きく伸びる。予算規則の再設計と 2.4 の再測定が要る |

**本番の実 POS は `table_no` をすべて `1` で送っている**（2 系統 2,219 行）。卓単位の案は
現状そのままでは効かない。→ [`cpsat-adoption-20260913.md`](./cpsat-adoption-20260913.md) §3
