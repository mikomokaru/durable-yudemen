## 3. R5.10 — 素の配送遅延の許容値（案）

R5.10 は「実測した下限を後から許容値として追認しない」と定め、R8.7 は「厳密な応答時間の
合否閾値が必要なら、測定条件とともに別途承認する」と定める。**以下は案であり、承認を
いただいた値を試験前に固定する。**

| 区分 | 案 |
|---|---|
| p50 | **500 ms 以下** |
| p95 | **2,000 ms 以下** |
| 単発の最大 | **5,000 ms 以下** |

**根拠。** 固定問題の麺の茹で時間は 45〜75 秒である（manifest の `probe` プリセット）。
推奨が数秒遅れても、開始時刻を選び直せる窓は大きく残る。一方、求解自体が cloud 実測で
0.6〜2.8 秒かかるので、配送がそれと同程度を超えると「提案が届くまで」が倍以上になる。
p50 500ms はその手前に置いた線である。**厨房の許容がこれと違うなら、そちらを採る。**

**測定の定義。** 2 通りを併記する。

1. producer の `cpsat.dispatch-result`（投入完了）の `at` から、consumer の
   `cpsat.solver-accepted` の `at` まで。求解時間は含まない。
2. **Queue が付ける `message.timestamp` から consumer の受領まで。** consumer は受理した
   要求にも非 H1 の受領行を出し、`enqueuedAt`（`message.timestamp`）・`receivedAt`・
   `attempts`・`requestId` を載せる（実装済み。`solver.ts` の `receipt`）。**時計を 1 つ
   減らした値**であり、producer の時計を経由しない。収集側も この行を取り、1 件目を
   別掲した分布として出す（実装済み。`collect-observations.mjs` の `deliveryLatency`）。

バッチ待ちは 0 に設定するので、設定由来の待ちは入らない。

**測定条件。**

- 店舗：manifest の shim 系列 1 店舗（実 POS の流入なし）
- 問題：small（予算 0.01）と hard（予算 0.14）の両方
- 回数：各 20 件、間隔 3 秒。**理由は busy 回避ではない**——fetch 経路が cloud から
  消えたので busy は起きない。間隔を置くのは、**待ち行列の滞留を配送遅延に混ぜない**
  ためである（前の求解が終わる前に次を積むと、待ち時間が配送時間に見える）
- **冷起動は分布から外す。** ただし**系列の 1 件目だけを外す形では足りない**——isolate が
  入れ替われば途中でも初期化が起きる。受領行に `coldStart`（この受領が WASM の用意を
  負ったか）と `initializations` を載せ、収集側はそれで分ける（実装済み）
- 平常時分布：同じ店舗へ、求解が走っていない時に同じ経路で投入した値を別に取る

**この測定の限界（先に申告する）。** 定義 1 は producer と consumer が別 Worker であり、
`at` はそれぞれのホストの時計である。両者の時計ずれは定量していない。定義 2 は時計を
1 つ減らすが、Queue が `timestamp` を付ける時点と producer の投入完了は厳密には別である。
ゆえにこの値は**上界寄りの目安**であって、ミリ秒精度の主張ではない。閾値を数十 ms 単位で
争う値にしないのはこのためでもある。判定には定義 2 を主、定義 1 を参考として用いる。

## 4. 2.4 — 必要余裕の閾値（案）

初期案の「CPU 8,000ms 未満・余裕 10,000ms 以上」は `waitUntil` の 30 秒枠を分母に
していたので、そのままは持ち込めない。**分母が 2 つになり、性質も違う。**

| 分母 | 上限 | 案（正常系） | 停止 |
|---|---|---|---|
| consumer の **CPU 時間** | `limits.cpu_ms` に **10,000 ms** を設定 | **5,000 ms 以下**（余裕 5,000 ms 以上） | 8,000 ms 超で停止 |
| consumer の **wall clock** | **15 分・設定不可** | **30,000 ms 以下** | 60,000 ms 超で停止 |

**根拠。** cloud 実測（初期案の経路）で solver の CPU は 638〜3,145 ms、invocation wall は
701〜4,384 ms だった。CPU 5,000 ms は実測の最大に 1.6 倍の余地を持たせた線で、10,000 の
設定に対して半分の余裕を残す。wall の 15 分は求解に対して桁が違い**拘束条件にならない**
——実効の分母は CPU 側である。wall 側を 30,000 ms で見るのは、callback 待ちなどの I/O が
想定外に伸びたことを検出するためで、上限からの余裕（870,000 ms）を合格根拠にはしない。

**帯ごとの扱い**（2.5 は「閾値未設定」を不合格にするので、中間を空けない）：

| CPU の観測値 | 扱い |
|---|---|
| 5,000 ms 以下 | 合格 |
| 5,000〜8,000 ms | **合格にしない。試験は続行し、探索予算を見直して再測定する。**「正常系で上限の半分を超えた」を合格に数えない |
| 8,000 ms 超 | 停止。予算を見直すまで再投入しない |

wall 側も同様に、30,000 ms 以下を合格、30,000〜60,000 ms を「合格にしないが続行」、
60,000 ms 超を停止とする。

CPU と wall を**別欄で記録する**。混ぜると、どちらの上限に対する余裕か読めなくなる。

## 5. 費用

| 項目 | 見積りの根拠 | 概算 |
|---|---|---|
| Queue 操作 | 1 メッセージあたり write（producer）＋ read（consumer）＋ ack の 3 操作。下記の配分 66 件に再配送を見て 80 件、約 240 操作 | 百万操作あたりの課金に対し無視できる |
| consumer invocation | **求解時間が solver の invocation とは別に独立計上される。** 66 件 × CPU 最大 3,000 ms ＝ 約 200 CPU 秒 | 既存見積り（solver 128 件 × 10,000 CPU ms ＝ US$0.0256）の 6 分の 1 程度 |
| DLQ の保持 | 既定の保持期間で置く。試験後に**削除する**（下記） | 保持中のみ |
| 観測ログ | 1 件あたり 20 行前後 × 80 件 ＝ 約 1,600 行 | 既存見積りの範囲内 |

### 送出枠の配分 — **上限の引き上げは求めない**

2.1 で承認済みの固定上限は **solver への全送出試行 128 件**（manifest の `maxDispatches` も
128）。記録から数えた消費は **45 件**である。

| 実行 | 件数 |
|---|---|
| bootstrap | 1 |
| 小問題＋難問の初回 | 2 |
| 連続（間隔なし・429 で停止） | 2 |
| 連続 20 件 | 20 |
| 並行操作 1 回目・2 回目 | 8 |
| shim 系列（503 で不成立） | 3 |
| DO 占有 | 3 |
| no-await（無効 manifest・503） | 3 |
| no-await 本番 | 3 |
| **消費（概算）** | **45** |
| **残枠** | **83** |

**この数は概算である。** cloud のドライバは 2.2 で作った `ledger.mjs` を通っておらず、
累積の送出はジャーナルに記録されていない（[確定事項 U 節](./execution-method-findings-20260912.md)）。
上の数は各実行の報告書から数えたもので、台帳による確定値ではない。

残枠 83 に対する配分（合計 **66 件**、余裕 17 件）：

| 用途 | 件数 |
|---|---|
| 配送遅延：小問題 20 件・難問 20 件（§3） | 40 |
| 平常時分布（求解を走らせない投入） | 6 |
| DO 応答性の繰り返し（§7・条件 1 の実測） | 15 |
| 初期化・冷起動の確認 | 5 |
| **合計** | **66** |

上限の引き上げは求めない。**この配分を超えたら停止する。**

**ただし 128 件の上限は cloud では機械的に守られていない。** 承認する側が知っておくべき
事実として明記する。

- manifest の `maxDispatches` は solver の **isolate 内カウンタ**である。再配備や isolate の
  入れ替えで 0 に戻る。累積の上限にはならない。
- 2.2 で作った永続台帳 `ledger.mjs` は、cloud のドライバから**呼ばれていない**。
- ゆえに 128 件の実効は、**cloud ドライバの手作業の計数だけ**である。上の「消費 45 件」も
  各報告書から数えた概算で、台帳による確定値ではない。

台帳をドライバへ接続するのは、この試験の範囲では行わない——接続そのものが新しい
未検証の機構になる。**配分を守る責任が人手にあることを、承認の前提として記す。**

いずれも 2.1 で承認済みの **US$20 の予算枠**の中に収まる。単価は
[Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/) と
[Queues pricing](https://developers.cloudflare.com/queues/platform/pricing/) による。
**これらだけを請求額の上限とはしない。**

**DLQ の後始末。** 試験終了後、producer binding を外し、consumer 配備を戻したうえで
`cpsat-plan-requests-dlq` と `cpsat-plan-requests` を削除する。DLQ に残っている
メッセージがあれば、削除前に件数と `attempts` を記録する——消してから「何が落ちたか」は
再構成できない。

## 7. 配備前に測る 2 件（9.2）

配備の承認をいただいても、この 2 件を測るまで先へ進まない。**条件 1 は 2.3 の最初の
測定として実施し、その結果で 2.3 の残り（DO 復帰・連続実行）と 2.4 に進むかを決める。**
条件 1 が不成立なら、そこで止まって第9節へ戻す。

1. **consumer が呼出連鎖の外にあること。** 連鎖の外の DO が自店舗の求解中も 39〜52 ms で
   応答した実測（F6）からそう見える。**資料では確認できなかった**——2026-09-12 の公式資料
   検索で、consumer の起動と配置（スレッドの共有）に触れた記述は見つからなかった。
   ゆえに**資料ではなく実測で確かめる**。方法は DO 占有 harness を Queue 経路で再走する
   もので、これは 2.3 そのものである。配備前条件と 2.3 の測定が同一になる。
2. **素の配送遅延**（上記 3 の定義・条件で）。

**合格条件は「速いこと」ではなく「遅い回が混じらないこと」とする。** 同居が起きるとすれば
偶発であり、1 回の成功は証拠にならない。求解中の店舗 DO の応答を繰り返し測り、平常時の
分布に対する外れ値の有無で判定する。既存の測定は平常時 114〜195 ms・占有時 456〜533 ms と
分離が明瞭で、混入があれば見分けられる。

## 8. ローカルで示せていること・いないこと

| 示せた | 示せていない |
|---|---|
| 要求元の handler が求解を待たない（binding 経由 p50 254 ms に対し Queue 経由 p50 0 ms、各 10 回）。**絶対値は代表値ではない**——ローカルの Queue は実配送ではなく、cloud の `send()` の往復を含まない | 求解中の要求元の応答性（Miniflare は全 Worker を 1 プロセスで動かす） |
| 実チェーンが Queue 経由で完走（15 check・74 観測） | 素の配送遅延（ローカルの Queue は実配送ではない） |
| ack・retry・DLQ の経路（`attempts` 付き） | isolate の再利用と memory growth |
| 送出前のサイズ検査（実データ寄り 44,081 B・最悪 77,696 B／上限 128 KB） | 同期求解中に時計が進まない問題が Queue の境界で解けるか |

最後の 1 件は誤読しかけた点である。Queue 経路で `solve-started`→`solve-finished` に
233〜240 ms の幅が出たが、**同じ harness の fetch 経路も 232〜416 ms の幅を示した**ので、
幅はローカル workerd の時計の性質であって Queue の成果ではない。cloud で確かめる。
