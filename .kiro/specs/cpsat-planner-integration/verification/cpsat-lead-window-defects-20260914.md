# lead が作った 2 つの欠陥——走行中が「今」より前に上がる局面（2026-09-14）

## 0. この記録の位置

`cpsat-delivery-lead-20260914.md` で入れた **lead（モデルが置ける最も早い開始時刻を今 + 8 秒へ送る）**
は、採用 0% を直した一方で**別の欠陥を 2 つ生んだ**。本記録はその発見・原因・修正・配備を残す。

**見つかったのは本番の現場観測からである。** 官能評価の店舗 `yamaokaya-1108` を人が操作した
11:15〜11:26 UTC の 11 分間に、それまで一度も出ていない失敗理由が現れた。

## 1. 症状

`cpsat-plan-failed` の `reason` に **`other`（`CP-SAT invariant failed`）** が 3 件。
直近 3 時間の失敗 119 件のうち、これ以外の 116 件はすべて `no-solution` である。

| 窓 | 失敗 | 内訳 |
|---|---:|---|
| 〜11:34（修正前） | 116 | `no-solution` 116 |
| 11:24:58〜11:24:59 | **3** | **`other`（invariant failed）**・すべて 1108・走行中 2〜4 本 |

## 2. 原因——**「何も『今』より前には上がらない」という仮定が 2 か所にあった**

モデルの「今」は**受領の見込み時刻**（実時刻 + `CPSAT_DELIVERY_LEAD_MS` = 8 秒）である。
**走行中のタイマーはそれより前に上がりうる**——残り 3 秒の麺は、計画が届く頃にはもう上がっている。

### (a) 走行中の `end` の定義域が逆転する

```ts
const end = b.variable(
  r ? Math.max(now + 1, r.start + item.boilSeconds - tolerance) : ...,   // 下限
  r ? r.start + item.boilSeconds + tolerance : horizon,                  // 上限
);
```

`tolerancePercent` は 0 なので上限 = `r.end`。`r.end < now + 1` のとき **下限 > 上限**となり、
`variable(lo, hi)` の `assert(lo <= hi)` が落ちる。**求解ごと失敗する**（1 杯ではない）。

### (b) クラスタ時刻の下限が「今」

```ts
const timeLo = Math.max(now + 1, soonest);
```

クラスタは `x[i][k] ⇒ end_i = T_k` で杯の上がり時刻を表す。走行中の `end` が `now + 1` より前だと
**どの `T_k` にも一致できず**、求解が `INFEASIBLE` になる。

**(a) を直すと (b) が出る**という重なり方だった。

## 4. 修正

| # | 場所 | 変更 |
|---|---|---|
| (a) | `formulate` の `end` の定義域 | **走行中には「今より後」を課さない**。上がる時刻は事実であって境界で締めるものではない。未着手の側は従来どおり `now + 1` |
| (b) | クラスタ時刻の下限 | `max(now + 1, soonest)` → **`soonest`**（最も早く上がる杯）。`now` は見込み時刻なので床にできない |

## 5. 回帰試験

`tests/cpsat-running-near-lift.example.test.ts`（実 WASM・harness 経由）。

| 主張 | 内容 |
|---|---|
| lead の窓の**内側**（残り 1 秒）で上がる走行中があっても解ける | 旧実装はここで全滅した |

**この試験は合成の走行中を要する。** 走行中のある局面は人が操作している店にしか現れず、
コーパスだけでは永久に踏めない——今日の実測でも、走行中があったのは 21 店中 **2 店だけ**だった
（1108 と 1125。どちらもこの日に人が触った店）。

## 8. 読み——**lead は 1 つ直して 2 つ作った**

| 効果 | 内容 |
|---|---|
| 直した | 採用 0%（322/322 棄却）→ 90%+ |
| 作った | 走行中が lead の窓の内側で上がると求解が落ちる（本記録） |

design 第 5.3 節の**補正（第二線・受領側で実際の遅れだけずらす）は実装済み**なので、
**lead を短くすればこの窓も狭くなる**。lead の値の見直しは、本修正の効きを本番で確かめてから行う
——「式・遅れ・補正率・棄却率」を 1 組で記録する規律（`cpsat-delivery-lead-20260914.md` §5）に従う。

## 8.1 配備後の実測（11:34:43Z の前後・各 40 分ほど）

| | 求解 | 失敗 | 内訳 | **走行中ありの求解 → 失敗** |
|---|---:|---:|---|---|
| 配備前 | 209 | 16 | `no-solution` 13・**`other` 3** | 34 件 → 15（44%） |
| 配備後 | 54 | 3 | `no-solution` 3・**`other` 0** | **3 件 → 3（100%）** |

**言えること。** `other`（`CP-SAT invariant failed`）は **3 → 0**。直した欠陥そのものは消えた。

**言えないこと。** `no-solution`（status=UNKNOWN）は減っていない。配備後に走行中のある求解は
**3 件しかなく（すべて 1125）、その 3 件とも失敗**している。**標本が小さすぎて率を主張できない**
——人が操作を止めたので走行中の局面が発生していない。

**したがって本修正は「invariant の失敗を消した」ところまでが実測の範囲である。**
本番の失敗の主因である `no-solution` には効いていない、あるいは効きが測れていない。

### `no-solution` の当たり所（次の作業）

`status=UNKNOWN` は**予算内に実行可能解が見つからない**ことを意味する。今日の実験では
「予算を 6 倍にしても目的値が動かない」ことを確かめているが、**それは走行中 0 の局面**での話で、
走行中のある局面では未測定である。区別すべき仮説は 2 つ。

| 仮説 | 確かめ方 |
|---|---|
| 予算が足りない（走行中の寄与が 4 本で頭打ち） | 走行中 5 本以上の局面で予算を振る |
| hint が実行不能で、探索が最初の解を自力で探している | `fixHints` で走行中のある局面の hint を固定して解く |

**どちらもローカルで測れる。** ただし合成の走行中が本番を写している保証は無いので、
`cpsat-plan-failed` に**釜ごとの空き時刻と上げ時刻の分布**を足して、本番の局面そのものを
取りに行くのが確実である（`local-vs-production-gaps` #8）。
