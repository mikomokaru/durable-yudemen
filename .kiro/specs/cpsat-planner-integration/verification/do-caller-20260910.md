# 呼出側が Durable Object のとき — ローカル計測

証拠: `do-caller-local-20260910.json`, スクリプト `check-do-caller.mjs`
前段: `accept-boundary-20260910.md`（機構の同定）

## なぜこれを測るか

これまで cloud で通したのはすべて、要求を出すのが probe 入口（ただの
entrypoint）である経路だった。その間も店舗の操作は 39〜52ms で返っていたが、
それは**呼出側が DO ではなかったから**である。アプリが実際に使う配置では、
店舗 DO 自身が Persist の Effect から `SOLVER` を呼ぶ。占有されるのがその DO
なら、話がまったく違う。

## 手順

DO を 1 つ用意し、同じオブジェクトに 2 種類の要求を出す。

- `/plan`：Effect と同じ形。`SOLVER` を呼んで待つ。
- `/ping`：その店舗が並行して捌かねばならない他の通信（注文の到着、Timer 開始）。

`/plan` を await せずに投げ、120ms 後に `/ping` を送る。子は 3 通り
——実 solver（実 WASM・hard・予算 0.14）、同期 1,500ms、非同期 1,500ms。
平常時の `/ping` を先に 3 回測り、遅い DO を占有された DO と取り違えないようにする。

## 結果

| 子 | DO の fetch 解決 | body 処理 | 待機中の `/ping` | 平常時の `/ping` |
|---|---|---|---|---|
| **実 solver** | 481ms | 0ms | **366ms** | 11, 2, 1ms |
| 同期 1,500ms | 1,500ms | 0ms | **1,381ms** | 4, 1, 1ms |
| 非同期 1,500ms | 1ms | 0ms | 2ms | 3, 1, 1ms |

**子の応答後の仕事が同期であるとき、呼出側の DO は自分の通信を捌けない。**
`/ping` は求解が終わるまで待たされ、遅れはおおよそ求解の残り時間に等しい。
非同期の子では 2ms で、DO の要求が直列化しているわけではないことも分かる。

## 何が言えるか

design 第 9 節は、この配置の成立条件を 2 つ挙げている。

> 求解より前に受理が観測できることと、**求解中の Timer 操作・通知が処理できる
> こと**を cloud 上で検証する。

呼出側が DO のとき、後者はローカルでは成立していない。cloud で 39〜52ms が
出ていたのは、要求を出したのが DO ではなかったからであり、この配置の証拠には
ならない。

## 何が言えないか

- **ローカル workerd は cloud ではない。** Miniflare は全 Worker を 1 つの
  workerd プロセスで動かすので、同一スレッドはむしろ保証されている。cloud で
  同じ占有が起きるかは別に確かめる必要がある。cloud 側で分かっているのは、
  entrypoint 呼出側が求解と同じ長さ待たされたこと（1,292〜3,270ms）までである。
- **cloud で DO 呼出側を通すには shim 系列が要る。** 配備済み shim の manifest
  が無効なため、この経路は一度も通っていない。確かめるには shim の再配備が要る。
- `/ping` は遅れはしたが**完了はしている**。「捌けない」は「失敗する」ではなく
  「求解の残り時間だけ待たされる」である。厨房の Timer では 3 秒の遅れが許容
  できるかは別の判断であり、ここでは測っただけである。

## 次

cloud で shim 系列（DO の Effect → SOLVER → shim → solver）を通し、同じ占有が
起きるかを確認する。起きるなら第 9 節の実行契機を作り直す。起きないなら、
ローカルの同一プロセス構成が原因だったことになり、この配置は残せる。
いずれにせよ 2.5 の判定はその後である。

必要な cloud 変更は shim の再配備 1 件（有効な manifest を同梱）で、
アプリ・solver は変更不要。承認事項として別に提示する。
