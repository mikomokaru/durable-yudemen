# 計画の質の評価計画（2026-09-13）— **測定の前に固定する**

task 7-B（元 7.2）の実施要領。R8.7 が「厳密な合否閾値が必要なら測定条件とともに別途

## 0. この評価が答える問い

**同じ局面を TS と CP-SAT に解かせたとき、費用の内訳がどう違うか。**

答えないもの：厨房での良し悪し（それは 7-D で調理者が判断する）、応答時間、運転の安定性。

## 2. 局面の作り方

コーパスは注文の到着だけを持ち、**開始・完了の履歴を持たない**。ゆえに局面は再生で作る。

1. ファイル単位（＝店舗・日・時間帯）に到着を時刻順へ並べる。
2. 本番の取り込み経路（`toRecordOutcome` → `StoreTimerDO.receiveRecords` → `RecordsReceived`）へ
   流す。**これは合成ではなく実 DO の遷移である。**（当初は `OrderArrived` と書いていたが、
   それでは取り込み変換の写しを作ることになる。写しは作らない——2026-09-13 の訂正。）
3. **開始・完了は入れない。** 履歴に無いものを仮説で足すと、その仮説が結果を動かす。
   ゆえに**この評価の局面は `running` が空である**——釜が走っている局面の比較は
   別に設計する（下記 §7 の限界）。
4. 各到着のあと `RequestPlan` が出た時点を 1 局面とする。指紋が変わらなければ要求は
   出ないので、**局面数は到着数より少ない**。

### 抽出

- **seed：`cpsat-plan-quality-20260913`**（文字列。標本を選ぶ疑似乱数の種）
- **局面数：各ファイルから最大 20、全体で最大 200。** ファイル内で一様に選ぶ。
  200 に満たなければ全数を使い、実数を報告する。
- 局面ごとに保存するもの：`storeId`・時刻起点・`pending` 件数・`running` 件数（0）・
  入力のハッシュ（`cpsatInputDigest`）・使った係数群の識別子・**取り込み変換の識別**。

**取り込み変換の識別を保存する理由。** 取り込み経路（`/pos/records` の変換）のコードが
変われば、**同じ payload から別の局面ができる**。あとで結果を比べたとき、差が計画の差か
変換の差か分からなくなる。ゆえに変換に関わるソースのハッシュを局面ごとに残す。

### 取り込みは本番と同じ経路を通す

**再生用に別の写しを書かない。** 写しが 2 つあると、差が計画の差か変換の差か分からない。
条件は 2 つである。

1. **本番と同じ選択規則を通す。** 計画対象は R2.3 の規則と上限（`PLAN_TARGET_LIMIT` 64、
   注文品目の上限 4096）で絞られる。再生でも同じ関数で絞る。
2. **局面の `pending` 件数を本番の分布と照らす。** 本番の実測は p50 64（上限に張り付き）・
   min 26 である。再生がこれと懸け離れた形の局面を作っているなら、同じものを比べて
   いない——その場合は§6 の停止条件に当たる。

## 4. 比較表の欄

**R4.8 に従い、返却された計画から費用を独立に再計算する。ソルバーの報告目的値は
使わない。** 両計画器の解を同じ `scoreSchedule`（`src/engine/objective.ts`）に通す。

### 費用関数は 2 つある。取り違えない（2026-09-13 の訂正）

本計画の初稿は欄を `liftOverflowCost` 60・`clusterCost` 30・`gapShortfallWeight` 2 …
という 12 係数（E1〜E9）で並べていた。**あれは CP-SAT モデル自身の目的関数**
（`experiments/cpsat-workers/tuning/defaults.json`）であって、engine の費用ではない。
engine の `scoreSchedule` にその項は存在しない（`src/` に当該の係数名は 1 つも無い）。

初稿のままでは、TS の計画をその欄で採点する手段が無い——CP-SAT の目的関数を engine の
外で書き直すことになり、§4.2 の「1 つの関数を両方に当てる」に自分で反する。ゆえに欄を
`scoreSchedule` の項へ置き換える。**測定の前に直した**（この欄で測った数値は無い）。

### 欄（`scoreSchedule` の項）

内訳は `scoreSchedule` を再実装せずに取り出す。各項は自分の係数に対して線形なので、
**係数を 1 つずつ 0 に置いた総和との差**がその項の値に厳密に一致する。定義を書き写せば
engine が式を変えたときに黙ってずれるので、書き写さない。

| 欄 | 内容 | 取り出し方 |
|---|---|---|
| `waitTime` | Σ Wait_Time（未着手の配置のみ・R4.2） | 残差（`businessCost` から下の 4 項を引く） |
| `tableLag` | w_table × Σ Table_Lag（卓の遅れの和） | `tableSyncWeight: 0` との差 |
| `orderSync` | w_order × Σ(同一オーダーの提供時刻差の許容超過) | `orderSyncWeight: 0` との差 |
| `affinity` | w_affinity × Σ max(0, slot 距離 − 許容距離) | `affinityWeight: 0` との差 |
| `liftOverflow` | 上げ窓で arms を超えて上がる本数 × L 秒 | `arms: 10000` との差 |
| `businessCost` | 上の 5 項の合計（Change_Cost を含まない） | `change: null` の総和 |
| `changeCost` | 旧 Shown_Plan からの変更費用（秒相当） | `total − businessCost` |
| `total` | `businessCost + changeCost`（＝採用判定が見る値） | `scoreSchedule(...).total` |
| `placements` | 配置した杯数 | |
| `targets` | 生成へ渡した計画対象数（CP-SAT は `cpsatTargets` の 6 件上限） | |
| `status` | `OPTIMAL`／`FEASIBLE`／その他 | |
| `reportedObjective` | **CP-SAT モデル自身の目的値。`total` とは別の費用関数の値であり、大小を比べられない。** 観測のためだけに残す | |

**`reportedObjective` と `total` の差を「ずれ」と読まない。** 単位も項も違うので、差が
出るのが正常である。R4.8 が禁じているのは「ソルバーの報告値で採否や優劣を決めること」で
あり、それは `scoreSchedule` を両方に当てることで満たしている。

### だが `scoreSchedule` は TS 計画器自身の目的関数である（2026-09-13 の但し書き）

「1 つの関数を両方に当てる」は満たすが、**当てている物差しは TS のものである**。CP-SAT が
別の目的で解いている以上、この採点で CP-SAT が劣るのは構造上ほぼ必然であり、**合意した
評価項目（R4.3 の E1〜E9・R4.7 の待ちと各ペナルティ）での良し悪しは、これでは測れていない。**

ゆえに比較表には必ず「**TS の目的関数による採点**」と明記する。そして 7-B の残作業として、
**E1〜E9 を両方の計画に当てられる独立の費用関数**を置く。

- `formulate`（`experiments/cpsat-workers/tuning/schedule.ts`）はモデルを**組む**側であって、
  任意の計画を**採点する**関数ではない。新たに書く必要がある。
- 書く場所は評価側であり engine ではない（engine の費用関数は 1 つのままにする）。
- **`tableLag` が CP-SAT モデルに無いという事実の読みは、この関数ができるまで保留する。**
  E 項目のどれかに対応するなら実のモデルの欠落、対応しないなら TS 固有の好みで、扱いが正反対である。

## 4.1 比較は 2 段で持つ

TS は `pending` の全件を計画するが、CP-SAT が置くのは `cpsatTargets` の**先頭 6 件**だけで、
残りは engine の合成（`committedSchedule`）が埋める。**厨房が見ているのは合成後の全体**
である。ゆえに 2 段で持つ。

| 段 | 比べるもの | 何の良し悪しか |
|---|---|---|
| **A：表示される全体** | CP-SAT 6 件＋合成した尾部 **対** TS の全体 | **現場の良し悪し**。画面に出るものの比較 |
| **B：先頭 6 件だけ** | CP-SAT の 6 件 **対** TS の同じ 6 件（同一集合に絞った部分計画） | **CP-SAT 自体の良し悪し** |

**混ぜてはならない。** 混ぜると §6 の停止条件「別のものを比べている」に自分で当たる。
§4 の欄は A・B の両方について出す。

## 4.2 費用の再計算は 1 つの関数を両方に当てる

TS の出力と CP-SAT の出力を**同じ `scoreSchedule`** に通す。計画器ごとに別の計算を書くと、
差が計画の差なのか計算の差なのか分からなくなる。内訳も同じ 1 関数から取り出す（§4）。

CP-SAT の `reportedObjective` は別欄に残すが、**`total` とは比較しない**（§4 の訂正）。

## 5. 判定の仕方

**「どちらが良い」を単一の数で言わない。** 出すのは次の 3 つである。

1. **局面ごとの `total` の差**（CP-SAT − TS）。分布（min／p25／p50／p75／max）と、
   CP-SAT が下回った局面の比率。
2. **内訳の差**。どの項（`waitingCost`・E1〜E9）が差を作っているか。
   「CP-SAT のほうが待ち時間は短いが E2 が増える」のような形で出す。
3. **比較できなかった局面**とその理由（片方が解けない、対象数が違う、など）。

**相関から原因を断定しない。** 差が特定の項に偏っていても、それが「その項の係数のせい」
とは言わない。言えるのは「差はここに出ている」までである。

## 6. 停止条件

- **片方が解けない局面が全体の 1 割を超えたら止める。** 比較の前提が崩れている。
- **独立再計算と報告目的値の差が、同一計画器の中で局面ごとに符号を変えたら止める。**
  再計算の実装が疑わしい。
- **`cpsatTargets` の 6 件上限により、比較対象が計画対象の一部にしかならない局面が
  半数を超えたら止める。** 別のものを比べていることになる。
- 実行時間が想定（200 局面 × 2 計画器 × 数百 ms ＝ 数分）の 10 倍を超えたら止める。

## 7. この評価が言わないこと（限界を先に書く）

- **釜が走っている局面を含まない。** 履歴に開始・完了が無いので `running` は空である。
  本番では `running > 0` の局面があり、そこでの比較は別に設計する。
- **卓が分からない。** コーパスの `table_no` はすべて `1` で、実卓か POS の既定値か
  判定できない（R2.6 の「不明」）。E4・E8 は卓の構造に効くので、**この評価の卓関連の
  項は実態を代表しない**。
- **提案の良し悪しではない。** 費用関数の上での差であり、費用関数自体が厨房の価値を
  正しく写しているかは別の問いである（7-D）。
- **本番の局面ではない。** 2026-09-05〜08 の注文で、いま運転している 73 店舗とは別である。
