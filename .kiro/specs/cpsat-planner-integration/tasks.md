## 進行規則とゲート

**2026-09-12・F-1 承認、task 3 着手。** F-1（CP-SAT モードの Effect 列の例外・R5.8／R9.12）の再確認を得た。2.5 は Queue 方式で成立とした（ユーザー判断・満たしていない条件を承知で進める）。よって 3.2 以降のゲートは開いた。着手した内容：
- **本物の solver に Queue consumer を接続**（`src/cpsat/worker.ts`）。既存の `planCpsat`（実モデル生成 → protobuf → CP-SAT → 検証 → `CookSchedule`）をそのまま使い、`deliver` の完了まで待って明示 ack する。`fetch` handler は残すが cloud からの到達経路は無い。
- **店舗 DO を producer にした**（`src/shell/store-timer-do.ts` の `requestPlan`）。`PLANNER_BACKEND` が `ts`（既定）なら既存の Service binding、`cpsat` なら `CPSAT_PLAN_QUEUE.send()`。**await するのは投入の完了だけ**で、求解も配送も待たない。不明な値は TS に読み替えず `configuration-invalid` を記録して要求を止める。`CPSAT_ACTIVATION_ID` が空なら同じく止める（要求の同一性に入るため・R1.6）。
- **送出前のサイズ検査を src へ置いた**（`src/cpsat/request.ts` の `checkCpsatPayload`）。1 通に収まらない要求は送らず理由を残す（R6.4）。
- 設定ガードを反転した——`PLANNER_BACKEND` が「無いこと」ではなく「**`ts` であること**」を固定する。CP-SAT を有効化する変更は、このガードが落ちることで必ず目に入る。
- 試験バンドルの分離ガードから `src/cpsat/request.ts` を外した（shell が正当に使うため）。`plan.ts`・`protobuf.ts`・`worker.ts` と tuning／Python は引き続き排除する。

**まだ CP-SAT は有効化していない。** `PLANNER_BACKEND: "ts"`・`CPSAT_ACTIVATION_ID: ""` のままで、配備もしていない。有効化は別の承認である。


**2026-09-12・2.5判定：不成立。** 判定したのは応答性条件だけで、2.5 全体の合否ではない。根拠は cloud 実測——求解中に同じ店舗 DO へ届いた独立した接続が、求解の終了と同時刻にしか完了しなかった（平常時 120〜192ms に対し 491〜533ms、重なり確認 2/3 ラウンド）。[記録](./verification/cloud-do-occupancy-20260912.md)。原因は `waitUntil` でも応答 body でもなく、求解が同期であること自体である（[切り分け](./verification/accept-boundary-20260910.md)）。await しない位置を 1 ホップ手前へ動かしても効かなかった（[cloud 検証](./verification/cloud-noawait-20260912.md)）。停止条件に従い 3.2 以降へ着手せず、第9節へ戻した。**方式の変更であって、CP-SAT・WASM・観測・台帳・requirements の否定ではない**——それらの成果は保持する。

**2026-09-12・新方式での再開条件。** 2.3〜2.5 は Queue 方式で測り直す。第9節 9.2 の配備前条件 2 件（consumer が呼出連鎖の外にあること・素の配送遅延）を先に満たす。合格条件は「速いこと」ではなく**「遅い回が混じらないこと」**とする——同居が起きるとすれば偶発であり、1 回の成功は証拠にならない。Queue の作成と consumer の配備は、対象・差分・費用を示した明示承認を経る。第9節の書き換えを作成許可に読み替えない。
