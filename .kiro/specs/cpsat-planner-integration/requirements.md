# Requirements Document

## Introduction

本 spec は、`timer-dev.yamaokaya.org` が実際の操作画面に提示する調理計画を、既存の TS 計画器から単一スレッドの CP-SAT WASM 計画器へ切り替え、元へ戻せるようにする。

目的は、CP-SAT を前提に、実際に解かせたい問題を安定して解けることと、厨房で使ったときの提案の良し悪しを確認することである。既存 TS 計画器とのスコア競争を採用条件にしない。官能評価と計測の結果を得てから、条件・係数の見直し、CP-SAT の継続採用、必要なら TS ネイティブへの再実装を判断する。

**状態：2026-09-12、CP-SAT を `timer-dev.yamaokaya.org` の全店舗で有効化し、運転中である（実利用者が乗っている）。2.5 の判定は不合格のままで、ユーザー判断による有効化である。R5.10 の配送遅延は p50 307 ms で 800 ms を満たし、p90 1,049 ms・max 2,131 ms（2026-09-13・`inputKey` のハッシュ化後）。p95 2,000 ms の扱いは未決である。R6.9／R6.10 の資源は上限内（CPU max 3,649 ms／上限 10,000・超過 0 件）。要件承認済み。F-1 による Effect 列の例外（R5.8・R9.12・差分表）も 2026-09-12 に再確認・承認を得た。2026-09-12、design 第9節の輸送方式変更（Service binding → Queue）に伴い R5.10 を新設し、R6.4・R6.7 へ追記した（配送遅延・輸送層の再配送・同一入力の複数回求解）。この差分もユーザー指示により追加したものであり、F-1 と同じく再確認の対象とする。重複応答と応答順の逆転は R5.3 が既に無条件で覆っており、変更していない。** **2026-09-13、ユーザー判断により R4.4・参考事実 4・評価項目 E1・差分表を改訂した**——`arms` はペナルティ、`arms + HELPER_ARMS` は計画のハード制約とし、CP-SAT の計画も `admit` も同じ規則で判定する。`severeLiftOverflowCost` は不使用となる。改訂の契機は、モデルが両方を値段にしていたために生成した計画が `withinLiftCap` で全数棄却され、本番 165 店舗・334 件の受領すべてで採用 0 件だったという実測である。同日さらに、**ユーザー判断により E4（組ごとの距離の和 → クラスタの広がり）・E7（全組の逆転 → 隣接組の逆転）を改訂し、E8 の距離生成を同一注文の組に限ることを決めた**。契機は、上げ窓を累積資源へ畳んだあと残る変数の大半が対の項になり、対象 32 件以上でモデル規模の防壁に当たったことである（全件 64 の計画は D2 で確定済み）。定義変更ゆえ同値性は成立しないので、**旧定義と新定義を同じ計画の上で計算した順位相関**で検証する（design 第 7.4.2 節）。** 同日、ユーザーは [design](./design.md) を承認し、[tasks](./tasks.md) の作成を指示した。設計承認は F-1 の追加差分の再確認を代替せず、依存する実装・property 改訂は tasks の再確認ゲートの後に置く。作業ツリーにある組み込み途中のコードを実装完了の根拠にしない。今回の tasks 作成では実装の続行・デプロイを行わない。

### 対象と不変点

- 対象は `timer-dev.yamaokaya.org`。対象外の環境へ一括展開しない。
- 変更するのは計画器の選択、計画要求・結果採用、既存画面へ提案を渡すために必要な接続部分である。
- UI、クライアントとの通信形式、注文・Timer の既存の永続フィールドの形と意味、店舗の既存データを維持する。永続への追加が必要な場合は、復帰先の旧 TS 版が無視できる省略可能フィールドに限る（R7.5）。既存データの変換や DO の再作成を前提にしない。
- 注文の取り込み、開始・麺揚げ・完了・取消・手動調整、音声通知、既存のオフライン動作を変更対象にしない。
- 技術実証時の「engine・DO を変更しない」から、今回の切り替えに必要な接続変更だけを範囲に加える。既存 TS 計画器のアルゴリズムを改善する変更は含めない。

### これまでの合意と参考事実

1. 求解は Cloudflare 上の Workers で単一スレッドの CP-SAT WASM を使う。WASM は C++ 製で、オンラインの計画経路に Python や Node.js の実行環境を必要としない。
2. 打ち切りは探索量に基づく。実時間の時計が進むことを、探索停止の成立条件にしない。予算は事前にわかる複雑度から動的に決める。
3. 業務の事実・ハード制約、報酬・ペナルティ、探索予算を分ける。将来の自然言語変換の対象は報酬・ペナルティ設定だけであり、今回その変換機能は作らない。
4. `arm` および `arm + 2` を超える麺揚げ負荷は、二段階の高いペナルティを持つソフト制約とする。後段はより重くする。**これは PoC（`experiments/cpsat-workers`）の形である。2026-09-13、本組み込みでは後段（`arm + 2`）をハード制約へ改めた（R4.4）**——engine の `withinLiftCap` が計画に対してハードに掛かっており、値段のままでは目的関数が得と判断した瞬間に上限を超える計画が出て、ゲートが丸ごと棄却するためである（実測で採用 0 件の本体だった）。PoC の記述はこの経緯として残す。
5. **ユーザー確認：POS は卓未定時に `table=1` をフォールバックとして使うため、この値の一致は実際の同卓を意味しない。** 異なる実卓の客が同じ値を持ち得るが、この値だけで全員別卓とも判定できず、個々の `1` が必ずフォールバックであるとも断定できない。初回の実データ検証で申告卓番号が `1` のみとなるのは既存サンプルの範囲（参考事実14）の帰結であり、物理的な単一卓を評価対象に選んだわけではない。「`table=1` の運用＝物理的に単一卓」「実際の複数卓は将来の対象」という前提は撤回する。現行の取り込みは `1` を `tableId="1"` として保存し、`tableMembers`・`tableKeyOf` はその同値を卓の所属として扱うため、`Table_Group` が店舗全体に退化するのはコード上の帰結であって業務上の同卓の証拠ではない。`recommend` の一片・錨依存の群導出は R2.6・R3.7 に従って接続を検証する（[取り込み](../../../src/shell/store-timer-do.ts)、[卓の投影](../../../src/engine/project.ts)、[群の導出](../../../src/engine/recommend.ts)）。
6. 現行アプリは未着手の先頭最大64件を計画対象とする。一方、過去のクラウド探索は**未着手の先頭最大6杯＋調理中**の範囲で行い、その範囲で通信往復を含む応答が平均約0.64秒、p95約2.44秒、最大約6.49秒、モデル変数数の最大が5011だった。調理中を含むため「モデル全体が6杯」という意味ではない。実験の再生入口は `pendingLimit` の既定6・許可範囲1〜20であり、21杯以上を指定した再生は拒否する。これらの実測は64杯規模や、新しいオンラインのモデル生成・直列化、操作から画面反映までの証拠ではない。6杯を本組み込みの上限として採るかは未決である。
7. 過去の探索では初期値が評価済み候補中の最良に残った。大域的な最良、現場での最良、今回の組み込み後の最良を証明した結果ではない。
8. 購入時刻を保持していないことは欠落ではなく、[pos-order-ingress Requirement 8](../pos-order-ingress/requirements.md) の既決事項である。AC 8.1 は上流観測時刻 `arrival_timestamp_ms` を `arrivalTime` の起点とし、AC 8.3／8.7 は券売機申告時刻 `payload.datetime` を起点にも永続属性にも使わず、AC 8.4 は DO 受理時刻も起点にしない。本組み込みでは実購入時刻は利用できないため、オンラインの待ち・順序は `arrivalTime` を代理値として評価し、「購入待ち時間の実測」とは呼ばない。この決定を design で再検討しない。
9. 待ち時間の集計は [CONTEXT.md の「麺揚げ待ち時間」](../../../CONTEXT.md) に従い、**各杯の経過秒数の和、占有2でも1杯分**で確定する。同じ会計でも各杯を足し、会計の最後の麺揚げまでを1回だけ数える集計は採らない。オンラインでの代理起点は前項による。
10. 過去の WASM 検証には、`FEASIBLE` の報告目的値が返却解からの再計算値と異なる既知事象がある。返却計画の有効性と目的値の報告精度は分けて検証する。
11. 過去実験の TS モデルから protobuf への直列化は Python bridge が担っていた。Workers 内でモデル生成・直列化・復号まで行う今回の経路には、その実験の検証結果はそのまま適用できない。R6.8・R9.9 で実行場所とモデルの同値性を検証する。
12. [初期 PoC の設定](../../../experiments/cpsat-workers/wrangler.jsonc) は CPU 上限1000 ms、[クラウド探索の記録](../../../experiments/cpsat-workers/results/cloud-search-20260909c.json) は10000 msで、後者のプラットフォーム観測 CPU 最大は4572.93 msだった。対象 Worker の上限は実際の配備時に確認する。CPU 上限による invocation の失敗は、CP-SAT が暫定解を返す探索量打ち切りとは別である（[Cloudflare の CPU 制限](https://developers.cloudflare.com/workers/platform/limits/#cpu-time)）。
13. 実験の CP-SAT モデルは注文の識別子を同一注文の費用に使い、`table=1` を全注文の同期根拠にはしていない。今回の訂正はその評価方針を覆すものではない。一方、アプリへの変換で `tableId` に基づく錨・群を導くと、卓未定値の一致を同卓として再導入する余地がある。なお [Boil_Sync 本体](../../../src/engine/sync.ts) は卓番号ではなく時間窓と `arms` に基づいて調整するため、この説明だけを理由に Boil_Sync のアルゴリズムを変更しない。
14. 2026-09-09 に既存サンプルの全 JSONL を再集計した結果、[noodle_plan_histories](../../../docs/data_samples/noodle_plan_histories) は20ファイル・1919レコード、[kenbaiki_orders](../../../docs/data_samples/kenbaiki_orders) は10ファイル・300レコードで、`payload.table_no` はすべて数値の `1` だった。各非空行を1レコードとして数えた値であり、重複排除後の注文数や杯数ではない。欠落・null・0・1以外の申告値の実例はなく、フォールバックと確定した実卓番号 `1` を識別する根拠は既存サンプルにはない。[toTableId](../../../src/shell/store-timer-do.ts) は欠落・`0`／`"0"` を `null`（卓なし）へ写す別の規則を既に持つ。`1` は保存される申告値であり、この null 代替ではないが、実卓か POS の既定値かはデータだけでは判定できない。今回の扱いは R2.6 の「不明」で確定し、POS 側の仕様への追加照会を前提にしない。

参考：[実験のモデルと評価量](../../../experiments/cpsat-workers/tuning/README.md)、[クラウド探索の実測と限界](../../../experiments/cpsat-workers/CLOUD_SEARCH_EXTENSION_RESULTS.md)。

### 評価・報告の規律

報告では、計画の質、実行可能性、実行時間、現場での使いやすさを別の判断として扱う。過去実験や別モデルでの最良を今回の最良へ読み替えず、未測定の区間を実測済みとせず、相関だけを最大の原因と断定しない。この規律をシステムの動作 AC と混ぜず、測定条件・適用範囲・検証状態を成果物の欄として検査する（R8.2〜R8.4・R9.8〜R9.9）。

### スコープ外

- 新しい評価用 UI、管理画面の設定編集機能、表示デザインの変更。
- SMAC の追加探索、自然言語からの設定変換、自動的な係数更新。
- 人員・技能プロファイルの新規導入。今回使うクラスタ間隔の仮説は明記するが、人数別の推定機能は作らない。
- StoreDO や Snowflake からの追加の履歴収集。検証は既存サンプルと、対象環境で許可された操作を使う。
- 未知の将来注文を使う最適化、全待ち注文を無制限に同時求解すること。
- ネイティブ版によるオンライン代替実行、対象外環境への展開、最終的なソルバー採否の確定。
- 実際の卓の推定・架空の卓の割当、POS に卓確定情報を追加する変更、確定した実卓に基づく新しい同期方針。卓未定の注文が実際には複数卓へ分かれること自体は、今回の評価範囲に含む。
- 対象 POS 側の仕様への追加照会による、フォールバックと確定した実卓番号の識別規則の調査。

## Glossary

- **計画器**：現在の注文・Timer・店舗設定・前回提案から、未着手品目のスロットと開始・麺揚げ時刻を提案する計算。Timer の操作を実行する権限は持たない。
- **局面**：ある基準時刻の未着手品目、調理中・麺揚げ済み未完了の Timer、配置、設定、前回提案、および利用可能な直近の麺揚げの事実。
- **計画対象**：その回に配置・時刻を求める未着手品目の集合。待ち行列全体や、制約として参照する調理中の品目とは区別する。
- **注文・実際の卓・卓未定**：[CONTEXT.md](../../../CONTEXT.md) の定義に従う。同じ注文は注文識別子で判定するが、それを同卓の証明にはしない。
- **POS 申告卓番号**：`payload.table_no` から既存の取り込み規則で保持する `tableId`。卓未定のフォールバック値を含むため、値の一致と実際の同卓は別の事実である。生の申告値を維持することと、計画でその値を同卓の根拠にすることを区別する。
- **麺揚げ待ち時間**：各杯の購入から麺揚げまでの経過時間。集計単位は [CONTEXT.md](../../../CONTEXT.md) を正本とする。本 spec のオンライン計算で使うのは次の「上流観測起点の待ち時間」であり、実購入起点の計測とは区別する。
- **券売機申告時刻**：`payload.datetime`。券売機が申告する naive JST の時刻。購入に関する申告値であって、時計の正確さが保証された実購入時刻ではない。本オンライン計画の入力・永続属性にしない。
- **上流観測時刻**：`arrival_timestamp_ms`。上流ストリームがレコードを観測した時刻。これを起点として既存規則が保持する `OrderItem.arrivalTime` をオンラインの評価に使う。同一注文の後着で最早の `arrivalTime` を引き継ぐ規則も維持する。
- **DO 受理時刻**：StoreTimerDO がレコードを受け取った時刻。再送で変わり得る。上流観測時刻や券売機申告時刻の別名ではなく、待ち時間の起点にはしない。
- **上流観測起点の待ち時間**：各杯の `arrivalTime` から麺揚げまでの経過秒数。オンラインでは麺揚げ待ち時間の代理値として使う。本 spec のオンラインの「待ち時間」はこの値を指す。
- **麺揚げ負荷**：所定の時間窓で麺揚げするスロット本数。占有2の1杯は2本として数える。店舗設定の名前は `arms`、対話での呼称は `arm` である。
- **クラスタ**：CONTEXT.md の調理クラスタ。今回の計画モデルでは厳密に同一秒の麺揚げを1クラスタとして数える。購入注文・卓とは別のまとまりである。
- **前回提案**：既存の `shownPlan`。配信対象として永続確定した提案であり、各利用者が実際に見たことまで保証する記録ではない。
- **Timer の中断**：厨房の Cancel 操作。既存規則に従って Timer を除去し、参照先の品目は期限内なら未着手へ戻る。注文自体の取消・削除や、完了とは異なる。
- **実行可能解**：本 spec の物理・業務上の必須条件を満たす計画。ソフト制約の違反や、最適性を証明できていないことだけでは無効にならない。

## 評価項目

R4.3 が要求する評価量。各 ID を独立した検証の単位とし、具体式・単位・境界例を design に対応づける。これは旧 TS の卓同期・同一注文同時提供・Slot_Affinity を追加で適用する表ではなく、CP-SAT モードでそれらに置き換わる評価項目の集合である。

| ID | 評価項目 | 意図・検証の境界 |
| --- | --- | --- |
| E1 | `arm` 超過（**`arm + 2` 超過は評価量ではない**） | **2026-09-13 改訂：**「その瞬間に手伝いの手が何杯分要るか」を罰する。旧＝「クラスタごとの超過の和」。窓が重なるとき旧は同じ超過を複数のクラスタで数えうるが、新は手を 1 回だけ数える。**`arms + HELPER_ARMS` の超過はハード制約へ移したため評価量から外し、係数 `severeLiftOverflowCost` は不使用**（R4.4）。`arms` 側の境界を検証する |
| E2 | 麺揚げクラスタ数 | 麺揚げ時刻をまとめる。同一秒と異なる秒を区別する |
| E3 | クラスタ間隔の不足 | 盛り付け・提供に使う間隔を確保する。上げ窓の長さとは区別する |
| E4 | 同時麺揚げの**広がり** | **2026-09-13 改訂：** 同じ時刻に揚げる品目の散り方を、クラスタごとの x・y の最大−最小で測る。旧＝全組の距離の和。**組の和は同じ散らばりでも杯数の二乗で効く「量」であって、手の移動という「幅」ではない。** 変数は杯数 × クラスタ数で書ける |
| E5 | 複数スロット占有品目の内部距離 | 特に占有2のスロットが離れることへ強いペナルティを付ける |
| E6 | 周縁・中央の選好 | 全物理スロットへの距離合計で判定し、占有1は周縁、占有2以上は中央を優先する |
| E7 | 購入順の**隣接**逆転（オンラインは上流観測順で代理評価） | **2026-09-13 改訂：** 購入順で隣り合う 2 杯の上がりが逆転した数を罰する。旧＝全組の逆転数。**全組では 1 つの遅れが後続すべてと組を作って増幅されるが、厨房で見えるのは「先に買った人の後に出た」という個々の事実である。** 同じ起点・同時麺揚げを逆転と数えない。起点は R2.2 に従う |
| E8 | 同一注文の空間的な分断・距離 | 同じ注文の品目が遠くへ散らばることを罰する。**2026-09-13：定義は不変。距離の生成を同一注文の組に限る（E4 の改訂が前提——全組の距離生成を要求していたのは E8 ではなく E4 である）** |
| E9 | 前回提案からのスロット変更 | 同じ未着手品目の割当先が頻繁に変わることを罰する。スロットの列挙順だけの変更は数えない |

## Requirements

### Requirement 1: 対象環境に限定した計画器の切り替え

**User Story:** As a 評価者, I want 普段の dev 画面で CP-SAT の提案を使いたい, so that 実際の操作を通じて提案の良し悪しを判断できる。

#### Acceptance Criteria

1. WHEN 対象環境で CP-SAT を選択したとき、THE アプリ SHALL 新しく生成する通常の調理提案に CP-SAT WASM の結果を用いる。
2. THE アプリ SHALL 計画器を明示的に選択でき、選択が未指定の場合は既存 TS 計画器を使う。計画器の選択・方針設定をどの設定層に置くかは、R1.7 の変更契機を実現する方法を決める。切り替えの具体的な設定名・単位・設定層と、その変更を要求判定へ届ける経路をセットで design に定める。
3. WHILE CP-SAT を選択している間、THE アプリ SHALL NOT 旧 TS 計画器のスコアに勝つことを CP-SAT 計画の採用条件にする。
4. WHILE CP-SAT を選択している間、THE アプリ SHALL NOT CP-SAT の提案の尾部・欠落分・求解失敗を、旧 TS 計画器による新しい提案で暗黙に補完する。計画器を戻す操作と CP-SAT の結果待ちは、設定と観測記録で区別する。既存 UI だけでは計算中・求解失敗・有効な提案なしを見分けられないことを今回の制限として受け入れる（R6.6・R8.9）。
5. THE 切り替え SHALL UI と既存クライアントの通信形式を変更せず、提案を既存の表示・開始操作に接続する。
6. WHEN 初回接続・再接続・再起動後に未着手品目があり有効な CP-SAT 計画がないとき、THE アプリ SHALL 新しい注文の到着を必須とせず、計画を要求できる。要求判定は業務状態の no-op による早期 return と独立に行い、調理中の Timer がなく再評価前後の業務状態が一致する場合も判定へ到達する。要求管理は R5.8 の非永続方式とし、要求のためだけの Persist・Broadcast は追加しない。計画器の選択、モデル・WASM の版、方針設定（係数・クラスタ間隔）、計画範囲、探索予算の決定規則の識別情報とその入力に対する予算値を、局面とともに要求の同一性に含める。
7. WHEN 計画器または R1.6 の設定・版が変わり未着手品目があるとき、THE アプリ SHALL その変更を計画要求の契機とし、無関係な注文・Timer の状態変化を待たない。旧 TS の `requestedDigest` との一致だけを理由に抑制しない。稼働中の店舗への設定適用では、適用の成功後に要求判定へ進める経路を持ち、適用失敗・無視した旧版の設定を入力にした要求は送らない。デプロイによってのみ変わる設定・版は、当該店舗の次回起動・復帰時に判定し、休止中の全店舗をデプロイだけで即時起動することまでは要求しない。

### Requirement 2: 実際の局面を欠落・捏造なく計画へ渡す

**User Story:** As a 調理者, I want 現在の注文と釜の状態に合った提案が欲しい, so that 実行できない計画や注文の見落としを避けられる。

#### Acceptance Criteria

1. THE 計画要求 SHALL 一貫した局面を使い、品目の識別、`arrivalTime`（上流観測時刻由来）、麺種・硬さ、占有数、現在の Timer、店舗のスロット配置、レシピ、`arms`、`toleranceRatio`、上げ窓、前回提案、および R1.6 の計画方針・予算の識別情報を引き渡す。
2. THE オンライン計画器 SHALL 待ち時間と順序の起点に `arrivalTime` を使い、券売機申告時刻 `payload.datetime` と DO 受理時刻を用いない。THE 評価記録 SHALL 起点を「上流観測時刻」と記す。履歴再生で券売機申告時刻を使う場合は「券売機申告時刻・購入＝到着の仮説」と記し、オンラインの代理起点と区別する（`pos-order-ingress` AC 8.1・8.3・8.4・8.7）。
3. THE 計画器 SHALL 計画対象の選択規則と上限を持ち、新しく返す計画では対象に含めた品目を各1回だけ配置する。この全件充足は新着の応答の条件であり、採用後に開始・削除などで残りだけとなった保持中の計画には R5.9 の残存配置の規則を適用する。上限外の品目は待ち行列に残るが推奨を持たず、後続の計画機会に対象となり得るようにする。上限を64未満にする場合、現行の最大64件への推奨付与より先読み範囲が縮むことを評価手順に記載し、その画面上の差を検証する。待ち行列への掲載と推奨の有無を混同しない。
4. THE アプリ SHALL レシピから茹で時間を取得できない品目を計画対象から除外し、この除外を `arms + HELPER_ARMS` の容量判定とは分ける。IF 茹で時間を取得できない・未対応の占有数・不正な設定などで品目を計画できない場合、THEN THE アプリ SHALL 理由を識別できるようにし、その品目を完了扱いにしたり、注文の正本から削除したりしない。
5. THE 計画器 SHALL 計画対象と釜・麺揚げ負荷・クラスタ間隔が干渉する調理中の Timer、および利用可能な直近の麺揚げの事実を考慮する。履歴がない場合は、空だったと実証された局面と区別する。
6. THE CP-SAT 計画器 SHALL 卓未定のフォールバック値の一致を、同じ注文または同じ実際の卓であることの根拠にしない。同一注文の E8 は注文識別子で判定し、別注文どうしも E2・E3 による調理クラスタにまとめられるが、それを同卓という事実にはしない。POS 申告卓番号の既存の永続値は維持し、注文ごとの架空の実卓を生成しない。既存サンプルにはフォールバックの `1` と確定した実卓番号 `1` を識別する根拠がないため、その卓関係は不明のまま扱う。すべての `1` をフォールバックと断定したり、欠落・`0` と同一視して `null` へ書き換えたりしない。
7. THE 計画器 SHALL 再生評価でもオンライン実行でも、その時点で未知の将来注文を参照しない。

### Requirement 3: 物理的な実行可能性と既存操作の保全

**User Story:** As a 調理者, I want 提案を採用しても調理中の状態が勝手に変わらない, so that 計画を安心して使える。

#### Acceptance Criteria

1. THE 計画器 SHALL 各品目に設定範囲内の相異なる `slotSpan` 個のスロットを割り当て、同一スロットを重複する調理時間帯へ割り当てない。
2. THE 計画器 SHALL 開始・麺揚げ時刻をレシピと承認済みの茹で時間の規律に整合させる。実験時の許容幅を、アプリで実行できると確認せずに持ち込まない。
3. THE CP-SAT 計画の採用 SHALL 調理中の Timer のスロット・開始時刻・終了時刻を直接書き換えない。既存の手動調整と Boil_Sync は引き続きそれぞれの責務として残し、その実効終了時刻を計画の入力にする。
4. THE アプリ SHALL 麺揚げ済みで完了操作前の Timer が占有するスロットを「今すぐ開始できる空き」と扱わない。将来の解放予測と、今の開始可否を区別する。
5. THE アプリ SHALL 調理中・完了済み・注文から削除された品目、および既存規則で期限切れとなった品目を未着手として提案しない。Timer の中断で期限内の未着手へ戻った品目は、既存規則どおり再び計画対象にできる。
6. THE アプリ SHALL 計画受領や提案時刻の到来を契機に自動で調理を開始・完了せず、人による既存の操作を維持する。
7. THE 計画の接続 SHALL 既存 UI に調理クラスタと開始済みの所属を整合して伝え、単位・時刻・群・占有の変換不整合だけで、開始可能な提案が操作不能になることを防ぐ。卓未定値が一致するだけで同じ群・走行中の錨への所属を設定せず、同一の CP-SAT クラスタが申告卓番号に基づく一片の境界だけで分裂することも防ぐ。群と錨の対応は調理計画と開始の事実で検証し、実際の同卓を推測しない。
8. THE CP-SAT 計画の生成・採用・保持 SHALL NOT `online-cook-scheduling` AC 3.3(e) の「同じ卓の錨へ合流できる品目を、合流できない品目のために錨より後ろへ押し出さない」をハード制約として課す。旧 `keepsAnchor` によるこの条件の再適用も行わず、まとまりの選好は E2・E3 のクラスタ費用で扱う。これは調理中の物理占有や R3.3 の Timer 不変条件を解除するものではない。

### Requirement 4: 合意した報酬・ペナルティを評価可能にする

**User Story:** As a 評価者, I want 待ち時間と調理時の負担を同じ方針で評価したい, so that 係数や計画器の配線の違いを、提案の良し悪しと取り違えない。

#### Acceptance Criteria

1. THE 計画方針 SHALL 業務の事実・必須条件、報酬・ペナルティ設定、探索予算を分離する。ペナルティ設定から必須条件や計算予算を書き換えられないようにする。
2. THE 待ち時間の費用 SHALL 各杯の経過秒数を1秒あたり1秒相当で合計し、占有2でも1杯分とする。同じ会計の最後の麺揚げまでを1回だけ数える集計は行わない。オンラインの起点は R2.2 に従い、待ち時間を短縮する利益と各ペナルティの秒相当を比較する。
3. THE CP-SAT 計画方針 SHALL 「評価項目」節の E1〜E9 を持ち、各 ID の定義・単位・係数・設定の識別情報と検証ケースを対応づける。旧 `online-cook-scheduling` AC 3.4(a)(b)(c) の Table_Group 近接・同一オーダー同時提供・Slot_Affinity の費用を追加で適用しない。
4. THE 計画の生成・採用・保持 SHALL NOT E1〜E9 のソフト制約への違反だけを理由に解を無効にする。**ただし上げ窓の負荷は二層に分ける（2026-09-13 改訂）**——`arms` の超過はペナルティ（E1）、`arms + HELPER_ARMS`（＝`arms + 2`）の超過は**計画のハード制約**である。THE CP-SAT の計画も THE `admit` も**同じ規則で判定する**。既存の開始操作自体の規律を緩めることとは別である。
5. THE アプリ SHALL 初期評価に用いる係数群とクラスタ間隔の仮説を明示し、求解ごとに暗黙に変更しない。THE 設定の記録 SHALL 適用するモデルの識別情報と R9.9 のモデル照合結果への参照を持つ。
6. THE 実装 SHALL TypeScript で方針の値を表現・検証できるようにし、不正値・不明な項目を黙って別の値へ読み替えない。設定を変えるだけのために C++ の業務ロジックを編集する必要を生じさせない。
7. THE 評価結果 SHALL 目的関数の総値だけでなく、待ちと各ペナルティの評価量を分けて確認できるようにする。12分超過は待ち時間の評価指標として数え、今回新たな注文破棄条件やハード制約にしない。
8. THE 評価 SHALL 返却された計画から費用を独立に再計算し、ソルバーの報告目的値との差があれば区別して記録する。報告値だけを使って計画の質を判定しない。

### Requirement 5: 非同期結果の鮮度と採用の安全性

**User Story:** As a 調理者, I want 計算中にも注文や操作を進めたい, so that 遅れて返った提案で現在の状態が壊れない。

#### Acceptance Criteria

1. THE アプリ SHALL 注文受理・Timer 操作・通知の完了を CP-SAT の求解完了待ちにしない。計算中でも既存操作を処理できるようにする。
2. WHEN 求解中に品目・Timer・前回提案、または R1.6 の計画器・方針・予算などの入力が変わったとき、THE 採用判定 SHALL 現在の状態との整合性を再確認し、不整合な旧結果を採用しない。
3. THE 採用判定 SHALL 重複応答・応答順の逆転・別店舗の応答・計画器切り替え前の応答を安全に扱い、古い結果や別系統の結果で現在の有効な提案を巻き戻さない。
4. THE 新着応答の採用判定 SHALL ソルバーの成功ステータスだけに依存せず、返却内容の形式、生成へ渡した R2.3 の対象集合に対する一意性と全件充足、スロット占有、時刻、レシピとの整合を検証する。保持中の計画の再検証は R5.9 に従い、全件充足を再要求しない。
5. WHEN 応答の遅延により提案開始時刻が過去になったとき、THE アプリ SHALL 時刻をそのまま有効とみなさない。補正する場合は調理時間・占有・調理中との関係を再検証し、補正不能なら採用しない。THE 実装 SHALL この補正を**2 段の守り**として置く（2026-09-13 追記）。第一線は生成の側で、モデルが置ける最も早い開始時刻を「解いた時刻」ではなく「受領の見込み時刻」（`now + CPSAT_DELIVERY_LEAD_MS`）とすること。第二線は受領の側で、実際の遅れの分だけ未着手配置全体を同じ幅だけ後ろへずらし、物理条件を再検証すること（design 第 5.3 節 手順 4・上限 30 秒・CP-SAT モードのみ）。この猶予を置かない実装では、Queue → 求解 → 復路の遅れ（本番実測 p50 2,648 / max 6,619 ms）により先頭の配置が必ず過去開始となり、卓が 1 つの実データでは**計画全体が棄却される**（本番 322 件すべて）。THE 猶予の値 SHALL 実測した遅れの分布から決め、**残余の棄却率とともに記録する**——大きくすれば棄却は減るが先頭の推奨がその分だけ先へ動くため、到着間隔に対して十分小さく保つ。
6. WHEN 結果を棄却したとき、THE アプリ SHALL 棄却された計画を永続化・配信しない。WHEN 採用したとき、THE アプリ SHALL 既存どおり永続確定後にその提案を配信する。
7. THE アプリ SHALL 結果採用だけで無限の再要求を起こさず、再接続や R1.6 の入力変化からの回復を可能にする。有効な計画がない局面では、同じ入力で過去に要求を出した記録だけで再要求を禁止しない。保持中の計画に有効な残存配置があっても、R2.3 の選択規則と上限で絞った現在の計画対象に未配置の品目がある場合は、残存配置を保持したまま R6.7 の上限内で要求できる。上限外の待ち行列はこの未配置判定に含めず、対象全件を有効な計画が覆い局面・方針・版が同じなら、上限外の品目の存在や一時的な要求記録の消失だけを理由に再要求しない。THE 検証 SHALL 同一入力で失敗した後、再接続・再起動を契機に新しい要求を出せること、および計画器・係数・予算規則の変更だけで再要求できることを確認する。
8. THE CP-SAT モード SHALL 要求の送出済み・処理中・再試行の記録を再起動で失われる一時情報として管理し、DO の正本へ永続しない。一時記録は送出の重複排除・同時送出制限という輸送の関心事として shell 側に置き、DO 側の要求要否・対象選択・採用判定は engine の純粋な `decide` 内に保つ。shell の一時記録を engine の隠れた入力にせず、`TimerState` へ非永続フィールドを足す形も採らない（`online-cook-scheduling` AC 5.1〜5.2・11.3）。既存の `requestedDigest` は TS 互換のため保持するが、CP-SAT の送出・抑制の根拠として利用・更新しない。要求の同一性は旧入力の四つ組だけでなく R1.6 に従う。要求記録そのものの永続確定は送出条件にしないが、要求が依存する業務状態・保存対象の設定に変更があれば、その永続確定後にのみ送出する。業務上の確定結果が変わらない場合、要求の送出や一時記録の更新だけを理由に Persist・Broadcast を追加せず、再接続だけで注文・Timer・`shownPlan` の事実も更新しない。既存の接続時 snapshot の送信は別である。THE CP-SAT モードの Effect 列 SHALL 確定状態を変更する場合は Persist を先頭にちょうど1件持ち、RequestPlan があれば末尾に最大1件置く。確定済みの状態と適用済み設定からの要求だけなら `[RequestPlan]`、状態変更も要求もなければ空列を許容する。計画再評価の新しいイベントもこの分類に従い、要求単独列に Alarm 更新・Broadcast を混在させない。この例外は CP-SAT モードに限り、TS モードの既存の Effect 列契約は維持する。
9. THE CP-SAT モード SHALL 新着の応答について、生成へ渡した計画対象集合の全件を各1回覆うことと、R3 の実行可能性を検証し、欠落・重複・不正配置があればその応答を一括で棄却する。

> **改訂（ADR-0016・2026-09-15）：一括棄却でも接頭辞でもなく、通らない一片を飛ばして続ける。** THE CP-SAT モードの段 1 SHALL 検査に落ちた一片を捨て、**後続の一片を引き続き検査して採る**。判定は解放表・上げ表を**採った一片だけ**で進めるので、落とした一片の配置は表に載らず、採った集合はそれ自身で実行可能である。**TS モードの接頭辞は変えない**——あちらは尾部を自前解で埋めるので飛ばす必要がなく、段 2 が接頭辞を前提にしている。飛ばした一片があれば、その**最初の理由**を段（`admitStage`）として返す——「全部採れた」と「一部を飛ばして残りを採った」は別の事実である。
>
> 理由は実測にある。CP-SAT の一片は伝票ごとに独立して並び、**片の中に早い配置と遅い配置が混ざる**（1 伝票に麺が 2〜4 杯・2 杯以上が注文の 27%）。すると釜の時刻が片をまたいで交錯し、接頭辞では後続が道連れになる——**空き釜 4 本の局面で届いた一片の 24% が落ちた**。並べ替えでは 9% までしか減らない（片の中の混在が残るため）。飛ばす規則で 3〜4% になる。有効な応答の一括採用を許容し、旧 `Plan_Unit` ごとの独立採用を必須としない。一方、保持中の計画については、開始・完了・注文削除・期限切れなどで現在の未着手対象から外れた品目の配置を除き、残存配置と現在の Timer・レシピなどの整合を R3 に従って再検証し、有効な残りを保持する。現在の対象全件の充足は要求せず、1杯の開始や対象の繰り上がりで未配置品目が生じたことだけを理由に全提案を破棄しない。Timer の中断による対象復帰は R3.5 に従い、注文削除と混同しない。
10. THE CP-SAT モード SHALL 要求の送出から結果の到着までに輸送の配送時間が加わることを認め、この遅延を R5.1 の応答性とは別の項目として扱う。R5.1 が禁じるのは既存操作を求解完了待ちにすることであり、配送が速いことを保証する条項ではない。IF 輸送が複数件を束ねて待ち合わせる設定を持つ場合、THEN THE 設定 SHALL その待ち時間を最小にする——厨房が要するのは1件ずつ速く解くことであり、束ねる利得はこれに優先しない。THE 検証 SHALL 待ち合わせ設定を除いた素の配送遅延を実測して記録する。この値は達成目標ではなく、選んだ輸送方式の下限として扱う。THE 許容値 SHALL R8.7 に従い、測定条件とともに試験前に承認する——実測した下限を後から許容値として追認しない。下限が承認された許容に収まらない場合は design 第9節の輸送方式の選択へ戻す。

### Requirement 6: 探索量の上限と失敗時の継続

**User Story:** As a 運用者, I want 重い局面でも計算が有界で失敗理由がわかる, so that 計画器の問題をアプリ全体の停止にしない。

#### Acceptance Criteria

1. THE オンライン計画器 SHALL Cloudflare の実際の Workers 上で単一スレッドの CP-SAT WASM を実行し、Python・Node.js サーバ・ネイティブソルバーへ求解を委譲しない。
2. THE 求解 SHALL 探索量の上限を持ち、計算中に時計が進まない条件でも停止する。THE 予算の記録 SHALL 探索量の単位を持ち、実時間の秒数とは別の項目にする。
3. THE 探索予算 SHALL 求解前に得られる入力・モデルの複雑度から有界に決定する。特徴量・算出規則・最大値を記録し、求解結果を見て予算が無制限に増える形にしない。
4. THE 計画器 SHALL 計画対象数、入力サイズ、モデルサイズ、メモリ使用について検査可能な上限を設ける。上限超過は識別可能な失敗とし、処理できなかった品目を落として成功扱いにしない。 THE 計画器 SHALL 同一入力の求解が複数回走り得ることを前提とする（R6.7 の再送許容と輸送層の再配送による）。IF 同一入力の求解を省略する機構を置く場合、THEN THE 記憶 SHALL 有界であり、THE 正しさ SHALL 実行の冪等性に依存せず R5.3 の採用判定が担う——省略は費用の最適化として位置づける。記憶が失われて余分な求解が走ったことを失敗として記録しない。ただし THE 観測 SHALL その求解を R8.10 の求解開始回数に含める——数えないことと失敗にしないことは別であり、重複の実費は計数から見えなければならない。
5. WHEN 打ち切りまでに実行可能解が得られたとき、THE アプリ SHALL 最適性の証明を必須にせず、検証に合格した解を採用候補にできる。
6. IF 実行可能解なし・不正モデル・例外・資源上限・通信失敗が発生した場合、THEN THE アプリ SHALL 注文・Timer の事実を維持し、現時点でも有効な既存提案だけを保持する。有効な提案がなければ既存 UI 上は推奨のない表示とし、失敗を計画成功と記録しない。計算中・求解失敗・提案なしの区別は観測側で行い、今回そのための UI 表示を追加しない。
7. THE アプリ SHALL 連続した状態変化・同時要求でも要求の滞留やメモリ保持を無制限に増やさず、1回の失敗後に正常な次の要求を処理できる。一時的な要求管理には、1回の起動・復帰中に保持する件数、同時送出数、各回復契機での再試行回数の上限を定める。再試行は許可された次の離散的な契機で扱い、DO 内で再試行の待機・常駐タイマーを抱えない。再起動・hibernation 復帰で記録が失われたことによる同一入力の再送は許容し、R5.3 に従って応答を安全に扱う。再起動をまたぐ送出1回限りの保証や、無限回の再起動に対する累積送出回数の有限性は契約にしない。この上限は単位時間の要求頻度を保証せず、回復要求が必要な局面では起動・復帰や回復契機の頻度により求解回数が増え得るため、R8.10 で稼働中も観測する。 IF 輸送自身が独立に再配送する層を持つ場合、THEN その再配送はこの再試行規律の外にあり、THE アプリ SHALL 輸送層の再配送回数を知らず、依存もしない。同じ要求が何度届いても採否は R5.3 の採用判定が決める。輸送層の再配送を減らすことを目的として、DO 内へ待機・常駐タイマー・**consumer 側からの受領確認**を持ち込まない。THE 送出 SHALL 輸送への投入完了の await は行う——「送ったことを確かめてから event 処理を終える」既存の規律（R5.8 の Effect 列と design 第9節）はこれで満たされ、禁じているのは求解や配送の結末を DO が待つことである。
8. THE オンライン計画器 SHALL モデル生成・protobuf 直列化・解の復号を Workers 上の TypeScript／WASM のオンライン計画経路で行い、Python bridge・Node.js サーバ・オフラインツールに依存しない。オフライン参照との比較は R9.9 の検証だけに用いる。
9. THE デプロイ記録 SHALL 対象 Worker の CPU 上限と探索予算の決定規則を記し、探索量上限が CPU 時間上限内の完了を保証しないことを明示する。THE 観測 SHALL CP-SAT の協調的な打ち切りとプラットフォームの CPU 上限超過を別の結果として識別する。CP-SAT モードの有効化前に、実際の対象 CPU 上限で正常系の評価局面が完走することを R9.10 により確認する。
10. THE 計測 SHALL 指定した探索予算、ソルバーが報告する消費探索量、プラットフォームの観測 CPU 時間、通信往復時間を別の項目に記録する。強制終了などで消費探索量や CPU 時間が取得できなければ、欠測とその理由を記し、0や指定予算で埋めない。

### Requirement 7: データを巻き戻さない復旧とデプロイ

**User Story:** As a 運用者, I want 問題があれば元の計画器へ戻したい, so that 試用中の注文や調理操作を失わずに評価を中止できる。

#### Acceptance Criteria

1. BEFORE デプロイする前に、THE 作業手順 SHALL 対象ドメイン、実際に配信する Worker、関連する計画器、DO の接続先、同じ Worker を共有する経路を確認・記録する。確認した対象と異なる場合は変更前に再確認する。
2. THE デプロイ SHALL 既存の認証・秘密情報・店舗設定・DO の識別子とデータを維持し、公開範囲を広げない。計画器へ未認証の任意入力を送れる公開経路を追加しない。
3. THE デプロイ手順 SHALL 切り替え直前の稼働版と設定、および TS 計画器へ戻す具体的な手順を記録する。調査中に稼働版が変わった場合は、古い調査結果のまま上書きしない。
4. THE ロールバック SHALL 切り替え後に追加された注文・開始済み Timer・完了や取消の事実を維持し、過去の店舗 snapshot への復元を必要としない。
5. WHEN CP-SAT 使用後の永続値を復帰先の旧 TS 版で読み直したとき、THE アプリ SHALL 正常に起動し、必要なら提案だけを再生成できる。永続への追加は、旧 TS 版が無視でき、新版も欠落を扱える省略可能フィールドに限る。既存フィールドの意味変更・削除、旧版が拒否するスキーマ版への更新、DO の削除や再作成を行わない。THE 検証 SHALL 新版→旧版→新版での読み書きを含め、旧版の書き戻しで追加フィールドが失われても安全に回復できることを確認する。
6. THE 検証 SHALL CP-SAT への切り替えと TS への復帰を同じ保存状態の系列で確認する。復帰後に到着した旧 CP-SAT 応答も適用されないことを確認する。

復帰時の提案再生成は、既存 `livePrefix` の `isStale`・`cannotStart`・`keepsAnchor`・`withinLiftCap` による不適合な一片の除外と、TS 尾部の再計算を第一候補とする。新しい復旧用ソルバーや店舗 snapshot の巻き戻しを前提にしない。ただし、その構造だけで全入力の安全性が検証済みとはせず、R7.5〜R7.6 の旧版を使った回帰検証で確かめる。

旧 TS 版へ戻すと、申告卓番号の一致を共通の卓として扱う従来の解釈も戻る。本 spec のロールバックは店舗データを失わず従来動作へ戻す契約であり、旧 TS 側の卓未定値の解釈を是正する契約ではない。この制限は復帰手順に記載する。

### Requirement 8: 実行と体感を分けて観測する

**User Story:** As a 評価者, I want 実際にどの計画器が動き、どこで待ったかを知りたい, so that 解の質・求解の遅さ・画面反映の問題を分けて判断できる。

#### Acceptance Criteria

1. THE 観測 SHALL 使用計画器、コード・WASM・係数・予算の識別情報、および要求・求解結果・採用／棄却の対応を追跡できるようにする。solver の成功と画面へ採用されたことを別に数える。
2. THE 計測結果 SHALL 「求解要求→応答」「アプリでの要求→採用・配信」「操作→クライアント反映」を別の測定区間として持ち、各区間の測定方法・起点と終点・取得済み／未測定を記録する。
3. THE 実測結果 SHALL 初回実行と連続実行、軽い局面と重い局面を分け、件数・平均・p95・最大・失敗数を示す。初期化を含めたか、並列実行を含めたかも明記する。
4. THE 複雑度の記録 SHALL 未着手の計画対象数、調理中の杯数、占有2以上の杯数、スロット数、モデル変数・制約数、探索予算を含める。要因分析を報告する場合、変化させた要因、固定した条件、分析方法、相関分析／要因分離実験の区別を欄として持つ。
5. THE 資源計測 SHALL WASM 線形メモリと、取得できる場合の isolate 全体メモリ・CPU 使用量を区別する。取得できなかった指標は未取得として示す。
6. THE ログ・共有可能な結果 SHALL 認証値や生の注文内容を含めず、再現に必要な非公開入力は既存の非公開サンプルの扱いに従う。
7. THE 初回受け入れ SHALL 過去実験の応答時間を SLA とせず、安全性・継続性・実計画の使用を優先する。厳密な応答時間の合否閾値が必要なら、測定条件とともに別途承認する。
8. THE 観測 SHALL 提案した品目・`serveAt`・クラスタを、実際に開始された Timer と Boil_Sync 調整後の実効 `endTime` に対応づけ、開始の遅れ・手動調整も区別して記録する。同じ秒の判定規則で、計画上のクラスタと開始後の終了予定によるクラスタの分裂・合流・時刻差を確認できるようにする。終了予定である実効 `endTime` とは別の欄に、`Timer.boiledAt`（Alarm または Reconcile による自動発火時刻）を記録する。`boiledAt` は人の麺揚げ操作を観測した時刻でも Complete の完了操作時刻でもなく、遅延・復帰時のまとめ発火を含む自動遷移の記録として扱う。未発火や対応づけできない値はその状態を記録し、予定時刻や完了操作時刻で補完しない（[自動発火](../../../src/engine/fire.ts)、[完了操作](../../../src/engine/complete.ts)）。
9. THE 評価手順 SHALL 計画器の選択状態、要求中、求解失敗、結果棄却、有効な提案なしを観測記録で確認する方法を示す。UI だけではこれらを識別できないことと、推奨が消えても注文の正本が消えたとは限らないことを明記する。
10. THE 稼働中の計測 SHALL 店舗・計画器・同じ集計時間窓ごとに、単位時間あたりの計画要求数（engine での生成と shell からの実送出を区別）、求解開始回数、DO の起動・復帰回数を併記し、再送・輸送上の抑制・要求契機の内訳を確認できるようにする。観測記録から起動・復帰をまたいで集計し、要求抑制用の永続状態にはしない。取得できない値や起動・復帰の分類不能は欠測・不明として記録する。THE 評価手順 SHALL 稼働中の集計窓・頻度の想定範囲と超過時の対応を定め、想定を超えた場合は R6.7 の上限規則と R2.3 の対象上限を見直して再検証する。検証時だけのクラウド計算費用上限でこの観測を代用しない。

### Requirement 9: 再現可能な検証と官能評価への引き渡し

**User Story:** As a 開発者・評価者, I want 同じ条件で再検証できるコードと結果が欲しい, so that 体感上の問題を切り分け、継続採用や改善を判断できる。

#### Acceptance Criteria

1. THE 成果物 SHALL 準備・ビルド・テスト・対象環境へのデプロイ・復帰の手順と、入力・設定・コード・WASM・seed・探索予算を特定できる記録を含む。秘密情報そのものは含めない。
2. THE 固定問題の検証 SHALL 独立に期待値を確認できる小問題で、WASM とネイティブ参照の実行可能性と最適目的値を照合する。同点の異なる配置まで同一であることを必須にしない。ネイティブ参照はオフライン検証に限る。
3. THE 打ち切り検証 SHALL 難しい問題で、時計に依存しない探索停止、実行可能解あり／なしの扱い、失敗後の次要求の正常実行を確認する。探索量制限内の途中解がネイティブ参照と一致することは必須にしない。
4. THE 組み込み検証 SHALL 新着、同一注文の複数品目、占有2、調理中との競合、麺揚げ済み未完了、開始・完了・Timer の中断と再開・注文の削除・手動調整、設定変更、旧応答、重複応答、再接続、再起動、対象上限超過、無効入力、求解失敗、ロールバックを含める。
5. THE 実データ検証 SHALL 今回の主コーパスを `docs/data_samples/noodle_plan_histories` とし、その manifest・入力ハッシュ・設定・抽出方法・seed・局面数・繰り返し数・時刻の起点を保存する。履歴にない操作や時刻は仮説と記録する。`kenbaiki_orders` は旧 native pilot の資料として区別し、補助的な回帰に使う場合も今回の主コーパスの件数や成績に混ぜない。両コーパスの申告卓番号は `1` のみであり、実卓の同一性・相違は不明と記録する。0・欠落・異なる申告卓番号などの分岐や、既知の複数実卓を含むシナリオは R9.11 の合成 fixture の検証であり、実データで検証済みとは数えない。
6. THE 検証結果 SHALL Node.js やローカル workerd の成功だけを cloud Workers での成功とせず、承認済みの対象環境で既存アプリの要求から CP-SAT 求解・採用・表示までの経路を確認する。
7. THE 連続実行検証 SHALL 無効解・未処理要求・欠落品目・例外・メモリの推移を報告し、元履歴数・抽出した局面数・係数違いの再生数・求解回数を別の欄として持つ。
8. THE 引き渡し資料 SHALL 現在の計画器、使用中の係数、適用するモデルと局面の範囲、既知の制限、実測応答、復帰方法を示す。実行可能性、継続実行、厨房での官能評価を別々の判定欄とし、各欄に合格／不合格／未実施と根拠を記載する。
9. THE 検証 SHALL 同一局面・同一方針・同一の時刻離散化から、実験の Python bridge が生成するモデルと、オンラインの TS 経路が生成するモデルを照合する。protobuf の表現差を除いて実行可能な配置・時刻の集合と、それぞれに対する目的値が同じになることを、制約・目的関数の対応と小問題の照合で確認し、解の復号と独立採点も照合する。1つの返却解や最適目的値の一致だけをモデル全体の同値性の根拠にしない。THE 照合結果 SHALL 直列化の差と業務モデルの意図的な変更を分け、一致しない場合は差分・影響・新モデルでの再検証結果を記録する。未照合・不一致のモデルに使う係数は未検証の初期仮説と記し、過去探索での妥当性を引き継いだ設定として扱わない。
10. THE クラウド検証 SHALL 配備対象の CPU 上限・予算規則・計画対象上限で、初期化、モデル生成、直列化、求解、復号・検証を含むオンライン経路を実行し、正常系の完走と上限超過を分けて記録する。意図的な上限超過試験を正常系の成績から区別し、通常の評価局面で CPU 上限超過が生じた場合は、予算規則・対象範囲または CPU 上限を見直して再検証するまで、その組み合わせで CP-SAT モードを有効化しない。
11. THE 卓未定の検証 SHALL 同じ申告値を持つ別注文、同じ注文の複数品目、別注文の走行中 Timer、同一／異なる麺揚げクラスタを含め、R2.6・R3.7 の成立を確認する。卓関係が不明で他の入力が同じ条件では、意味を持たない代替値の一致・不一致だけで同卓の費用や錨が生じないこと、同一注文の費用は注文識別子に従うこと、元の申告卓番号を保存したまま既存画面で操作できることを検証する。0・欠落・1以外の申告卓番号や、同じ `1` の背後に同卓／別卓を仮定したケースは、既存履歴と分けた合成 fixture による単体検証とする。実卓の仮定は試験シナリオの前提に限り、オンラインで得られない卓属性を計画入力に追加したり、実際の卓が分からない履歴に正解の卓割当を捏造したりしない。
12. THE 回復要求の検証 SHALL 未着手品目あり・調理中 Timer なし・有効な計画なし・旧 `requestedDigest` 一致・業務状態の再評価結果不変の fixture で、接続・再接続・再起動から要求判定へ到達し、要求のためだけの Persist・Broadcast や `shownPlan` 更新を生じさせずに送出できることを確認する。一時記録が残る場合と失われる場合、失敗後の回復、再送と遅れて届く重複応答、および R6.7 の上限を検証する。同じ engine 入力に対する `decide` の出力は shell の一時記録によって変わらず、輸送上の抑制は shell の送出結果として別に観測されることも確認する。既存の Effect 順序 property はモードを区別し、TS の従来主張を残したまま、CP-SAT の状態変更列・要求単独列・空列を R5.8 に従って検証する。新しい計画再評価イベントと要求単独列を生成器が実際に踏み、状態変更時の Persist 先頭・唯一性や RequestPlan 末尾の検査を全体として緩めていないことも確認する。
13. THE 設定変更の検証 SHALL R1.2 で選んだ設定層と契機ごとに、計画器・係数・予算規則、および入力となる既存店舗設定の変更だけで要求判定へ到達することを確認する。保存対象の設定は正常な適用後にだけ新設定で要求し、適用失敗・旧版の投影の無視ではその設定による要求を出さないこと、デプロイ由来の変更は店舗の次回起動・復帰で検出すること、変更前の応答を R5.3 に従って扱うことを含める。
14. THE 計画保持の検証 SHALL 対象が欠落・重複する新着応答を棄却するケースと、全件を採用した後に1杯を開始・注文削除・期限切れにしたケースを分ける。後者では対象の繰り上がりによる未配置があっても、現在の条件に対して有効な残存配置が保持されることを確認し、調理中との競合などで本当に無効になった配置は保持しないことも確認する。
15. THE 要求頻度の検証 SHALL 同じ局面・方針・版で上限内の対象全件を有効な計画が覆うケースと、未配置や求解失敗で回復要求が必要なケースを分け、起動・復帰を繰り返して確認する。前者では上限外の待ち行列の存在や一時記録の消失だけで再要求せず、後者では R6.7 に従う再送と求解回数を R8.10 の観測で確認する。要求の生成・実送出・求解開始の件数を混同せず、起動・復帰をまたいだ集計で観測済み記録の数え落とし・二重計数がなく、欠測を0件扱いしないことを確認する。

## 既存 spec との関係

| --- | --- |
| `online-cook-scheduling` の自前解生成・TS による尾部補完（Requirement 4・AC 7.5） | R1.1・R1.4 により、新しい通常提案を CP-SAT に統一する。保持・再生成にも旧 TS の生成規則を混ぜない |

## 未決事項（design 前後で確定する）

以下は要件承認時に design へ渡した論点である。設計上の選択と初期値は承認済みの [design](./design.md) 第12.3節に整理した。以下の「未決」「暫定」はその時点の記録であり、設計で確定した選択を未決に戻さない。一方、F-1 の再確認、実測による成立確認、試験規模・閾値・費用枠、配備対象・復帰版の確認は tasks のゲートとして残す。

1. **計画範囲：2026-09-13 に確定した——全件（`PLAN_TARGET_LIMIT` 64）である。** 部分集合を渡さない。一片はその Table_Group の計画対象を全件置かなければ `isStale` で落ちるので、部分集合の計画は構造上採用されない（本番 165 店舗・334 件の受領すべてで採用 0 件だった実測がこれを示した）。全件を渡すので R2.3 の「上限外の表示差」は生じない。
   **到達状況：現状の実装が全数を解けるのは 24 件までで、閂は対の項（E4 距離・E7 逆転・E8 分断と `equal`）が杯数の 2 乗で膨らむことである**（design 第 7.4 節）。**天井を超える局面は部分計画を送らず、R6.4 の「対象超過」として理由つきの失敗を返し、engine は自分の計画を保つ。** 未対応品目（茹で時間を引けない・占有が範囲外）は正本に残し、対象入りするまで推奨を持たない。
2. **茹で時間と調理中との接続**：PoC は調理中の終了時刻も許容幅で動かすが、アプリでは既存 Boil_Sync が担当する。`toleranceRatio`・固定する時刻・丸め・群と錨への変換を整理する。卓未定値の一致を開始済みの所属の根拠にせず、旧錨への合流のハード制約も復活させない。モデルの差は R9.9、計画と実効終了時刻の差は R8.8 で扱う。
3. **初期係数と間隔**：利用する係数ファイルの版、強いペナルティの具体値、標準の人員・技能を仮定した間隔。追加探索は行わず、初期仮説を明示する。過去実験から引き継げる根拠の範囲は R9.9 の照合で決める。待ち時間の杯単位集計とオンラインの代理起点は、参考事実8〜9・R2.2・R4.2 で確定済みであり、未決に戻さない。
4. **動的予算・上限**：複雑度の特徴量と算式、モデル・入力・メモリ・同時要求の上限、対象 Worker の CPU 上限と正常系の評価範囲。探索量から CPU 完了時間は保証できないため、R6.9〜R6.10・R9.10 に沿って組み合わせを実測する。
5. **鮮度と回復**：R1.6 に列挙した計画器・モデル・係数・予算等を含む同一性の符号化、応答の追い越し、再起動、遅延補正、入力が静止したまま失敗したときの再要求条件。[settle](../../../src/engine/settle.ts) の `isSameConfirmedResult` は指紋判定より前で Effect を空にし、Timer のない Reconcile では指紋の変更だけでは要求へ到達できない。本要件案は **(b) 要求判定を no-op 抑止と独立にし、要求記録を永続しない** 方式を選ぶ（R1.6・R5.8）。要求記録の Persist のために AC 7.6 を緩める案 (a) は採らない。置き場所は shell の輸送管理とし、現在は全フィールドが永続対象の [TimerState](../../../src/engine/state.ts) に非永続フィールドを加えないことも本要件案で定める。未決なのは一時情報の寿命、再接続と再起動を区別した再試行の契機・抑制・上限、記録消失時の応答処理であり、要求記録の永続化や配置層ではない。R7.5 の省略可能フィールドを検討する場合も要求記録には用いず、採用済み計画の由来など別の用途と必要性を明示し、旧版の書き戻しで消失しても回復できるようにする。
6. **接続方式と命名・観測**：独立 Worker の分け方、設定名・単位・設定層、要求・応答の内部契約、観測方法。現行 [applyProjection](../../../src/shell/store-timer-do.ts) は投影の保存、`adoptProjectionConfig`、config 配信で終わり、`decide` を呼ばない。[Event](../../../src/engine/event.ts) にも設定変更の種別はない。計画器の選択・係数を env／Wrangler／同梱設定に置くならデプロイ後の次回起動・復帰と Reconcile 等を契機にできるが、R1.6 の no-op 抑止の解消が必要である。StoreProjection に置くなら、正常な適用後から計画の再評価へ進む明示的な経路（新しいイベントまたは同等の要求判定契機）が必要になる。どちらを選んでも、レシピ・配置・`arms`・`toleranceRatio` など既存の計画入力が投影経由で変わる経路への対応は省けない。I/O は shell が担い、純粋な判断へ適用済みの設定を渡す経路として設計する。UI に計算中・失敗表示を追加しないことは R1.4・R8.9 で確定し、観測側で区別する操作手順と対応づけを定める。新しい公開シンボルは `naming.md` に従い、実装前に確認する。
7. **モデルの同値性検証**：Python bridge と TS 経路の制約・目的関数・離散化・復号の比較方法と fixture、意図的なモデル変更の一覧。単一の最適解一致だけで同値とする方法は採らない。
8. **検証規模と稼働中の観測**：主コーパス `noodle_plan_histories` からの局面数・連続回数・並列数・検証時のクラウド計算費用の上限、表示反映の計測方法。それとは別に R8.10 の稼働中の集計窓・要求頻度の想定範囲・超過時の対応手順を定める。既存の実入力は申告卓番号 `1` のみで実卓の関係は不明とし、物理的な単一卓を仮定しない。他の申告値や既知の同卓／別卓シナリオは合成 fixture と分け、未測定の大規模局面や確定した実卓情報を使う別方針へ結果を外挿しない。
9. **群の投影**：既存サンプルに卓未定値と確定した実卓番号 `1` の識別根拠はなく、卓関係を不明として扱う点は参考事実14・R2.6 で確定する。POS 仕様の追加調査は本 spec の範囲外であり、未決なのはその識別ではなく R3.7 を満たす群・一片・錨の投影である。単純な `1 → null` の書き換えや注文 ID の卓番号への転用は前提にせず、既存永続値を保ったまま設計する。

これらを確定せず、作業中のコードの値を後から「ユーザー承認済みの要件」とみなさない。
