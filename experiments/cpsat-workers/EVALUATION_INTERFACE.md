# 評価方針のTSインターフェイス案

状態: **以下は検討経緯を残した設計案。SchedulePreferences / ScheduleEvaluation / replayOrderHistory の名称承認後、隔離実験を実装した。現行engine・DO・UI・永続形式は未変更。**

現在の実装範囲・正確な項目一覧・仮説と未実装部分は [tuning/README.md](tuning/README.md)、
実測結果は [SMAC_RESULTS.md](SMAC_RESULTS.md) を参照。以下に残る旧フィールド案・確認待ちの記述を、
現行の公開型や採用済み仕様として扱わない。

## 目的と進める順序

**既存engineとの互換性を目標にしない。** ユーザーは既存engineでまだ良い計画が得られていない。
まずCP-SATで業務条件と評価方針を詰め、望ましい計画が得られる状態を作る。
その後、同じ品質を満たすTSネイティブ実装へ戻すか、CP-SATを使い続けるか判断する。

既存の採点式・配置・admitは比較資料であって、品質の正解ではない。
CP-SATの探索基盤の検証と、こちらが記述する業務モデルの正しさは別に検証する。
探索上限で返ったFEASIBLEを、最適性の証明済みとは扱わない。

## ユーザーと確認済みの切り分け

1. **入力事実**: 既存経路から得る。固定とは自然言語が編集しないという意味。注文・Timerは実行ごとに変わる。
2. **必須条件**: 人が合意した成立条件をモデルに固定する。自然言語による評価方針変更では緩和しない。
3. **評価方針**: 自然言語から変換するのはここだけ。
4. **探索予算**: 通常のTSコードが探索前の複雑度から選ぶ。具体的な予算式・校正は別の検討。

必須条件が固定ということは、既存engineの全アルゴリズムを正しい業務要件として継承することではない。
条件を詰める過程での人によるモデル改訂と、運用時の自然言語による選好調整を区別する。

現行engine・DO・UI・永続形式・admin契約は今回変更しない。設計と検証は隔離実験で行う。
新しい評価方針を既存admitに通すことを合格条件にしない。デプロイも行わない。

## 推奨するインターフェイス

**既知の評価項目を持つ、JSON化できる完全な値オブジェクト。**
項目は業務上の意味で定め、Wasm・CP-SAT・既存engine固有のパラメータを露出しない。

型名候補: **SchedulePreferences**（調理計画を選ぶ際の選好）。
既存のPolicyは店舗設定を合成・配布する概念なので、その名は再利用しない。

次は名称・仕様確認のための宣言案であり、実装済みのexportではない。
型宣言と変更パスは初期案のまま。後述の追加検討（上げ負荷の2段階化・配置・調理クラスタ・購入順の逆転）を
反映するフィールド名はまだ確定しておらず、これを現時点の完成した項目一覧とは扱わない。

```ts
interface SchedulePreferences {
  readonly orderSync: {
    readonly weight: number;
    readonly toleranceSeconds: number;
  };
  readonly tableSync: {
    readonly weight: number;
    readonly toleranceSeconds: number;
  };
  readonly affinity: {
    readonly weight: number;
    readonly toleranceDistance: number;
  };
  readonly liftOverflow: {
    readonly costPerSlot: number;
  };
  readonly planChange: {
    readonly slotCost: number;
  };
}
```

planChangeは初期案の仮名を残しているが、今回の変更費用はスロット指定の変更だけに絞る。
先頭・投入順・開始時刻・クラスタ分割の変更費用は案から除いた。公開名はこの範囲に合わせて別途確認する。

- 待ち時間の係数を1に固定し、費用の尺度を定める案。その他の費用は待ち時間何秒分に相当するかで説明する。
- weightは連続的な悪化量に掛ける係数、costは1回／1本の出来事に対する費用。
- 0はその減点だけを無効化する。釜の排他などの必須条件は残る。arms + 2は追加検討でソフト制約へ変更する方針になった。
- 費用はすべて小さい方が良い。新しい報酬条件を既存の減点へ勝手に読み替えない。
- 既存の3・2・1やL・2Lを新設計の既定にしない。既定値は期待する局面での比較から決める。
- 任意の式、実行コード、対象フィルタ、優先順位DSLはv1で受け取らない。未対応の指示は明示する。

## 評価量の意味も先に固定する

型だけでは、同じ言葉で違う式を作れてしまう。以下は業務上の意味を確認するための案。
**特に卓同期と上げ負荷の数え方は未確定であり、モデル実装前に決める。**

| 項目 | 評価量の案 | 費用の単位 |
| --- | --- | --- |
| 待ち時間 | 各品目（1杯）の購入〜麺揚げ時間の和。同じ会計の品目も別々に加算 | 待ち秒そのもの |
| 購入順の逆転 | 購入時刻の前後関係に対して提供時刻の前後関係が逆になる場合に減点。逆転した品目ペア数で数える案 | 逆転1組あたり待ち秒相当の案 |
| 注文同期 | 同一注文の提供時刻の最大差から許容秒数を引いた正の部分、を注文ごとに加算 | 超過1秒あたりweight秒相当 |
| 卓同期 | 候補: 同卓の最遅提供から各品目の差の許容超過を加算 | 超過1秒あたりweight秒相当 |
| 釜の近さ | 同時に上げる麺のスロットの離れ。代表slotだけでなく使用する全slotを見る案。集約式は未確定 | 距離に応じた待ち秒相当 |
| 占有2の内部距離 | 同一品目が使う2slotの離れに強いペナルティ。基準距離と係数は未確定 | 距離に応じた待ち秒相当 |
| 占有数に応じた配置 | 周囲slotまでの距離合計で中央・周縁を判定。占有1は周縁、占有2以上は中央を優先 | 位置の好みに反する量に応じた待ち秒相当 |
| 上げ負荷 | arms超過とarms + 2超過の2段階のソフト制約。後者のペナルティを高くする。時間窓と集約式は未確定 | 各段階の超過1slotあたり待ち秒相当の案 |
| 調理クラスタ | 麺揚げ時刻をまとめる目的。クラスタ数に固定費を掛ける評価案 | 1回の麺揚げ作業あたり待ち秒相当の案 |
| スロット指定の変更 | 前回提示した割当からslot集合を変更した品目数を数える案 | 1品目あたりslotCost秒相当の案 |

調理中の仲間を同期の対象に含める範囲、距離評価の対象となる品目・まとまり、
比較基準となる提示済みスロット割当の定義は、入力事実と必須条件から決める。
自然言語が暗黙にその集合や意味を変更しない。

スロット変更費用を直近ほど強くすることや、遠い将来ほど割り引くことは今回の合意に含めない。
まず時間に依存しない費用を案とし、時間による重み付けが必要なら期待局面を基に別途検討する。

### 上げ間隔とスロット変更費用を独立させる

arms・liftIntervalSeconds・toleranceRatio・釜レイアウト・茹で時間は固定条件側。
上げの物理的な窓を短くして変更を起こりにくくする、といった間接調整はしない。
slotCostを変えても上げ間隔・合流条件・他の評価項目の係数は変わらない。
ここでの麺揚げ負荷の時間窓と、後工程の作業余裕を見込む目標クラスタ間隔は別の量である。
後者をliftIntervalSecondsだけで代表させず、後述の長めの基準と技能・人員による短縮を初期案とする。

### table=1について

本番もtable=1というユーザー確認があるため、複数卓未検証を今回の障害にしない。
ただし全注文が同卓として扱われる場合、tableSyncは全体を揃える方向に作用する。
それを望むかは別の品質判断であり、既存の非ゼロ重みを正解として引き継がない。
卓同期を使うか、weight=0から始めるかは期待局面で決める。

### 追加検討で確認した方向と未確定事項

**上げ負荷**: armsを超える麺揚げと、arms + 2を超える麺揚げを2段階で減点する。
後者も禁止ではなく、高いペナルティのソフト制約とすることをユーザーと確認した。
最初の超過2slotを60秒相当/slot、それ以上を600秒相当/slotとする数値は説明用の仮置きであり、未承認。
この例は高い段階に低い段階の単価を重ねない方式だが、最終的な費用式と時間窓の集約は別途確定する。

**配置**: 同時に上げる麺を近くに置く。占有2では、同一品目が使う2slotの離れに強いペナルティを付ける。
中央・周縁は対象slotから周囲slotまでの距離合計で判定し、合計の小さい側を中央、大きい側を周縁として、
占有1は周縁、占有2以上は中央を優先することをユーザーと確認した。
距離合計の対象を使用中も含めた店舗の計画対象全slotに固定すること、位置の評価に使用する全slotを含めること、
同一品目内の距離を別品目間の距離項と二重計上しないことは提案段階。
距離の集約・正規化・基準距離・係数は未確定である。

**調理クラスタ**: ユーザーが確認した目的は、投入時刻ではなく**麺揚げ時刻をまとめること**。
茹で時間が違う品目は投入時刻をずらして揃えられる。注文・卓のまとまりとは区別する。
既存の卓単位の群を、そのまま新モデルのクラスタとして固定しない。

評価案は「麺揚げ作業1回ごとの固定費」、すなわちクラスタ数に一定の費用を掛ける形。
待ち時間・上げ負荷・距離・配置の費用に加算し、作業回数の削減と、まとめるための不利益を比較する。
クラスタ数や1クラスタの本数をあらかじめ固定せず、全品目を一群にすることも要求しない。
1回30秒相当という説明例は未承認の仮置きであり、既定値ではない。

モデルの初期案では、各品目が一つのクラスタに属し、同じクラスタの品目が麺揚げ時刻を共有する。
ただし、厳密な同時刻で数えるか、短い時間幅まで同じ作業とするか、調理中の品目をどう含めるかは未確定。
所属ラベルだけをまとめても費用を節約できないよう、クラスタの所属と実際の麺揚げ時刻を結び付ける。
腕の超過はクラスタごとではなく店舗全体の実時刻の窓で評価する案とし、
ラベルの分割や微小な時刻ずらしだけで負荷を隠さない。窓の境界・重複の扱いは独立して検証する。

**購入順の逆転**: 購入時刻の順序に対して提供時刻の順序が逆になる場合に、ペナルティを付けることを
ユーザーと確認した。追い越しを禁止するハード制約ではなく、他の費用と比較するソフト制約とする。
購入が先のAと後のBについて、Aの提供がBより遅い場合を逆転と数える案。
同時提供は逆転に含めず、異なる購入時刻の品目も同じ調理クラスタにまとめられるようにする。
購入時刻が同じ場合も、この項では前後を決めず、注文IDや入力の列挙順で逆転を作らない案とする。

初期の費用案は「逆転した品目ペア数 × 逆転1組の費用」。各ペアは一度だけ数える。
例えば購入順A・B・Cに対し提供順B・C・Aなら、AとB、AとCの2組が逆転する。
これは逆転の件数を評価する案であり、何秒先行したかを掛ける費用とは別である。
品目単位か注文単位か（注文単位ならどの提供時刻を使うか）、同時刻の扱い・時刻粒度・係数は実装前に確定する。
品目ペアで数える場合、大きな注文ほど寄与が増えることも期待局面で確認する。
購入時刻の正本と既存arrivalTimeの対応は要確認とし、受信時刻を無条件に購入時刻とみなさない。

既存の到着順による計画対象選択は、購入順に提供する保証ではない。
待ち時間の単純和も、同じ対象集合なら到着時刻の和が定数となるため、購入順の逆転そのものには費用を付けない。
既存の前回計画からの投入順変更費用は、購入順の逆転の代用にはしない。
今回、投入順変更そのものの費用は採用せず、購入順に対する提供順の逆転だけを別項目で評価する。

**スロット指定の安定性**: ユーザーが守りたいのは、順序ではなく**スロット指定がころころ変わらないこと**。
広い意味での計画変更費用ではなく、同じ品目のスロット割当を変更する費用に絞る。
先頭の対象・投入順・開始時刻・クラスタ分割だけが変わっても、この項では減点しない。
それらの変更が待ち時間・上げ負荷・購入順などの別項目に与える影響は、その項目で評価する。

初期案は、前回現場へ提示した割当と新しい割当を同じ未着手品目について比較し、
slot集合を変更した品目数に一定の費用を掛ける形。探索途中で表示していない候補は比較基準にしない。
占有2の `[2, 3]` と `[3, 2]` は同じ集合なので変更なし、`[2, 3]` から `[2, 4]` は1品目の変更と数える案。
変更したslot本数ではなく品目ごとに1回とする数え方・係数は、実装前に確認する。
前回割当のない新規品目には変更費用を付けず、その配置のために既存品目を移した場合は既存品目側の変更を数える案。

開始済みの投入時刻・スロットを固定された事実として扱うことと、未着手のスロット変更を減点することは区別する。
取消・実際の開始・設備や占有状況の変化で成立しなくなった旧割当を、変更費用のために維持させない。
品目の欠落を変更費用で許すのではなく、計画対象を正しく扱う成立条件と分けて検証する。

検証案は、同じ局面の反復や小さな新着でスロット割当が頻繁に入れ替わらないこと、
変更費用を上回る改善があるときには移せること、旧割当が成立しなくなったときには修正できること。
前回割当を基準にするのは変更負担の測定のためであり、既存engineの計画を品質の正解にはしない。

確認した目的・選好と、以上の評価式の提案を区別する。用語はCONTEXT.mdに記録し、
公開フィールド名・係数・式への合意前に型のexport追加や現行実装の変更はしない。

### 調理中の品目との関係（設計提案）

注文全体を「調理中」と一括分類せず、同じ注文内でも投入済み・未投入が混在する品目単位で扱う。
基本案は、**投入済みの時刻とslotは固定し、麺揚げ予定は許容範囲内で調整できるようにした上で、
調理中と未投入を合わせて評価する**こと。調理中は単に空きslotを減らす障害物ではなく、
残りの品目が時刻・場所を合わせる相手でもある。これは提案段階で、既存Timerへの反映は行わない。

| 品目の状態 | 入力として固定するもの | 計画で決めるもの |
| --- | --- | --- |
| 未投入 | 注文・品目の同一性、購入時刻、麺種・茹で加減、占有数 | 現在以降の投入時刻、slot割当、許容範囲内の麺揚げ予定 |
| 投入済み・未発火 | 開始記録、実際に割り当てたslot、品目参照、規定の終了時刻・許容幅 | 許容範囲内での麺揚げ予定。投入・slotは動かさない |
| 発火済み・完了未確認 | 発火記録、slot割当、完了未確認という観測 | 通常の再同期に戻さず、残っている作業・解放見込みを実行モデルで扱う |
| 完了確認済み | 完了記録 | 新たな調理対象にしない。評価に必要な実績だけを残す |

麺揚げ予定の通常の許容範囲は「元の規定終了時刻 - 早上げ許容幅」から
「元の規定終了時刻 + 遅上げ許容幅」までとする案。過去への麺揚げは計画しない。
未投入でも投入済みでも同じ茹で時間・許容幅の規則を適用し、開始イベントを境に都合よく規則を変えない。
許容幅は入力事実・成立条件側で決め、自然言語の評価方針やGAが拡大しない。
前回の調整済み予定を新しい中心にすると再計画ごとに延長できてしまうため、元の規定値を基準にする。
人が茹で加減を変更した場合は、その事実を反映した新しい入力で計画し直す。

現行のsynchronizeも、元のendTimeを中心に、茹で時間 × toleranceRatioの幅でadjustmentを計算している。
調理中の終了予定がすでに完全固定されているわけではない（src/engine/sync.ts、src/engine/project.ts）。
ただし既存の同期アルゴリズムをそのままCP-SATの必須条件にはせず、
許容幅の採用と具体的な同期方法の採用を区別する。調理中の予定時刻変更に新たな安定性ペナルティは追加しない。

評価の対象は、各項目の意味に従い調理中と未投入の計画を合わせる。

- 上げ負荷: 店舗全体の同じ実時刻の窓で合算する。調理中2slotと新規1slotは合計3slotであり、
  arms = 2なら第一段階の超過。別の群ラベルにしても回避できず、arms + 2も引き続きソフト制約とする。
- 調理クラスタ: 調理中の品目と同じ時刻に合流すれば、新しい麺揚げ作業を増やさずに済む。
  ただし時刻を合わせるための待ち・上げ過負荷・距離と比較し、合流を強制しない。
- 同時麺揚げの距離: 調理中の固定slotも距離の評価に含める。近づけるために投入済みのslotを動かさない。
- 同じ注文の視覚的なまとまり: 調理中の仲間と提示中の未投入品目を同じ注文参照で結ぶ。
  卓ではなく注文であり、table = 1を理由に全品目を同一注文とみなさない。
- 購入順の逆転: 調理中と未投入の間の逆転も評価する。購入順ではない登録順を代用しない。
- 待ち時間: 調理中を含め、対象となる各杯の購入から麺揚げまでを一度ずつ評価する。
  実履歴の累積では各再計画の予測値を足し直さず、実行結果の一杯分を一度だけ数える。
- スロット変更: 変更できる未投入品目だけを前回の実提示と比較する。
  投入済みの固定は高額ペナルティではなく、探索で動かせない事実として扱う。

注文参照のないTimerも、slot占有・上げ負荷・調理クラスタ・同時麺揚げの距離には含める。
購入時刻や注文の同一性を捏造せず、注文依存の評価から外した件数は評価範囲として明示する。
調理中だけで既に生じている過負荷を隠さず、不可避の部分と新しい計画で増減する部分を区別して報告する。

通常の許容域がすでに過去になっている品目を、過去に上げたことにしたり許容域を後ろへ書き換えたりしない。
すでに発生した遅れは入力から持ち越し、未処理作業として扱う。許容域を満たす通常計画ができないことと、
残りの作業を計画できないことを同一視せず、実行上の超過を別途記録する。

特に、タイマー発火は実際の麺揚げ完了の観測ではない。現行itemStatusOfではboiledもCompleteまではcookingであり、
occupiedSlotsOfもTimerがあるslotを占有中として扱う一方、initialReleaseは予定終了を使った解放予測である。
実験でも現在の開始可否・将来の解放予測・実際の取り出しを分ける。
完了確認の遅れだけで茹ですぎを断定せず、実際の取り出し記録がない範囲は実行モデルの仮説として扱う。
slotが再利用できる時刻は麺揚げ予定と取り出し・空ける作業の仮定に従い、表示上の残り時間0だけで空きを確定しない。

検証例は、残り120秒の調理中Aに対し、90秒茹でのBを30秒後に近くの空きslotへ入れて合流できること。
180秒必要なBは、Aを許容範囲外まで延ばしたり過去にBを投入したりして合流させない。
合流先があってもarms超過の費用と比較し、別クラスタを選べることも確認する。
過去のPoCにあるbaseline anchorの開始時刻・slot固定は、新しい業務要件として継承しない。

TSインターフェイスには、品目との参照・開始記録・固定slot・規定終了・許容幅・完了に関する観測を
必要な入力として渡し、solver内部の変数や群ラベルを業務入力に要求しない方向とする。
調理中の麺揚げ予定を調整する案を採る場合、隔離実験の出力にもその予定が必要になる。
名称・入力の正本・出力契約を確定するまで公開型や現行Timer・UI・DO・永続形式は変更しない。

## 値と数値精度

- 完全な方針は全項目必須。未知キー・欠落・null・NaN・無限・負数は拒否する。黙って既定化やクランプをしない。
- 更新用の変更案では省略=変更なし。完全な方針の欠落とは区別する。
- weight・costは小数第2位までを提案。上限値は品質試験と整数域の安全性から別途決め、無制限の数値入力にはしない。
- 時間の許容幅は整数秒、距離の許容幅は固定されたレイアウトの距離単位とする案。距離をcmと誤解させない。
- 内部の時刻粒度・整数係数・点数のスケールはTS採点とCP-SATで共通に定める。
  ミリ秒を使う場合も、weightの小数との積が整数で表現できるスケールにする。
- UI向けの丸め値では比較しない。係数×変数域×項数の上限を検査し、安全な整数域を超えるモデルを拒否する。
- 現行の秒切り上げ・切り捨てに合わせることは合格条件ではない。採用する丸め規則と境界例を明示する。

## 自然言語の出力は変更案

自然言語が設定全体を書き直すのではなく、**許可された項目と適用後の絶対値**の列を提案する。

型名候補: **SchedulePreferenceChange**。

```ts
interface SchedulePreferenceChange {
  readonly field:
    | "orderSync.weight"
    | "orderSync.toleranceSeconds"
    | "tableSync.weight"
    | "tableSync.toleranceSeconds"
    | "affinity.weight"
    | "affinity.toleranceDistance"
    | "liftOverflow.costPerSlot"
    | "planChange.slotCost";
  readonly value: number;
}
```

これは任意の文字列パスでオブジェクトを更新する仕組みではなく、固定の許可リスト。
同じfieldの二重指定は拒否し、fieldごとに型・単位・値域を検査する。

| 自然言語 | 変更案または応答 |
| --- | --- |
| 同じ注文は30秒までずれても減点しない | orderSync.toleranceSeconds=30 |
| 釜の変更1回は、待ち時間を20秒増やすのと同じくらい嫌 | planChange.slotCost=20 |
| 釜の変更の費用を今の倍に | 現在20ならplanChange.slotCost=40 |
| 釜の変更は気にしない | planChange.slotCost=0。他の評価項目と必須条件は変えない |
| 同じ注文をもっと揃えて | 具体値と影響の案を提示し確認する。重要度を黙って捏造しない |
| 絶対に同時に出す | 必須条件の変更要求として対象外。weightを巨大にする代用はしない |
| 上げ間隔を短くする／倍まで計算する | 対象外。固定条件や探索予算は変更しない |

変更案には、アプリ側で原文・変更前の方針識別・差分・同一局面の試算を紐づける。
古い方針に対する相対指示を、更新後の別の方針へ適用しない。
変更案→検証→試算→承認→利用という順序。識別・承認の永続化は今回実装せず、既存DOの形式を増やさない。

## 採点結果の説明

型名候補: **ScheduleEvaluation**。
総点と、上表の評価項目ごとの点数を返す。項目には基礎量・適用した係数／費用・寄与点を対応づける。
総点は寄与点の和に一致し、「釜変更の費用を変えたら、なぜこの計画になったか」を比較できるようにする。
返却する正確な型と単位は、上記の評価量・時刻粒度への合意後に確定する。

同じ候補で1項目の設定だけを変えた場合、その項目の寄与点以外は変わらない。
計画自体を解き直した場合は他の評価量も変わり得るので、「設定の効果」と「計画変更の結果」を区別する。

異なる方針で採点した総点同士を、そのまま改善の判定に使わない。
入力事実・基準時刻・前回計画を固定し、比較対象の両計画を同じ方針で評価する。

## 係数探索と麺揚げ待ち時間

換算秒数を人が直接予想しにくいため、ユーザーから遺伝的な選良で係数を探す案が出た。
構成案は、外側で係数セットを探索し、内側のCP-SATがその係数で調理計画を作る形。
GAの採用・実装・実行はまだ行っていない。計画の探索手段をCP-SATからGAへ置き換える話とは区別する。

外側の採点について確認した起点と終点は、**購入からそのオーダーの麺揚げまで**。
投入から茹で上がるまでだけでも、麺揚げ後の配膳まででもない。小さいほど良い待ち時間の合計を主スコアとする案。
候補ごとに係数が違う内側の重み付き総点を、係数セットの良し悪しの直接比較には使わない。

集計単位は**各品目（1杯）**とユーザーに確認した。
同じ会計の2杯が購入5分後と7分後に上がる例は、5 + 7 = **12分（720秒）**。
会計内の最後の1杯が上がるまでの7分だけを数える方式は採らない。

```text
待ち時間合計 = Σ 各品目の（麺揚げ時刻 − 購入時刻）
```

待ち時間の集計単位は内側の初期案と同じ品目単位であり、購入注文単位の最遅時刻へ変更しない。
占有2以上でも一つの品目の待ち時間は一度だけ数え、使用slot数を掛ける上げ負荷の評価とは区別する。
購入時刻の正本、計画上の麺揚げ時刻と実行結果の麺揚げ時刻の使い分けも、採点実装前に固定する。

評価方法の提案は、同じ注文履歴・初期状態で各候補のCP計画に従って最後まで進行させること。
現在の実注文試験は現行engineが生成した局面への点ごとの試験であり、CP計画を次の状態へ戻していない。
したがって、その結果をそのまま係数選良の営業全体スコアにはしない。
採点対象の未完了品目を落として待ち時間を小さく見せないこと、探索用と未使用の検証用履歴を分けることも検証案とする。

待ち時間だけでは、待ち時間に影響しない購入順の公平さやスロット指定の安定性の係数は決められない。
移動・麺揚げ負荷・指示変更の作業遅延を実行モデルに含めるか、現場負荷の採用基準を外側に別途設けるかは未決定。
これらの遅延や採用基準を仮定して既に実装済みのように扱わず、係数を0へ寄せるだけの評価にならないかを確認する。

### 認知負荷を生む具体的な状況

ユーザーが認知負荷として評価したいのは、単なる情報量ではなく、次のような状況に伴う負担である。

| ユーザーが挙げた状況 | 観測・再現する量の案 |
| --- | --- |
| arms = 2で3本の麺揚げが来て、後回しの麺が茹ですぎになる後ろめたさ | 適正な麺揚げ時刻に対する実際の麺揚げの遅れ。発生品目数・超過秒数・最大超過を別々に記録 |
| 同じオーダーの麺が離れた釜に配置され、視覚的に散らかることによるpain | 同じ注文の使用slotの空間的な広がりを距離で測る案。時刻差ではなく、注文のまとまりの把握しにくさを評価したい |
| 麺揚げ間隔が短すぎて盛り付け・提供が後回しになる負担 | 麺揚げ後に滞留する品目数、盛り付け・提供までの待ち、後工程が追いつかない時間 |

これらの事象を評価対象とする意図は確認したが、表の具体的な測り方・集約式・重みは提案段階である。
腕の超過本数などの計画上の指標と、その結果として起こる茹ですぎや後工程の滞留を区別する。
事象の回数や秒数をそのまま人の感情の強さだとは扱わず、負担の代理指標とする。
ユーザーはヒアリング工程を設けるのが難しいため、まず仮説を適用する方針を選んだ。
現場の主観評価の収集を、この実験を進めるための前提条件にはしない。

同じオーダーの「遠く離れて」は、**釜の位置が離れることで視覚的に散らかり、ユーザーが感じるpain**を
指すとユーザーに確認した。単に釜間の移動時間を短縮するための評価にはしない。
同じ注文の麺を、配置を見ることでひとまとまりとして把握しやすいことが目的である。
距離はその代理指標であり、距離の数値だけで視覚的な把握のしやすさを完全に説明できるとは仮定しない。
代表的な配置を比較する主観評価は将来の検証手段として残すが、初期実験では必須にしない。
まず以下の仮説に対する整合性と、実注文履歴での挙動・感度を検証する。

既に検討している「同時に上げる麺の近さ」と「同じ注文の視覚的なまとまり」は、対象集合が異なり得る。
同時クラスタだけを近づければ同じ注文の見やすさも必ず満たす、とは扱わない。
対象とする注文・表示中の品目の範囲や距離の集約方法、両者の費用をどう対応させるかは未確定。
また、これは同じ注文の麺揚げ時刻の差を別途減点すると決めたことを意味しない。
スロット変更費用は前回提示からの割当変更、視覚的な散らかりはその配置自体の把握しにくさであり、別の観点である。
現行UIの表示方法を変更するのではなく、まず隔離実験でスロット配置を評価する目的として記録する。

特に茹ですぎの評価では、**計画上の麺揚げ時刻と、実際に麺揚げできる時刻を分ける**。
投入を遅らせて適正な茹で時間を守った場合は、購入からの待ちは増えるが茹ですぎとは数えない。
既に投入済みで適正な麺揚げ時刻を過ぎても釜に残る場合を、茹ですぎの評価対象とする案。
適正な茹で時間の許容範囲は別途確認し、名目の茹で時間からのすべての差を自動的に品質違反としない。
計画上のarms + 2超過をソフト制約にすることは、現場で任意本数を瞬時に処理できるという仮定ではない。
実際に処理できる本数、作業時間、手伝いの有無に従って、遅れが発生する場合を再現する必要がある。

採点用の実行モデルに、麺揚げ・湯切り・盛り付け・提供と担当者の作業競合を含めることを検討する。
どの作業を同じ担当者が行うか、所要時間、釜間の移動の影響は未計測・未確定であり、仮定と実測を分ける。
既存の局面生成は終了後の最初の1秒tickで対象TimerをCompleteにしており、これらの作業競合や滞留を再現していない。
現行engine・DO・UI・永続形式にこれらの状態を追加する承認ではなく、まず隔離した評価モデルの検討とする。

合意済みの主指標である「各杯の購入〜麺揚げ待ち時間の合計」の終点は変更しない。
麺揚げ後の盛り付け・提供の滞留は、それとは別の評価指標として明示する。
これらを単一スコアにまとめる係数や、複数指標のまま候補を比較して人が選ぶ方式は未決定。
原因となる事象を具体化できても、認知負荷の換算係数まで自動的に定まるわけではない。

### 後工程の処理能力とクラスタ間隔

**ユーザーから確認した要因**: 必要なクラスタ間隔は、盛り付け担当者の技能や、
客席まで運ぶ提供担当者の人数によっても変わる。店舗に対して常に同じ秒数とはしない。
ここから先の表現と計算は設計仮説であり、作業時間・能力を測定した結果ではない。

**最新の初期方針**: ユーザーから、基準間隔を長めに取り、技能・人員に応じて短くできる形が提案された。
初期案はこの粗い目標間隔を使う方向に絞り、以下の詳細な後工程シミュレーションは開始の必須条件にしない。
ヒアリングを待たず、余裕を見込んだ仮説値を使う。長めの値であっても、実際の処理能力を保証したとは扱わない。

具体式の提案は、目標間隔 = max(目標値の下限, 基準間隔 × 体制別の短縮係数)。
短縮係数は技能と人数を合わせた体制に対応させ、初期は少数の組み合わせを表で持つ。
基準の体制を1とし、能力が高い体制では0より大きく1以下の係数で短縮する案。
例えば同じ杯数なら基準120秒、体制に応じ100秒・80秒とする程度の粗さから試せるが、これらの数値は説明用。
人数が2倍なら自動的に半分にする式にはせず、提供だけ増員して盛り付けの能力が変わらない場合などは、
短縮を小さくするか据え置く仮説を表に明示する。兼務者を二つの役割で二重に増員扱いしない。
利用可能な後工程担当者がいない状況は、通常体制の係数へ黙って丸めず、別の運用条件として扱う。

基準間隔が想定するクラスタの杯数を明記する。杯数が変わる実験では、
直前に上げたクラスタの杯数に応じた非減少の基準間隔の表を用いる案とし、1杯と大量の麺揚げを無条件に同じ負荷にしない。
この杯数は品目数であり、arms負荷を計算する占有slot数とは区別する。
表の数値・体制の区分・目標値の下限は仮置き設定であり、公開シンボルや本番設定への反映はまだ行わない。

間隔の不足はmax(0, 目標間隔 - 次のクラスタまでの実際の予定時刻差)に係数を掛けるソフト費用とする提案。
目標値の下限は設定する目標に対する下限であり、実際のクラスタ間隔の新しいハード下限ではない。
クラスタは麺揚げ時刻と対応づけ、単なる群ラベルの分割・変更で採点を回避しない。
調理中の麺揚げも隣接クラスタ間隔の評価に含め、合流ならクラスタを増やさない一方、
同時に上げる量は別のarms超過・arms + 2超過の費用で評価する。

基準間隔・短縮係数は、その実験で所与とする現場能力の仮説として固定する。
不足をどれだけ嫌うかという評価係数とは区別し、GAが能力や人数の仮定を都合よく変えないようにする。
詳細な滞留モデルを使わない初期結果では、報告できるのは待ち時間と目標間隔の不足などであり、
実際の盛り付け待ち・運搬待ちを測定または再現したとは呼ばない。
詳細モデルに進む場合も、同じ後工程負担に対する間隔不足と滞留の費用を無自覚に二重加算しない。

#### 詳細モデルを必要とした場合の候補（初期実験の前提にはしない）

盛り付けの技能は、品目または品目カテゴリごとの作業秒数の違いとして表す案。
提供は、担当人数・一度に運べる杯数・一往復で担当者が占有される時間を仮定する。
クラスタの杯数・構成と、各工程に既に残っている仕事や担当者が空く見込みも入力に含める方向とする。
粗い初期モデルでは客席経路の最適化までは行わず、往復時間を仮置きする。
盛り付けと運搬を兼務する場合は同一人物の作業時間を二重に利用せず、別担当なら工程の並行を許す。

人員・作業時間の仮定は一回の計画で所与とする現場条件であり、好みを表すペナルティ係数ではない。
シフトや配置の変化で入力は更新できる。「固定条件」は自然言語の評価方針やGAが都合よく編集しないという意味で、
全営業時間・全店舗で同一という意味ではない。新たな運用設定や永続化を追加する承認ではない。

説明例として、盛り付け1人で20秒/杯、提供は1人につき2杯/往復60秒、4杯ずつのクラスタが続くと仮定する。
工程間で並行して作業でき、運搬の積載数を満たせるなら、盛り付けは1クラスタ当たり80秒の仕事量。
提供1人なら運搬側は120秒/クラスタ、提供2人なら平均60秒/クラスタの能力となる。
したがって滞留を増やさない平均的な到着間隔の目安は、それぞれmax(80, 120) = 120秒、max(80, 60) = 80秒。
これは定常的な処理能力からの目安であり、各クラスタに課す最小間隔や、滞留が発生しない保証ではない。
初期の残作業、盛り付け完了のずれ、運搬の出発・帰着、部分積載での出発によって実際の待ちは変わる。
客席へ届けた時刻と、往復を終えて次の運搬が可能になる時刻も区別する。

評価案は「間隔が固定のN秒より短い」だけの減点ではなく、仮説的な実行モデルで
麺揚げ→盛り付け→運搬の順序と担当者の競合を再現し、盛り付け待ち・運搬待ちの杯数と持続時間を採点すること。
最大滞留や待ち時間の最大値も併記する。これをソフト評価として扱い、待ち行列の発生を無条件に禁止しない。
麺揚げ担当者のarms超過・arms + 2超過とは独立した負担であり、クラスタ数の削減だけでも代用しない。
主指標の「各杯の購入〜麺揚げ待ち時間」の終点は変えず、後工程の評価を明示して追加する。
まず隔離した実行モデルで仮説を検証し、どこまでCP-SATの内側に組み込むかは別途決める。
ヒアリングを必須にせず、仮の作業時間と人員構成を変えた実験で感度を確認する。

### ヒアリングを前提にしない仮説評価

**確認した進め方**: 視覚的なpainは、ヒアリングによる校正を待たずに仮説モデルで評価する。
以下の具体的な式・数値は、そのための初期実験案であり、人の負担の実測値や確定した公開APIではない。
目的は仮説のもとでの良い計画を探すことであり、実際のpainの改善を証明したとは報告しない。

仮説は、同じ注文が多くの場所に分かれるほど、分かれた場所が遠いほど負担が増え、
その状態が長く続くほど累積負担が増える、というもの。
スロット変更は持続状態ではなく、前回実際に提示した割当からの変更イベントとして数える。

初期の測り方は次の案とする。

- 同時に提示される未完了品目を対象にする。対象範囲・更新時刻は現行の提示仕様を確認して実験側で固定し、
  候補ごとに表示対象を減らしたり、まだ提示していない探索候補を採点したりしない。
- 固定レイアウトの基準隣接距離をd0とする。同じ注文の各品目を頂点とし、
  品目間距離は両品目のslot集合間の最短距離とする。距離がd0以下の品目同士を接続する初期案。
  d0・斜め・釜の境界の扱いはレイアウトとともに固定し、探索対象にはしない。
- 注文ごとの連結成分数をKとし、分断数はmax(0, K - 1)。対象が0〜1品目なら0。
  一本の隣接列でA A B Bは合計0、A B A Bは合計2になる。
- 距離の追加量は、品目間の辺の費用をmax(0, 距離 / d0 - 1)とした最小全域木の費用。
  隣接でつながる部分は0で、離れたまとまりを最短につなぐための余分な距離を注文ごとに足す。
  同じ占有2の一品目は一頂点とし、その内部のslot距離は既に検討している別の強いペナルティで扱う。
- 分断数と距離の追加量は、提示状態が継続する秒数を掛けて履歴全体で積算し、60で割る。
  それぞれの単位は「分断・分」「基準隣接距離・分」。再計算回数やサンプリング回数では加算しない。
- 変更量は、実際の提示更新でslot集合が変わった品目数の累計。
  同じ集合の列挙順だけの違いや、新規品目の初回割当は変更に含めない。

外側の評価に加える配置負担の換算は、次の数値から試す提案とする。

| 仮説上の出来事・持続量 | 待ち時間合計への換算費用の初期案 |
| --- | --- |
| 余分な分断1つが1分続く | 10秒相当 |
| 上記の距離の追加量1が1分続く | 1秒相当 |
| 提示済み割当が1品目変わる | 10秒相当 |

配置負担は10 × 分断の積算量 + 1 × 距離の積算量 + 10 × 変更量。
購入〜麺揚げ待ち時間は従来どおり各品目の秒数を合計し、この費用を加える形を試す。
ここでの秒相当は交換比率であり、実作業がその秒数だけ遅れるという仮定ではない。
この部分式で茹ですぎ・上げ過負荷・後工程の滞留まで評価できるとは扱わず、他の検討済み項目も削除しない。
スロット変更費用を別名で二重に加算しない。

GAを用いる場合、遺伝子は内側のCP-SATが計画を作るための係数とし、
候補の良し悪しを判定する外側の仮説評価式・係数は一回の探索中に固定する。
外側の係数を候補自身が下げて有利になる採点にしない。
配置負担の係数を基準・0.5倍・2倍に振る別実験で感度を見る案。
各評価基準で同じ候補群を採点し直し、必要に応じて各基準で再探索する。
異なる基準で得た総点を直接比べず、共通の履歴で待ち時間・分断・距離・変更の内訳と候補の順位を比較する。

仮説の検証例は、他条件が同じなら分断をつなぐ配置の費用が増えないこと、
同じ分断を遠ざけても費用が下がらないこと、同じ表示状態を細かく分割して積算しても値が変わらないこと。
すべての対象品目を処理し、未完了品目や表示対象の除外で費用を隠さない。
隣接で長く連なる注文は分断費用も距離の追加費用も0になり得るため、この式が把握するのは主に分断であり、
細長さ・色・文字の見づらさなど視覚的なpainのすべてではないことを限界として残す。
実履歴の反復と未使用履歴で仮説のもとでの安定性を確認するが、それを主観評価の代替的な実証とは呼ばない。
既存の独立局面試験は提示履歴を伴うCP計画の連続進行ではないため、この積算評価はまだ未実装・未実測である。

## CP-SATを先に完成させる

- TSで事実・必須条件・評価方針からCPモデルを作る。protobufや変数番号は評価方針に露出しない。
- TSの独立した採点でCPの目的値・内訳を照合する。同じJSONを読むだけでは式の一致を保証できない。
- 独立した必須条件検査を行う。solverのFEASIBLEだけで業務的な正しさを判断しない。
- baselineをヒントに使うことと、baseline配置を必須条件として固定することを区別する。
  過去の100局面試験は91配置を固定し、30局面は全配置固定だった。この結果を新モデルの品質証明に流用しない。
- 「短い注文を長い注文待ちで止めない」「必要な揃えを守る」「少しの改善で釜を頻繁に変えない」等の
  期待局面を用意し、好ましい計画と好ましくない計画の比較で方針を詰める。これらも具体的な条件・期待を人が確認する。
- 事前複雑度に応じた探索予算は独立のTS処理として選ぶ。予測は厳密な実行時間保証ではなく、指定予算に最大値を持つ。
- その後、同じ事実・必須条件・評価方針・品質基準に対してTSネイティブを比較する。
  同点の別配置を失敗にせず、品質・成立性・安定性・資源消費を比較する。

## 現行アプリとの関係

既存adminは評価重みを設定対象にしていない。既存admitも現行の評価式を使う。
新方針で良い計画を既存admitが棄却しても、それを新方針の失敗とはしない。
既存との比較記録は残せるが、採用判定を新方針の品質ゲートに使わない。

将来本番に統合するときは、生成と採否が同じ評価方針に基づく必要がある。
その統合作業は元の「engine・DO・UI・永続形式は変更しない」範囲から分けて承認する。
今回インターフェイスを設計しただけで本番へ設定が反映されるとは扱わない。

## 合意後の検証条件

1. 完全値と変更案の検証。固定条件・探索予算の混入、未知項目、重複、値域・精度違反を拒否。
2. 期待局面での望ましい／望ましくない計画の順位が、合意した意味と一致。
3. 固定した計画で1項目の変更が他の項目の寄与点や必須条件を変えない。
4. 重みや費用を0にしても必須条件違反を受け入れない。
5. CPモデルの目的値・内訳と独立したTS評価が一致。丸め・窓端・同時刻の例も含む。
6. 実注文と未使用の局面で有効解率・改善内容・反復安定性を検証し、CP計画に従う連続進行も確認。
7. 十分な解が得られない場合、モデルの誤り・評価方針・予算不足・探索基盤の失敗を区別。
8. 将来のTSネイティブはCP-SATで固めた同じ品質基準と比較。既存engineの出力を正解にしない。
