# 相談：予算で打ち切る CP-SAT で「費用を上げても効かない」が 4 回続いた。構造へ移すべきか、探索が足りないのか

## 0. 一行で

**目的関数の重みを 10〜100 倍に振っても結果がほとんど動かない、という現象に 4 回連続で当たった。
手書き貪欲法（以下 TS）は同じ性質を「構造」で達成している。CP-SAT 側も費用をやめて構造にすべきか、
それとも探索量が足りないだけなのか、切り分け方と打ち手について意見がほしい。**

---

## 1. システムと実行環境

ラーメン店の**麺茹でタイマー**。POS から注文が届き、「どの杯を・いつ・どの釜で茹で始めるか」を
画面に推奨として出す。調理者はそれを見て開始ボタンを押す。計画器を手書き貪欲法（TS）から
**CP-SAT（WASM）**へ置き換える移行の途中で、両方が同じ局面を解ける状態にある。

### 動かせない制約

| 項目 | 値 |
|---|---|
| 実行基盤 | Cloudflare Workers（Queue consumer）・**単一スレッド**・WASM |
| 時計 | **凍結**（`Date.now()` が進まない）。壁時計での打ち切り不可 |
| 打ち切り | CP-SAT の**決定的時間**（deterministic time）予算。`(0, 1]` |
| 現在の予算式 | `min(1, 0.004 + 杯数 × 0.007 + min(走行中, 4) × 0.082)` → 24 杯・走行中 0 で **0.172** |
| CPU 上限 | 20,000 ms（**実測 p50 1,731 ms / max 4,571 ms**——余地はある） |
| 解の状態 | **ほぼ常に `FEASIBLE`**（最適性の証明には至らない） |
| 応答の遅れ | 要求 → 求解 → 復路で p50 2.6 秒・max 6.6 秒 |
| モデル規模 | 24 杯で変数 約 1,000・求解 約 420 ms |

## 2. 起きていること——「費用を上げても効かない」が 4 回

### (a) 同じ伝票の杯を揃える

同じお客の 2〜4 杯を同時に上げたいが、CP-SAT はバラバラに置く。

| 広がり（同じ伝票の最遅 − 最早の合計・秒） | |
|---|---:|
| TS | **45** |
| CP-SAT | 5,042 |

広がりに費用を足して重みを振った（12 局面）。

| 重み | 10 | 50 | 200 | 1000 |
|---|---:|---:|---:|---:|
| 広がり | 3,892 | **3,304** | 3,664 | 3,959 |

**単調に減らない。** 予算を 0.172 → 0.5 → 1.0 と 6 倍にしても目的値が 3 桁目まで一致（162,079 /
162,078 / 162,082）。**構造（同一伝票を同一クラスタへ縛る等式）を入れても 3,777 までしか行かない。**
最終的に効いたのは**貪欲 hint を伝票単位で組み直す**ことだった（5,042 → 1,650）。

### (b) 前回と同じ釜を使う（ちらつき）

連続する 2 回の計画で釜が入れ替わる。本番では対応した杯の **93%** が別の釜へ移っていた。
モデルには `slotChangeCost`（1 杯 100 ＝「10 秒待つ」相当）が既に在ったが効いていない。
**hint に「前回と同じ釜」を入れたら 93% → 0%。** 費用は 1 行も変えていない。

### (c) 上の (b) が釜の混雑時に崩れる

求解中に釜が埋まる局面では、重みを 40 倍にしても 11% 動く。120 倍で 0% になったが、
**400 倍にすると今度は注文順の逆転が 5 割増える**（53 → 78）。

### (d) 注文順の逆転（いま相談したいもの）

「だいぶ待たせているオーダーを差し置いて、後のオーダーを選んでしまう」という現場の指摘。

| 逆転（購入順で隣接する 2 杯の上げ順が逆・件） | |
|---|---:|
| TS | **45** |
| CP-SAT | 138 |
| **貪欲 hint 単体**（hint を固定して解いた値） | **94** |

逆転の重みを振った（24 局面）。

| 重み | 20（既定） | 60 | 120 | 240 |
|---|---:|---:|---:|---:|
| 逆転 | 138 | 130 | **165** | 105 |

**やはり単調でない。** hint に「先に注文された杯より先に上げない」下限を課すと 138 → 105 まで
減るが、**TS の 45 には届かず**、かつ待ちが +5.8%、(c) で直したばかりの釜の安定が 0% → 6% に戻る。

## 3. TS が「構造」で達成している形

TS は**卓（伝票）ごと・到着順**に処理し、**解放表（各釜がいつ空くか）を 1 群ずつ進めながら**置く。

```
群 1 を置く → 解放表を更新（使った釜が塞がる）
群 2 を置く → 更新後の表から選ぶ   ← 群 1 が取った釜はもう空いていない
```

ゆえに**後の群が前の群を追い越せない**（逆転が構造的に起きにくい）。同じ群の杯は
**pack として一括で置く**（必要な釜数が揃う最早の時刻を探し、全員を同じ上げ時刻に置く）ので、
**同時提供も構造から出る**。

**ただし総和では CP-SAT が勝っている。**

| | Σ 杯数 × 待ち時間 | 逆転 | 広がり |
|---|---:|---:|---:|
| TS | 232,797 | **45** | **45** |
| CP-SAT | **229,000 前後** | 138 | 1,650 |

CP-SAT は「早く出せるものから出す」ので待ちの総和が小さく、その裏返しとして順序と同時性を失う。

## 4. モデルの形

### 変数・制約（1 杯 = 1 ジョブ、24 杯で変数 約 1,000）

```
start_i, end_i, size_i    整数秒。end = start + size、size ∈ [茹で時間 ± 許容(0〜10%)]
slot_i[a]                 杯 i が占める a 番目の釜（slotSpan は 1 か 2）
presence_i[a][s]          釜 s に居るか（bool）。Σ_s presence = 1、Σ_s s·presence = slot
区間                      各釜ごとに NoOverlap（optional interval）
上げ窓                    cumulative。窓 45 秒内で同時に上げる杯数の上限
                            arms + 2 = 4 がハード、arms = 2 超過分はソフト
クラスタ                  x[i][k]（杯 i がクラスタ k）。x ⇒ end_i = T_k、T_k は狭義単調増加
                          K は貪欲解の相異なる上げ時刻数 + 4
使用不可の釜              走行中・茹で上がり待ちの釜は presence = 0 に固定
```

### 目的関数（すべて線形整数・重み付き和）

| 項 | 重み | 内容 |
|---|---:|---|
| 待ち | 10 | Σ_i end_i（1 秒 = 10） |
| 上げ超過 | 60 / 600 | arms 超過 / さらに超過 |
| クラスタ数 | 30 | 相異なる上げ時刻の個数 |
| 上げ間隔の不足 | 2 | クラスタ間隔が目標に届かない分 |
| 同時上げの空間的広がり | 1 | 同クラスタの杯の座標の広がり |
| 2 釜の距離 | 60 | 1 杯が 2 釜に跨るときの釜間距離 |
| 周辺 / 中央 | 1 / 1 | 釜の位置の好み |
| **購入順の逆転** | **20** | 購入順で隣接する 2 杯の上げ順が逆（1 件 = 200） |
| 同一伝票のまとまり | 30 | 同じ伝票の杯の間の木の弧が「遠い」 |
| **前回と違う釜** | **10** | 前回の提案と釜が変わった杯（1 杯 = 100）。**Head 近傍は 120 倍** |

### hint

貪欲解を hint として渡す。**解が常に `FEASIBLE` なので、ソルバーは hint の近傍を返す**——
という経験則が (a)(b) で効いた。

## 5. 聞きたいこと

1. **「重みを 10〜100 倍に振っても単調に動かない」をどう診断するか。**
   モデルの最適解が本当にそこにあるのか、探索が出発点から出られていないのか、
   この観測だけで言えることと言えないことを整理したい。**切り分ける実験**として何を回すべきか。

2. **予算を上げるべきか。** CPU には余地がある（実測 max 4,571 ms / 上限 20,000 ms）。
   (a) では 6 倍にしても目的値が動かなかったが、それは**走行中 0 の局面**での話で、
   混雑局面では未測定である。**予算不足かどうかを安く確かめる方法**はあるか。

3. **順序を制約にすべきか。** 現場の要件は「多少遅くなっても順番どおり」で、
   これは費用ではなく**守るべき制約**に見える。ただし
   - 大盛（2 釜）が空きを待つ間、後続を全部止めると全体が遅れる
   - TS も厳密には止めておらず、`firstFit` が「入る場所から詰める」ので多少は前後する

   **「追い越しを許すが、待ち時間に比例して許しにくくする」**ような、実行不能を招かない構造の
   書き方はあるか。あるいは**辞書式**（まず逆転を最小化し、その値を制約にして待ちを最小化）が
   この予算で現実的か。

4. **一般論として。** この規模（変数 1,000・単一スレッド・決定的時間 0.172）で
   **重み付き和の多目的**を扱うのは筋が悪いのではないか。
   「構造で決めるもの」と「費用で誘導するもの」の線引きの原則があれば聞きたい。
   現在は 10 項の重み付き和で、重みはすべて実験で決めた値である。

5. **単一スレッドでの探索の底上げ。** `num_workers = 1` では LNS worker が回らないと理解している。
   `interleave_search` などのパラメータで単一スレッドでも近傍探索を効かせられるか。
   有効なら、上の 4 つの問題すべてに効く可能性がある。

## 6. 補足：これまでに効いた手・効かなかった手

**効いた**（いずれも hint = 出発点を変えるもの）
- 前回と同じ釜を hint に入れる（釜の入れ替わり 93% → 0%）
- 伝票単位で貪欲を組み直す（広がり 5,042 → 1,650）
- 使えない釜（茹で上がり待ち）を貪欲が選ばないようにする（求解失敗 39% → 2%）

**効かなかった**（いずれも費用・制約・予算）
- 広がりの重み 10 → 1000（単調でない）
- 逆転の重み 20 → 240（単調でない）
- 予算 0.172 → 1.0（目的値が 3 桁目まで一致）
- 同一伝票 ⇒ 同一クラスタの等式（5,042 → 3,777 で頭打ち）
