# 前回配信対象として確定した提案（Shown_Plan）を履歴の事実として状態に持ち、そこからの変更費用（Change_Cost）を目的関数に足す

確定計画の尾部は毎回ゼロから置き直され、釜の同点は index 昇順で断つ。走行中が 1 本増えるだけで解放表と上げ表が変わり、同じ待ち行列に対して残りの品目の釜・投入の順・まとまりが動く。現場が既に段取りを組んだ部分——**次に投入する品目とその釜**、**一緒に扱うまとまりと投入の順**——が動くと、覚え直す負担がそのまま知的負担になる。守りたいのは計画全体の固定ではなく、手を伸ばそうとしている対象である。ゆえに変更を禁じず、**費用にする**。新しい費用 = Business_Cost（既存の目的関数）+ Change_Cost。釜の占有・slotSpan・上げ窓の上限・合流の契約のハード制約は変えず、変更費用は feasible な候補の間の選び方にだけ効く。

**前回の提案を `TimerState.shownPlan` に持つ（永続 v12）。これは「導出値を状態に昇格させない」規律の例外ではない。** その規律は現在の状態から毎回導ける値についてのもので、前回 `Persist` に載せた提案は、時刻が進み走行中が変われば現在の状態からはもう導けない——過去の出力であり、いま計算し直した確定計画のキャッシュではない。定義は「配信対象として永続確定した提案」であって「現場に見せた」ではない（Persist の後に Broadcast が続くが、送信失敗や接続端末ゼロでも永続は成立し、見せたことは保証できない）。確定結果の同じ `Persist` に、選んだ計画の推奨（`recommend` の出力）から組んだ Shown_Plan を載せるので、確定した推奨と Shown_Plan は常に一致する。no-op・棄却・hydration では更新せず、`isSameConfirmedResult` は `shownPlan` を比べない（比べれば時刻経過だけで空振りの Persist が出る）。持つのは品目ごとの `slotIds` / `startAt` / `serveAt` / `anchor` と、同じ群に在った相手の鍵 `mates` である。群の識別子は snapshot 内で閉じる（ADR-0008）ので文字列は持たず、まとまりは鍵の組で持つ。**Head の旗は持たない。** Head は時刻と走行中に依存するので、比較の時点の now と**遷移後（再同期後）の Timer 集合**で、旧 Shown_Plan からも新しい計画からも同じ関数（`domain/lift-group.ts` の `headsOf`——表示と同じ導出）で導く。確定時点の旗を保存すると、時間経過で濃くなった品目を守れず、anchor の失効で後続群が隠れただけの同じ計画に費用が付く。遷移前の集合を使うと、遷移で始まった品目の釜を旧 Shown_Plan の他の品目がまだ使えると見て偽の先頭変更が生まれる。履歴として保持する対象（配置）と、現在の保護対象（そこから今導く Head）は分ける。

**費用は 4 種で、重みは秒相当を `liftIntervalSeconds`（L）から導き、新しい設定は足さない。** 対応する品目（`externalOrderId` + `itemIndex` が旧 Shown_Plan と新しい計画の両方に在り、待ち行列にも在るもの）の間でだけ数える。(a) 先頭の変更——旧 Shown_Plan の Head に在った品目が新しい計画の Head に無い：2L。(b) 釜の変更：L。(c) まとまりの変更——前回同じ群だった組が別の群に割れた、または対応する組の `startAt` の順が逆転した：組ごとに L（逆転は群を跨いだ全対応の組で数える）。(d) 時刻の移動——`startAt` が h_i（合流の窓）を超えて動いた分について、跨いだ窓の数 × L / (k + 1) の床（k = 前回の `startAt` が今から何個目の窓か。遠い将来ほど軽く、整数ゆえ単調非増加）。開始済み・キャンセル済みで消えた品目と新規の品目は数えない。**未着手の品目を推奨から消して費用を逃れる経路は、費用ではなくハード制約で閉じる**——外部計画の一片は卓の計画対象と品目集合が一致しなければ `isStale` で棄却され、卓ごと省けば合成の尾部が自前解で必ず置く。欠落に費用を定めれば「消失 2L 対 分割 3L」のような逃げ道の算術が生まれる。店舗全体の項なので Lift_Overflow と同じく `total` にだけ足し、卓ごとの部分和 `bySlice` は変えない。

**採点に足すだけでは足りない。** 自前解が前回を候補に持たなければ、同点を index で断つ限り前回の配置は出てこない。釜の選択は対応する品目の前回の釜が候補の時刻までに空けばそれを第一候補にし、batch の並びの同値は前回の `startAt` 順で断ち、列の分割は「前回の配置の再現 → 前回のまとまりを保つ → 前回の先頭を今の窓に残す → pack → split」の候補を局所費用（業務費用 + 変更費用の差分。先頭の判定は置いていない品目を前回の配置で補った計画から導く）で比べる。ただし列ごとの局所比較は後続の一片への影響（上げ窓の押し出しとその変更費用）を見ないので、局所では勝つが全体では劣る候補へ動き得る（実測：卓の一片は 370 秒改善するが後続の単独品が 83 秒遅れ、変更費用を足すと前回より 218 秒悪化）。ゆえに**前回に忠実な計画（候補を比べず再現 → pack）と候補を比べた計画の 2 本を組み、総費用（Business_Cost + Change_Cost）が真に下がるときだけ後者を採る**。外部ソルバへは `RequestPlan.shownPlan` で運び、同じ費用で最適化できるようにする。指紋には畳まない——Shown_Plan は前回の出力であって入力ではなく、入力の同一性では同じ計画は同じである。

## Considered Options

- **時刻の差だけを費用にする**: 同じ時刻のまま釜だけが変わる・まとまりが割れる・先頭が入れ替わる変更に費用が付かず、最も守りたい投入対象を守れない（実測：同じ時刻に置かれるのに釜だけが変わった）。採らない。
- **Head の旗を Shown_Plan に保存する**: 確定時点の旗では「10 秒に開始」と確定した品目が 10 秒に濃くなっても旗は偽のままで守れず、anchor の失効で後続群が隠れただけの同じ計画に費用が付く。比較の時点で両側から導く。
- **未着手の品目の欠落に費用を付ける**: 費用の算術が逃げ道になる。既存のハード制約（`isStale`・合成の尾部）が既に閉じているので、費用は定めない。
- **前回の配置をハード制約にする（変更禁止）**: 釜の占有・上げ窓と衝突し、利益が覚え直す負担を上回る変更まで禁じる。費用にして feasible な候補の間の選び方にだけ効かせる。
- **Shown_Plan を確定計画のキャッシュとして読む**: 確定計画は毎回導く導出値で、キャッシュにすれば二つの真実になる。Shown_Plan は比較にだけ用い、確定計画・no-op 判定・hydration には使わない。

## Consequences

- 永続 v12（`shownPlan`）。v11 以前の欠如は空（比較の相手なし・費用 0）に畳み、壊れた要素はその要素だけ落とす。切戻しは `version` を 11 にするだけ（`docs/persisted-schema-rollback.md`）。
- `settle` は Shown_Plan が在ると計画を 2 回組む（忠実な計画と候補を比べた計画）。n ≤ 64 で問題にならない。
- `scoreSchedule(slices, pending, scoreContext: ScoreContext, params)`——`ScoreContext { members, lifts, change }`。`admit` は 3 回の採点に同じ文脈（旧 Shown_Plan は `prev.shownPlan`・Timer 集合は再同期後・now は受領時刻）を渡し、段 2 の総和比較に Change_Cost が乗る。改善判定の基準は Committed_Plan のまま。前回と大きく違う計画で微小な改善を出す外部解は通りにくくなる。
- 性質 5.6 は「同じ入力で続けて計画すると、同じ計画（Change_Cost 0）か総費用が真に下がる計画になる」と言い直す。前回を残す候補が前回の無い計画に無かった配置を見つけることがあり、それは「利益が上回れば変わる」そのものである。計画が変わるのは総費用が真に下がるときだけで、前回そのものは変更費用 0 ゆえ、now を含む業務入力を固定すれば業務費用そのものが厳密に下がり、有限回で同じ計画に落ち着く。
- ADR-0008「永続的な群の履歴は持たない」は識別子について保つ。Shown_Plan が持つのは直前の提案の「同じ群だった相手の鍵」だけで、識別子を跨いで比べない。
- 群の連鎖と Head の導出は `src/domain/lift-group.ts` に移り、client と engine が一つの関数を共有する。表示・Boil_Sync・ハード制約は変えない。
- 重みは実機で見直す。設定に上げるのは、値の店舗差が実在したときである。
