# 釜の占有は玉数から導く。設定も状態も釜数を持たない

メニュー対応表（`menuItems[].sizes[]`）と注文品目（`OrderItem`）が持つ麺量の事実は**玉数**（`portions`・0.5 刻み）
であり、品目 1 件が要る釜の数（`slotSpan`）は domain の純粋関数 `slotSpanOf(portions) = ⌈portions / 1.5⌉` で導く。
釜数は設定・状態・永続・ワイヤのどこにも保持しない。

**なぜ玉数が事実か。** 麺を釜へ落とす人が知りたいのは「何玉入れるか」であり、「何釜使うか」はその帰結である。
2026-09-14 に、中盛（1.5 玉）が 9 商品コード・51 箇所で「2 釜」と登録されていた——人が釜数を入れる形は誤る。
麺量マスタ 490 行・10 店舗では例外なく 0.5→1・1.0→1・1.5→1・2.0→2・2.5→2 で、「1 釜（テボ）に入るのは 1.5 玉まで」
という物理が全行を説明する。麺種では分かれない（つけ麺の 1.5 玉も 1 釜）。

**なぜ定数か。** `PORTIONS_PER_SLOT = 1.5` は釜の物理で、10 店舗で差が無い。設定にすれば投入漏れの面が一つ増え、
店舗ごとに「同じ玉数が違う釜数」になる余地が生まれる。店舗差が実在した日に設定へ上げる（`liftIntervalSeconds` が
2026-09-17 にそうなったのと同じ道）。

**導出は半玉単位の整数演算**（`⌈2p / 3⌉`）で行う。0.5 刻みの p に対し 2p は正確な整数で、天井が浮動小数の丸めで
1 ずれることがない。

**読み手は意味を変えない。** engine の割当・上げ窓・Acceptance_Gate、CP-SAT のモデル、client の釜の組は、従来
`item.slotSpan` と書いていた箇所で `slotSpanOf(item.portions)` を読む。同じ場面で同じ釜数が出るので計画の判定は
変わらない。永続は v15（`portions` を足し `slotSpan` を落とす）。

## 却下した案

- **(a) 釜数を残し玉数を足す。** 二つの真実。設定変更や移行のたびにずれる余地が残る（14 日の誤りがその実例）。
- **(b) `PORTIONS_PER_SLOT` を店舗設定にする。** 店舗差が実在しない。
- **(c) 移行で玉数を `null` か和型にする。** null の品目の釜数を別に持たねばならず「両方ある／どちらも無い」が表現可能に
  なる。和型は真だが、一度きりの移行のために全読み手が永久に分岐を持つ。運用前ゆえ、v14 以前の釜数を仮置きの玉数
  （`portions = slotSpan`）として読む形にとどめた。
- **(d) イデア（Policy）を釜数から逆算して移行する。** 逆写像は一意でない（1 釜は 0.5 / 1.0 / 1.5 のどれでもありうる）。
  本部の正本に推定値を書き込むのは事実の捏造である。正しい玉数は本部が持ち、投入し直す。
- **(e) 玉数を名前（`中盛`）から引く。** 名前を判定に用いない規律（pos-order-ingress）に反し、改名が解釈の変化になる。
  つけ麺の中盛は 2 玉であり、語は玉数を一意に定めない。
