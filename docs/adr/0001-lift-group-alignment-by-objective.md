# 調理計画の単位は「同時に上げる群」で、群の一致は制約ではなく採点の帰結とする

調理計画（online-cook-scheduling）は当初「全オーダーの待ち時間の総和の最小化」を第一目的に置き、卓の同時提供は許容幅（60 秒）の内側に散らすソフト制約だった。現場が実際に欲しいのは「次に何を茹でるかを迷わず決められること」であり、待ち時間と同期はその順序を決める採点基準にすぎない。そこで計画の単位を **Lift_Group（同時に上げる群）＝同じ卓の、計画対象に入った未着手の品目すべて** に定め、群の中の提供時刻（serveAt）を一致させる方向へ改める。

一致を **ハード制約にも保証にもしない**。目的関数の卓同期項を「最大差の許容幅超過分」から「卓の成員のうち最遅からの各成員の遅れの和 × w_table」へ変える。**成員には同じ卓の走行中 Timer（実効 endTime を serveAt とし、動かせない）を含める。** この形の最適点はただ一点 `max(走行中の錨, 未着手の earliest の最大)` であり、群の全員が錨に届くときは錨に揃い、届かない品目があれば群ごと錨より後ろへずれる。自前解も外部ソルバの解も同じ物差しで「揃える方が点が良い」状態になり、Acceptance_Gate は feasibility だけを見ればよい。揃わない配置はどの層でも嘘にならず、減点として計上されるだけである。

## Considered Options

- **ゲートに一致を求める**: 揃えない外部解を棄却する。揃えられない卓が永遠に計画されない場面が生まれ、群の定義が計画と判定の二箇所に住む。採らない。
- **許容幅を 0 にする**: 最大差しか見ない形では 3 本以上の卓で 3 本目以降を待たせる得が無く、揃わない。採らない。
- **錨に固定した基準点で採点する**: 走行中の錨に届く品目だけを錨に揃え、届かない品目を単独で遅らせる配置が最適になるが、`earliest` が解放表（＝計画順）に依存して採点が一片で閉じず、外部での再現性を失う。採らない。
- **走行中を採点に含めない（当初案）**: 錨へ揃える配置が Σ Wait_Time の分だけ点が悪く、自前解のハードコードになる。採らない。

## Consequences

- 計画は「釜が空いていても待て」と言う。待ちに上限を置かず、揃えのための待ちは Σ Wait_Time に数える（定義を二つにしない）。
- 揃える方が点が良くなるのは w_table > 1 のときで、既定 2 では成り立つ。w_table ≤ 1 の店は「卓を揃えない」を選んだ店であり、妥当域は変えない。
- 採点が走行中を読むため、`scoreSchedule` は `running` を受け、Boil_Sync の調整が採点を動かす。これは「Boil_Sync の出力を所与の事実として読む」既存の立場（AC 9.3）の適用である。
- 永続された `AcceptedSlice.score` は走行中や重みの変化とずれるため、改善判定は比較の時点で Committed_Plan と外部解の両方を再採点する。**`PlanSlice`（したがって `AcceptedSlice`）と `CookSchedule` から `score` を落とす**（採点は placements からの導出値。`baselineSchedule` / `committedSchedule` は採点を呼ばなくなり、配置と採点が分離される。`settle` の等価判定は placements の比較で足り、移行は v9 の余剰 score を捨てる）。基準は Committed_Plan のままで、自前解へ移さない。
- 一致が成り立つのは群が釜容量（`slotSpan` の合計）に収まるときで、超える群は batch に割れ、差は減点される。錨は batch ごとに取り直す。
- 最適性の主張は「釜の割当と batch の分割を所与として」に限る。割当を変えた外部解が自前解に勝つことは正当にありえ、それが外部ソルバを残す理由である。
- 卓同期項の秒換算は切り上げにする（ADR-0006）。切り捨てで揃えると 1 ms ずらした外部計画がゲートを通り、client の等号による群が割れる。
- `tableSyncToleranceSeconds` は計画で使われなくなり、`orderSync*` は減点項としてだけ残る。設定・ワイヤ・外部契約に及ぶため撤去は別の判断とし、撤去候補として記録する。
- 卓を持たない品目は単独の群。オーダー（伝票）は群の単位にしない。
