# arms は計画ではソフト制約（実質タイブレーク）、Boil_Sync ではハード制約のままとする（非対称は意図）

計画（開始前）と Boil_Sync（開始後）で `arms`（同時に上げられる本数）の扱いを揃えない。計画では arms 超過を減点項に留め、卓の同時提供が arms に勝つ（3 品目の卓は arms=2 でも一群として計画する）。Boil_Sync は今のまま arms 本ずつの Sync_Set に分割し、開始後に 2+1 へ endTime をずらす。

理由は、腕が 2 本であることは上げる瞬間の物理であり、その瞬間を扱うのは Boil_Sync だからである。計画の群は「なるべく arms 以下」という意図であって、現場には群を見せないので、開始後に分かれても表示に矛盾は出ない。Boil_Sync の arms 分割を撤去する案は、同 spec のハード制約（AC 1.1 / 1.2）の改訂と 69 ファイルのテスト改訂を伴い、得るものが無い。

**arms 超過の重みは設定にも定数にもせず、`max(0, tableSyncWeight − 1)` から導く。** 任意の w_table ≥ 1 で「卓 > arms」が式から出て、設定の妥当域を変えずに済む。arms 超過は卓の群を組むときにだけ生まれる費用で、群を組む価値の一段下に群を組む代償を置く関係が式になっている。単位は秒 対 本数で既定では 1 本 1 秒に相当し、**実質はタイブレーク**である。効かせるなら「arms を超えた 1 本が上げ遅れる秒数」という計測値が要り、それが実在したときに持ち込む。「卓同期 > arms 超過 > 釜距離」の全順序は要求しない（既定 2 と 1 の間に整数が無く、採点は整数で閉じる）。

同じ理由で `slotSpan`（大盛が要する釜数）は **計画のハード制約** に置く。要求として持っているのに割当が読まない状態は「まだ実装していない」として pos-order-ingress AC 6.36 が繰り延べていたもので、本判断がそれを解消する。釜容量は `slotSpan` の合計で数える。**品目自身の釜どうしの距離は採点しない**——既存の釜距離項は代表 slot 1 点で見るため品目内の距離を計上できず、新しい項を建てるほどの重複も無い。自前解の釜選択は第一基準を「`slotSpan` 個すべてが空く最早時刻の最小化」に置き、釜距離は同点が余るときだけ断つ（採点しない値のために採点する値を悪化させない）。

**Arms_Overflow は「群の本数」ではなく「同じ `serveAt` を持つ卓の成員（走行中を含む）の本数」で数える。** 腕が競合するのは同時刻だけであり、群が釜容量を超えて batch に割れた場合に同時に上がらない本数まで減点しない。卓同期項と同じ成員集合の上で数えることで、「卓の成員とは何か」が一箇所に留まる。

## Consequences

- 計画が arms と slotSpan を読むようになるため、Input_Fingerprint に両方を含める（`digest.ts` の「arms は畳まない」「全フィールドを含める」を改める）。
- 開始時に `slotIds` の数と `slotSpan` の一致を検査しない規律（既存 AC 8.3）は変えない。計画がハード制約にした後も、開始は現場の判断に委ねる。
- 品目自身の 2 釜が離れていても計画は成立する。隣接は好ましさであって条件ではない。
- Acceptance_Gate は `slotIds` の本数が `slotSpan` に等しいことに加えて **釜が相異なること** を見る。`["3","3"]` は本数 2 を満たしながら 1 釜しか占めず、解放表にも現れない。本数で数える設計が開けた穴を同じ場所で閉じる。
