# 釜の解放予測と開始可能性を分離する

本番で、計画上は「今」開始できるはずの先頭が押せない釜に置かれ、本当に開始できる後続まで隠れた（ユーザー調査・2026-09-06・対象 6947f39）。原因は二つの契約の食い違いである。engine の解放表（`initialRelease`）は茹で上がった釜（boiled・Complete 前）の実効 endTime が過去ゆえ `now` に空くと扱い、空き釜と同じ値になる。client の占有判定（`occupiedSlots`）は Complete まで占有扱いにし、全釜 idle でない提案は出さない。さらに群の連鎖（`visibleGroupsOf`）は未開始の先頭群で止まる。再現（6 釜・arms 2・Thin 60 秒・卓なし 8 品・表示の先頭から 3 秒間隔で開始・茹で上がりの 15 秒後から釜番号の大きい順に Complete）：72 秒に釜 1 を Complete すると、残りの A は boiled の釜 0 に「今」（先頭群）、B は空いた釜 1 に「今」（後続群）で、A は占有で非表示、B は連鎖で非表示——提案はゼロになり、75 秒の釜 0 の Complete まで止まる。24 品の連続処理では Complete を昇順に行えば空白 0 箇所、降順なら 6 箇所で、前回計画の履歴の有無に依らない。永続的な停止ではなく、**釜の再利用時の完了順に依存して提案が途切れる**構造である。

**三つの概念を分けたまま持つ。** (1) **Startable_Slot**——Timer（running / boiled とも）が一つも載っていない釜。domain の `occupiedSlotsOf(timers)` の補集合で、client の全釜 idle と engine が**同じ関数**で読む事実。(2) **今割当可能な釜**——Startable_Slot のうち、採用済み接頭辞の予約と表示順で先行する配分を反映した解放表で解放時刻が `now` 以下の釜（`pinNow` の局所変数 `assignable`。予測 ＋ 事実の導出値で、公開名にしない）。(3) **解放表**——「将来いつ空く見込みか」の予測。boiled の釜は `now`。**変えない**（Complete の時刻は予測できず、boiled を占有として載せれば待ち時間の起点が消える）。事実を読ませるのは二箇所だけである。一つは自前解の**「今」置く配置（`startAt ≤ now`）の釜の配分**（`pinNow`）——「今」の品目を最終的な表示順（`startAt` → `compareArrival`。計画の一片の順ではない——先頭 arms 本は表示の順で数える）に並べ、`release ≤ now` の釜の上で排他的に配る：今割当可能な釜が足りれば Startable_Slot だけから（前回の釜 → いまの釜 → `chooseSlots`）、足りなければ待つ釜（boiled）だけから、それも足りなければ index 順の退避先。Timer の在る前回の釜は「今」には守らない（釜の変更費用 L は払う——開始できない提案を守る価値は無い）。空き釜が足りなければ余りは Complete を待つ（空き釜不足の待ちは残す）。もう一つは確定計画の合成の**保持の条件** `cannotStart`——過去開始（`startAt < now`）∨ 開始を妨げる配置（`startAt ≤ now` かつ釜に Timer）で、採用済み接頭辞（再配分されない）にだけ当てる。復元した一片には当てない（過去開始は retime で消え、残るのは空き不足で boiled を待つ配置だけで、それは合法・AC 1.4）し、生成した計画全体の成立の条件でもない。将来配置（`startAt > now`）の釜の選択は占有を直接の条件にしない（boiled はそれまでに Complete される予測に立つ。先行する「今」の釜が変わることによる解放表の波及は許す）。連鎖・全釜 idle・ゲートの feasibility（Timer の在る釜に「今」置く外部計画は feasible のまま——次の合成で落ちる）は変えない。

**計画は 1 段目 ＋ loop で組む。** 1 段目は従来の業務費用の計画（何を「今」置くか・時刻）。loop（`placeNow`）は、「今」の集合（nowSet）**全体**を最終的な表示順で配り直し、1 段目の将来配置をそのまま復元し、計画順に物理的なハード制約の述語（置ける品目に限る `isStale`・`feasibleRelease`・`keepsAnchor`・`withinLiftCap`）で検証して、不正な一片だけをその位置で——配分した「今」を残して——再生成し、再生成で新たに「今」になった品目が在れば nowSet に足して配り直す。**停止性は nowSet の増加**（増えなければ止まる・釜の固定に依らない）。loop で発見した順に釜を固定してはならない——後着の品目が先に空き釜を固定すると、後から「今」になった先着の品目（表示の先頭）が boiled の釜に落ちて押せず後続も隠れる（同卓の先着 Short 60 秒・後着 Long 600 秒・釜 0 が boiled・釜 1 だけ空き）。1 段目の時刻を下限にする規則（当初の 2 段目）は撤回した——場面 E（24 釜・arms 1・L 49）で合流分を 150.001 → 199 秒へ押し、窓が説明しない延期として `keepsAnchor` (d) を破った。後の一片の配分した「今」の釜は手前の一片に対して**取り置く**（解放を ∞ に）が、これは計画順の解放表（ゲート・合成が読む「その釜は次にいつ空くか」）を成り立たせるためだけで、上がりは載せない（載せると手前の pack の延期の理由が計画順の検証に見えず (d) を破る）。取り置いた釜は batch の幅に数えない。**固定した「今」を残した再生成が計画順で成り立たない場面では、候補 K を組む**——1 段目の全時刻を保ち、配分で「今」が新しく取った釜を使っていた将来配置を、動いた「今」が空けた釜へ index 順に写す**釜の交換**（「配分した釜に置き換えるだけ」では、空き釜へ動いた品目と同じ釜に 30 秒後で置かれていた将来配置と重なって違法になる）。K を再生成も取り置きも無しに計画順の物理的なハード制約で検証し、合法なら K と再生成（「今」の入れ替えを含む）を同じ旧 Shown_Plan に対する総費用で比べて真に低い方（同点は K）。**1 段目の「今」は絶対保護しない**——まだ調理者に見せていない内部候補で、守るのは示した提案の安定性（R と変更費用）と完成した計画の開始可能性である。総費用の向きは重みで変わる（6 釜・釜 0 boiled・arms 1・L 5・同卓の 45 秒麺 N と 75 秒麺 A・別注文の 45 秒麺 C と大盛 M：同期の重み 0 なら再生成 1427 対 K 1457 で再生成——N 今・M 5 秒後、既定の重みでは A と N を 30 秒ずらす卓の遅れで K 1457 対 再生成 1487 で K——N は 30 秒後・M 今）。どちらの向きでも、「今」を失うのは物理的に開始不能だからではなく別品目を繰り上げる業務上の選択で、選ばれる理由は費用である。1 段目への無条件のフォールバックは置かない——場面 E の 1 段目は「今」の大盛を Timer の残る釜 1 に置いており、合法性のために開始可能性を捨てる順序になる。完成した候補は合成・ゲートと同じ共通のハード制約を計画順に満たすことを性質で検査し、自前解だから免れる述語は置かない。

**前回の計画は再生成せず復元して比較候補に残す（ADR-0010 の Component 5「前回に忠実な計画と候補を比べた計画の 2 本」を置き換える）。** 性質 5.6（同じ入力で続けて計画すると同じ計画か総費用が真に下がる計画）は実占有で 3 回に 1 回落ちた。原因は、前回に忠実な候補（`Continuity.faithful`）を**生成器で作り直して**前回を再現しようとしていたことで、固定・下限・取り置きの規則を足しても将来の釜・分割・群まで一致する保証にならない（反例 4 場面：下限 209.821 → 209 秒で総費用 +2、釜の取り置きで +40・+76・+64）。守りたい end state は「入力が変わっていないのに提案が理由なく悪化しない」であり、それは生成器の再現性ではなく**候補の選択規則**で成り立たせる。保持候補 R：`shownPlan` の品目のうち置ける品目に在るものを初出順の一片に組み `slotIds` / `startAt` / `serveAt` / `anchor` をそのまま持つ（復元）→ 過去開始の「今」は `startAt = now`・`serveAt = now + 現在の茹で時間` に置き直す（retime）→ 錨は旧 Shown_Plan の品目のうち**今回 Timer になったもの**の実効 endTime にだけ付け直す（`reanchor`。全走行中に付け直すと生成器が意図して付けなかった錨が付き、同じ入力で前回と 1 箇所違う計画になった）→ 一片ごとに計画順で合成と同じ述語で検証し、不正な一片はその位置でその卓を再生成する（「最初の不正で止める」接頭辞の形は、now が進むたびに前回の「今」が落ちてほぼ全再生成になる）→ 前回に一片が無かった卓を末尾に置く → 同じ loop を通す。生成候補 F（文脈つきの生成器 ＋ loop）と R を**同じ旧 Shown_Plan**に対する総費用（業務費用 ＋ 変更費用）で比べ、R ≤ F なら R（同点は前回）。`Continuity.faithful` は撤去し、生成器の前回の釜の第一候補・並びの同値・前回の配置を再現する分割の候補は残す（復元は生成器の優先規則を置き換えず補完する——外すと 3000 場面中 42〜126 で劣る）。`isStale` の対象集合は**置ける品目**（`placeableTargets`：期限 → 64 件 → 茹で時間が引ける ∧ `slotSpan ≤ arms + HELPER_ARMS`。空き不足と上げ窓の混雑は除外理由にしない）で、自前解・合成・ゲート・復元が同じ集合を使う——正本の計画対象のまま比べると、未知麺種を含む卓の一片は自前解がその品目を置かないので常に「欠落」で落ちた（3000 場面中 1319 一片）。指紋と要求は正本の計画対象のまま。

## Considered Options

- **boiled を占有として解放表に載せる**: Complete の時刻は予測できず、boiled の釜を ∞ に置けば待ち時間の起点が消え、いつ空くか分からない釜を計画から外すことになる。解放表は予測の契約（ゲートの feasibility も同じ表を読む）で、事実を混ぜれば予測が壊れる。採らない。
- **連鎖を緩めて後続群を無条件に出す**: 先頭群が押せないままで、業務のまとまり（ADR-0005・0007）を崩す。第一案にしない。engine が先頭群の「今」を Startable_Slot へ置くので、空き釜が足りる限り先頭群が押せ、連鎖は変えずに済む。
- **同点処理だけ（Timer の無い釜を同点の先に）**: 前回の釜の第一候補（AC 3.1）と変更費用が boiled の釜の旧割当を守り続ける。また計画の一片の順（卓の最早到着）で空き釜を配っても表示の先頭（`startAt` → 到着順）に渡らない——同時到着の「卓 a／注文 z」と「卓 b／注文 a」は計画では a、表示では b が先。選択規則として、表示順の排他的な配分に固定する。
- **client だけで直す**: サーバの計画・要求・ゲートは押せない釜を指したままで、snapshot の推奨と表示が食い違う（真実が二つ）。採らない。
- **前回の計画を再現規則で生成し直す（ADR-0010 の faithful）**: 固定・下限・取り置きの規則を足し続けても、実占有では 5.6 が落ちた。復元に置き換える。
- **1 段目の全時刻を下限にして 2 段目を組み直す**: 実装由来の規則で、場面 E で合流分を窓が説明しない時刻へ押した。合法性のために 1 段目へ戻す案は、その 1 段目の「今」が押せない釜に在るので元の不具合を再発させる。復元 → 検証 → 不正だけ再生成に置き換える。
- **1 段目の「今」を絶対保護し、物理的な例外としてだけ外す**: 1 段目は内部候補で、K（時刻を保ち釜だけ交換）が合法な場面で「今」を入れ替えるのは費用の判断である。例外ではなく候補 K との総費用比較にする。

## Consequences

- 計画は F と R のそれぞれで 1 段目 ＋ loop（と、固定を外す場面では K の検証と採点）を走らせる。n ≤ 64 で問題にならない。`settle` が組む候補は最大 2 本（＋ K）。
- 性質 5.6 は実占有で**選択規則から**成り立つ——R は前回そのもの（変更費用 0）ゆえ、計画が変わるのは総費用が真に下がるときだけ（1500 回 × 8 で反例なし）。loop を通した計画は「自分自身を前回として組み直す」ことの不動点ではない（次回が同じ入力で真に良い計画へ 1 歩進み、そこで落ち着く）。
- 性質 4.1 の保証対象は「最終的な「今」の集合の表示順で最初の品目」で、例外は空き不足・採用済み接頭辞の予約による排他・上げ窓・合流の契約。保証は再計画の時点に限り、遷移なしの時刻経過だけで将来配置の `startAt` が来た場合は次の遷移で置き直す。
- Property 1／16（錨の一致）は `startAt > now` の配置について主張し、「今」に固定した品目を除く（固定分との同期と再生成した batch 内部のまとまりは分ける・判断 15）。5.7 (i) は (i-a) 生成器（占有なし）：表の外の番号は読まれない、(i-b) loop（実占有）：前回の釜が表の外なら R は F と同じ計画、に言い直した。4.7′ は K を実際に組んで合法性と総費用を比べる。
- 実測の頻度：10000 場面 14112 候補のうち固定を外す場面 11・すべて K が合法で選ばれ再生成 0。反例の形に絞った生成器（6 釜・釜 0 boiled・arms 1・L 5）では 20000 場面 29935 候補のうち固定を外す場面 159・K 違法 25・K 選択 130・再生成選択 4。摂動（2 秒経過・先頭の開始・新着・Complete）の後、摂動できた 248 場面のうち R が F と違う計画として選ばれたのは 39 場面（15.7%）、変更費用 0 が 182 場面（73.4%）、変更費用の平均 96.2 秒。
- 8 品の再現は 72 秒の釜 1 の Complete の直後に A が釜 1 に「今」で先頭・B は待つ釜 0 へ退避し、A 72 秒・B 75 秒に始まる（修正前は 75・78 秒）。24 品 48 通り（卓なし／同卓／4 品ごと × slotSpan 1／2 × 昇順／降順 × Shown_Plan 有無 × 接頭辞有無）で例外に当たらない空白 0 箇所。
- 取り置きの意味：後の一片の「今」の釜は手前の一片に対して ∞（上がった後に使う配置も許さない）。上がりは載せず、窓の上限は後の一片の側で検証する。batch の幅は取り置いた釜を数えない（数えると ∞ の釜を取って上げ表の走査が止まらない）。
- `reanchor` の相手は旧 Shown_Plan の品目から始まった走行中に限る（同じ入力の再計画では何も付け直さず、前回そのものが復元される）。
- 公開の口：`occupiedSlotsOf`（domain）、`cannotStart` / `feasibleRelease` / `placeableTargets`（`schedule.ts`。`isStale` と `placeableTargets` は合成・ゲート・復元が共有、`cannotStart` は合成の採用済み接頭辞だけ、`feasibleRelease` はゲート・復元・loop の `revalidate` が当て、合成の `livePrefix` は採用済み接頭辞に当てない——既知の制限として `online-cook-scheduling` に記録）、`tableKeyOf`（`project.ts`）、`scheduleCandidates` / `scheduleStages`（性質の検査が選ばれなかった側と K を見る）。`baselineSchedule` は `now` の隣に `occupied` を受ける。`livePrefix` が解放表の feasibility を採用済み接頭辞に当てない事実は文書に記録した（契約は変えない）。
- 永続スキーマ・ワイヤ・`RequestPlan` は変えない（v12 のまま・`docs/persisted-schema-rollback.md` に行は増えない）。`src/solver` は `occupiedSlotsOf(request.running)` を渡す。
- 将来品目の繰上げ（1 段目が待つと決めた品目を「今」にする候補）と Complete の自動化はスコープ外のまま。
