# 1 釜 1 Timer は状態の不変条件であり、入口の検査ではなく遷移の結果で守る

`slot-suggested-start`（AC 3.7・要件 8.3）は「engine は釜の占有を検査しない」と定めた。理由は判断 7 に
記録されている——**拒否は状態の嘘を防ぐためであり、現場の選択を否定するものではない**。釜の占有は
「推奨との一致」「`slotIds` と `slotSpan` の一致」と同じ括りで、どれも**アプリが提案したとおりに操作したか**
の検査である。厨房が提案と違う釜を使うのは普通の運用であり、そこで拒否すればアプリが現場を縛る。
重畳は「押す場所が idle にしかない」という client 側の構造が防ぐ、とした。

**その前提は 3 つの事実で崩れている。**

**client の構造は単一端末・オンラインでしか働かない。** `degraded-slot-superimposition` は、縮退中に
boiled 化した server-confirmed タイマーが `view.timers` に残ったまま同じ釜へローカル暫定タイマーを
立てられる経路を**バグとして記録している**。そこで破られている不変条件は本 ADR と同じ「1 スロット ≤
1 タイマー」である。複数端末と、押してから DO に届くまでの遅れ（2026-09-14 実測で数秒）も同じ穴を開ける。

**正本の形が重複を許している。** `TimerState.timers` は釜を鍵にした表ではなく `readonly Timer[]` で、
各 Timer が `slotIds` を持つ。`MAX_TIMERS`（100）は台数の上限で釜の本数と無関係である。ゆえに
**釜 12 本の店に 14 本の麺が茹だっている状態**が型としても検査としても作れる。`initialRelease` の
「同一 slot を複数 Timer が占める状態は表現可能である。その釜が空くのは最後の一本が上がった時」は、
その状態を**読む側が畳んでいた**ことの記録である。

**読む側が増え、畳めなくなった。** CP-SAT（`cpsat-planner-integration`）は走行中を**動かせない事実**として
受け取り、「1 つの釜で同時に茹でられるのは 1 杯」を**ハード制約**として課す。重複した正本を渡すと、
新しい杯を 1 つも置く前に前提が矛盾し、**解が存在しない**（`INFEASIBLE`）。TS 計画器は「最後の一本で
空く」と 1 つの数字に畳んでいたので矛盾に気づく必要がなかった。ローカル実測では、同じ釜に 3 本
載せるだけで 8 局面すべてが `INFEASIBLE` になる。

判断 7 の線引き——**正本が嘘をつくなら拒否する**——に照らせば、釜の重複はいま嘘の側にある。
「釜 12 本に 14 本」は現場の選択ではなく、物理的に存在しない事実である。

**守る場所は入口ではなく遷移の結果である。** 開始の入口ごとに占有を検査すると、経路を足すたびに
書き忘れる余地が残る（現に `startTimer` と `startOrderItemTimer` の 2 つがあり、将来増えうる）。
`decide` は core への唯一の入口なので、そこで**遷移の結果が物理的に在りうる状態か**を一度だけ問えば
すべての遷移が覆われる。大盛（`slotSpan` 2）は同じ Timer が 2 釜を占めるだけで重複ではない——
**所有者が違うとき**にだけ拒否する。

**既に壊れている状態では止めない。** 遷移が重複を**新たに作った**ときだけ拒否する。永続から復元した
状態に重複が在れば、あらゆる操作が永久に拒否されて店舗が動かなくなる。

**そして `migrate` でも直さない。** ADR-0014 が件数の上限を `upsertOrder` と `migrate` の 2 箇所に
置いたのとは配置を変える。理由は 2 つある。**「移行は Timer を落とさない」は `migrate` の性質として
固定されており**（`migrate.property` の Property 5・5.8・12——v7/v9/v10/v11 のいずれの面でも
「それ以外は写しである」）、それを緩めるには実害が要る。そして**実害が観測されていない**——本番の
実測（2026-09-14・求解失敗 111 件のうち `INFEASIBLE` **0 件**）が示すとおり、重複はいま発生して
いない。直すべき既存データが無いのに移行の契約を緩めれば、**起きていない欠陥のために、移行が
事実を落とす自由を手に入れる**ことになる。

**既存の重複が万一在っても、時間が解決する。** `decide` が新しい重複を作らせないので、在るものは
茹で上がりと完了で消えていく。`migrate` の修復が必要になるのは、**重複が実際に観測され、かつ
自然に消えないことが分かったとき**である。その判断材料は `cpsat-plan-failed` の `INFEASIBLE` で
——CP-SAT が矛盾を検出する唯一の読み手として働く。

## Considered Options

- **開始の入口で釜の占有を検査する**: `startTimer` / `startOrderItemTimer` に検査を置く案。経路ごとに
  書く必要があり、将来の経路で書き忘れる。実装しかけたが採らない。
- **状態の形を変える（釜を鍵にした表）**: `slots: readonly (TimerId | null)[]` を正本にすれば重複は
  **型として書けない**。最も強い保証だが、`.slotIds` の参照が 91 箇所（engine 56・client 16）あり、
  wire 契約とスキーマ移行（現在 v13）を伴う。**正しい方向だが、CP-SAT の移行と混ぜると切り分けが
  効かなくなる。** 本 ADR では採らず、別途計画する。
- **中間オブジェクトで両側から参照を張る**: `Timer.slotIds` と占有表の両方が釜を持つ形。
  **`design-philosophy.md`「導出値を状態に昇格させない」が名指しで禁じる形**である——二つの真実の源が
  生まれて必ずズレる。採らない（片方向にするなら上の「釜を鍵にした表」と同じものになる）。
- **CP-SAT 側で重複を畳む**: 衝突した釜を「使えない」と見なして解く案。矛盾を飲み込んで隠すだけで、
  正本の嘘は残る。読む者が増えるたびに同じ処置を書くことになる。採らない。
- **`migrate` でも修復する**: `truncateOrderItems` と同じ 2 箇所配置。**移行の 4 つの性質
  （「Timer を落とさない」）を改訂する必要があり**、実害が観測されていない段階では釣り合わない。
  採らない（Consequences を参照）。
- **拒否せずログだけ出す**: 頻度を測ってから決める案。本番の実測（2026-09-14・失敗 111 件のうち
  `INFEASIBLE` **0 件**）が示すとおり、**いま重複は起きていない**。ただし起きていないことと
  起こせないことは別で、正本が不可能な状態を持てること自体が欠陥である。観測は併せて行うが、
  それを理由に不変条件を先送りしない。

## Consequences

**新しい拒否事由 `SlotOccupied` が増える。** 現場から見れば「その釜は使用中です」。client は既存の
`error` メッセージの経路で受ける（`webSocketMessage` が要求元の WS だけへ返す）。

**要件 3.7（AC 8.3）の改訂が要る。** 「釜の占有を検査しない」は撤回する。同じ AC が括っていた
「推奨との一致」「`slotIds` と `slotSpan` の一致」は**検査しないまま**である——あちらは現場の選択で
あって、正本の嘘ではない。

**`migrate` は変えない。** 型でも `decide` でも永続から入る値は守れないが、**守らないことを選ぶ**。
重複を抱えた状態は読み込まれ、`decide` が新しい重複を足さないまま、茹で上がりで自然に解消する。
**この選択は観測に紐づく**——`INFEASIBLE` が本番に現れたら、`migrate` の性質を改訂して修復を入れる。

**本番では挙動が変わらない見込みである。** 2026-09-14 の実測で `INFEASIBLE` は 0 件、つまり重複は
発生していない。拒否が実際に増えるかは `command-rejected` の観測で分かる。

**状態の形を変える案は残る。** 本 ADR は不変条件を**実行時に**守る。型で書けなくするには正本の形を
変える必要があり、それは CP-SAT の移行が落ち着いてからの別作業とする。
