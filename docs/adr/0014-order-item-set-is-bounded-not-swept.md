# 注文品目の正本は有界であり、上限は掃除の出来事ではなく集合の構築点に作り込む

`order-lifecycle`（ADR-0013）で品目を「開始で消費せず生涯を通じて残す」に改めた時点から、`TimerState.orderItems` は実質的に減らなくなった。集合を離れる経路は「POS の取消・0 件の後着（`removeOrder`）」と「後着に現れなかった同じ注文の品目」の 2 つだけで、**いずれも未調理の品目に限る**——`completedAt` を持つ品目を除く経路は存在しない。`pending-order-expiry`（ADR-0011）が入れた期限は**読む側の述語**であって正本を変えないので、期限切れの品目も永続層には残り続ける。

正本は単一キーの単一の値として永続され（`SNAPSHOT_KEY = "activeTimers"`）、確定のたびに全体が書き直される。ゆえに集合が伸びることは 2 つの形で効く。いつか永続の値の上限に当たって `Persist` が落ち、以後いっさい確定できなくなる。それ以前に、すべての遷移が肥大した直列化を払い、hydration が同じ量の復元を払う。

**上限は集合の性質であって出来事ではない。** 「古いものを掃除する」別の仕掛け——専用の遷移・Alarm・起動経路・永続の鍵——を作らず、`src/engine/pending.ts` の純粋関数 `truncateOrderItems(items)` を一つ置き、**件数を増やしうる唯一の経路の出口**でそれを通す。件数を増やすのは `upsertOrder`（POS 到着）だけである——`complete` / `cancel` は既存の要素に厨房の事実を書くだけ、`removeOrder` は縮めるだけ、`start` は照合するだけ（品目を消費しないのが ADR-0013 の帰結）。もう一つ、**永続から値が入ってくる口**である `migrate` も同じ関数を通す。この 2 箇所で、上限を超えた集合は構造的に存在しなくなる。掃除を別の出来事にすれば「掃除が走ったか否か」という第 2 の状態が生まれ、走っていない時間帯の振る舞いを別に語ることになる。上限が集合の性質であれば、語ることは一つで済む。

**truncate はストレージ操作ではなく配列を短くすることである。** 永続層は SQLite バックエンド（`new_sqlite_classes`）だが、コードが触るのは非同期 KV API だけで `ctx.storage.sql` は使わない。品目ごとの行は存在しないので、品目を落とすことは行の削除ではない——`put` は従来どおり単一キーへの 1 回のままで、shell は一行も変えない。

**上限は件数だけ（`ORDER_ITEM_LIMIT` = 4096）、忘れる順は `compareArrival` の古い順だけ、そして何も守らない。** 時間窓による truncate は行わない——期限（`ORDER_LIFETIME_MS`）は「現場に見せるか」、保持は「永続に載るか」で、別の関心である。`truncateOrderItems` は `now` も Timer も設定も受けない。それが 2 つの軸を分ける線である。`cooking`（生きた Timer の参照先）も例外にしない——守る述語を一つ入れれば「上限を超えているのに落とせない」場面が生まれ、上限が上限でなくなる。落ちた参照先は既に在る経路（`orderItemOf` が null・釜のカードは麺種だけ・`complete` / `cancel` は品目に何も書かず Timer を閉じる）へ落ちるだけで、新しい経路も新しい拒否事由も要らない。手順は 2 段で、**選定にだけ全順序を使い、残る品目の相対順序は入力のまま**にする——並べ替えれば内容の同じ再送が差分に見えて空振りの `Persist` / `Broadcast` を呼ぶ。`compareArrival` が全順序になるのは鍵が一意なときに限るので、それを事前条件として宣言し、破れうる唯一の口（永続からの復元）に関門を置く。

**忘却は不可逆である。** 落ちた品目は永続にも snapshot にも二度と現れず、`completedAt` を持っていた履歴もそこで失われる（Operation History は Timer の操作を tail から出すので、調理の履歴はそちらに残る）。これを受け入れるのは、代わりに得るものが「いつか確定できなくなる」ことの回避だからである。上限に当たった到着は拒否しない——`MAX_TIMERS` が「これ以上は始められない」という現場への回答であるのに対し、注文の到着は現場が断れる出来事ではない。受理は成立し、代わりに最も古い品目が静かに落ちる。

## Considered Options

- **期限（時間窓）で正本も切る**: ADR-0011 の述語をそのまま状態にも効かせる案。負荷が高い時間帯には 2 時間で数百件が積むだけなので上限としては働かず、逆に静かな店では何も切らない。バイト数を有界にしたいという動機に対して、時間は代理として弱い。採らない。
- **`cooking` を守る**: 参照が解けない Timer を作らずに済むが、「上限を超えているのに落とせない」場面が生まれて上限が上限でなくなる。しかも守るための述語は Timer 集合を要求し、`truncateOrderItems` が `now` と Timer に依存し始める（期限との線が消える）。参照先の無い Timer を扱う経路は ADR-0013 判断 13 で既に一つに畳んであり、そこへ落ちるだけで済む。採らない。
- **掃除を別の遷移・Alarm にする**: 「掃除が走ったか」という第 2 の状態が生まれ、新しい wake 源も増える（ADR-0011 が避けた形と同じ）。採らない。
- **バイト予算で切る**: 直列化後のバイト数を予算に収める案。文字列長が未検証でも真に有界になるが、性質が「直列化の実装」に依存する——実際に載るのは structured clone であって JSON ではない——ので、決定性の検査が実装の詳細に縛られる。件数を採る。
- **hydration で縮めた集合を確定する**: 起動時に `put` すれば永続が即座に縮むが、「hydration は `Persist` を起こさない」という既存の規律を壊し、wake のコストを変え、shell を変えることになる。次に `Persist` が立つ任意の確定変化で縮むので、稼働中の店では分単位で解消する。採らない。

## Consequences

- **件数はバイト数の厳密な上界ではない。** `itemName` / `sizeName` / `externalOrderId` / `noodleType` / `tableId` は長さを検証していない（`toDeclaredName` は「空でない文字列か」だけを見る）ので、1 件あたりのバイト数に上界が無い。4096 は「代表的な品目 279.7 B に対して、長めの入力でも 2 MB に収まる最大の 2 冪」として選んだ値である。満杯の状態の実測は品目集合 1.093 MiB・全体 1.137 MiB（品目集合が全体の 96.1%）。回帰はこの代表値の桁を守るだけで、`put` が必ず通ることは主張しない。
- **永続の値の上限は 2 MB（key + value 合わせて）である。** SQLite バックエンドの制約で、`yude-men-timer/design.md` の「KV バックエンドで 128 KiB」は backend を移した時点で更新されないまま残っていた記述である（本 ADR と同時に訂正した）。
- **永続が縮むのは次の確定変化のとき。** hydration は Working_Copy を組むだけで `put` を起こさないので、上限超過の永続値は次に `Persist` が立つまで残り、wake のたびに読み直される。`Persist` は到着に限らずあらゆる確定変化で立つので稼働中の店では分単位で解消する。静かな店では残るが、そこでは伸びてもいない。
- **鍵の重複は移行失敗になる。** `compareArrival` の全順序は鍵の一意性を前提にするので、`migrate` が復元後の全件を検査し、重複が在れば `MigrationFailed`（部分受理はしない）。engine が作る集合に重複は生じないので、これは壊れた永続値を弾く関門である。個別に捨てないのは、`completedAt` を持つ側が消えれば「完了済みの品目が POS の再送で未調理として復活する」既知の害に触れるからである。
- **忘れられた注文の後着は新しい `arrivalTime` で入り直す。** 引き継ぐ起点（同じ注文の残っている品目）が無くなるためで、ADR-0011 が「引き継ぐ起点が無くなった後」について述べたのと同じ帰結である。4096 件先の後着は現実の運用に無いので、「生き返らない」ことは保証しない。
- **永続スキーマの版は上げない。** 集合の形は変わらず、変わるのは要素数の上界だけである。件数の超過それ自体は移行失敗の事由にしない——超過は移行が直せる欠陥である。
- **有界性の検査は列挙であって網羅ではない。** 「`orderItems` を返す変換の件数がどう動くか」は変換ごとに独立して検査するが、将来新しい変換が増えればその性質は自動では守られない（字面の構築点を数える静的検査は成立しない——`complete` / `cancel` は `map` で新しい配列を作り、`fromSnapshot` / `toSnapshot` は写す）。engine を実走させて各遷移の直後に上限を見る性質が二重の網になる。
- **`lastSequenceByTerminal` は本 ADR の対象外で、構造的には有界でない。** 未知の端末ごとにエントリが増え、識別子も `sequence_number` も長さを検証しない。有界性は外部契約（1 店舗の端末集合は有限・`sequence_number` は 56 桁）への前提であり、明示するに留める。**無条件に伸び続けるのは `orderItems` だけ**である。
