# 上げ窓（Lift_Window）を計画のハード制約にする。上げの間隔は設定 `liftIntervalSeconds` に持つ

#30・#31 の後も「次の品目は常に now」だった。計画が走行中を読むのは釜の占有・同じ卓の揃え先・同卓の同時上げの減点（1 本 1 秒相当）だけで、店舗全体の走行中が**いつ上がるか**は新しい品目の置き場所に効いていない。腕は arms 本で、上げて湯を切って盛り付けるまでに時間が要るのに、9 本が 1 分以内に上がる計画が出る。Boil_Sync の maximin は ±h_i の内側でしか散らせない（60 秒の麺なら 12 秒幅）ので、開始後には救えない。上げと上げの間に要る秒数は、設定にも定数にも無かった。

**`liftIntervalSeconds`（既定 20 秒・妥当域 5〜120）を StoreConfig に足し、店舗全体の上がる時刻（走行中の実効 endTime と計画済みの serveAt）を並べたとき、任意の長さ `liftIntervalSeconds` の窓に上がる品目の slotSpan の合計が arms を超えないことをハード制約にする。** 新しい品目の serveAt は、合流の規則（ADR-0008）で決めた候補以降の最初に空く窓へ置く。釜が空いていても窓が埋まっていれば startAt は未来になり、提案は薄く現れて時刻が来たら濃くなる。計画は開始のたびに実際の走行中の上がり時刻から窓を引き直す。大盛（slotSpan 2）は 2 本分の腕を使う。数える範囲は店舗全体。

これは ADR-0002 の「計画では arms はソフト（実質タイブレーク）」を覆す。あちらは「効かせるなら上げ遅れる秒数という計測値が要り、それが実在したときに持ち込む」と書いた——実機でその必要が出たので持ち込む。目的関数の Arms_Overflow 項と `max(0, w_table − 1)` の導出は役目を失い、外す。Boil_Sync（開始後の ±h_i の微調整・arms 本ずつのセット分割）は変えない。上げの間隔を作るのは計画の役目である。

## Considered Options

- **腕を釜と同じ資源としてモデル化する（占有表を持つ）**: ユーザーの像と違う。扱うのは「走行中の上がり時刻を避けて置く」であり、上げ窓の表は上がり時刻の並びから毎回導く導出値に留める。採らない。
- **Arms_Overflow の重みを上げる（ソフトのまま）**: 重みで散らしても間隔は保証されず、目的関数の最遅参照と衝突して群が壊れる。採らない。
- **h_i を上げの間隔に転用する**: 品質の許容幅と上げの所要時間は別の物理量。60 秒の麺で 6 秒は上げの間隔として短すぎる。採らない。
- **表示だけで絞る（判断 21）**: 濃いのを arms 本に絞っても計画は「全部いま入れろ」のままで、始めれば同時に上がる。表示は計画の帰結を見せるだけにする。

## Consequences

- 合流（ADR-0008）は残る。錨は群の所属のためのもので、serveAt は錨の後の空いた窓になりうる。`anchor` の意味（合流先の走行中の実効 endTime）と client の `started = anchor > now` は変えない。
- ゲートは外部計画にも同じ窓を検査する（ハード制約 (f)）。採用済み一片は上げ窓の表に載せ、尾部はそれを避ける。現在の走行中と衝突する採用済み一片は陳腐化と見なす。
- 連続投入の不変（Requirement 7.6）の「合流した残りは `startAt ≤ now`」は「上げ窓を満たす最初の時刻」へ改まる。9 本・arms 2・間隔 20 秒なら startAt は now・+20・+40・… と並ぶ（Requirement 7.9）。
- StoreConfig に項目が 1 つ増える（registry の compose・config ワイヤ・`RequestPlan`・指紋）。client は読まない（表示は計画の startAt に従う）。
