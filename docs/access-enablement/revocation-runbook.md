# 失効運用ランブック（iPad 紛失・担当者離任）

> 対象要件: cloudflare-access-enablement 要件 9.1 / 9.2 / 9.3 / 9.4 / 9.5
> 参照: design.md「D-4. 失効運用（要件9）」「Data Models 失効の運用記録モデル（要件9.4）」
> 関連手順: `identity-roster-registration.md`（Provisioning_API の使い方・逆引き・全置換の意味論）
>
> 本書は**運用手続き**であり、アプリコードの変更を伴わない（要件10.1 / 10.4 の差分制限）。
> セッションの継続と失効判断は **Cloudflare_Access に委ねる**。アプリ側にセッションストア・失効ロジックを**新設しない**（要件10.4）。
> Roster の改定は**既存の Provisioning_API（`/admin/*`・`ADMIN_TOKEN`）**のみを用いる。新規実装・再実装はしない。

---

## 0. 前提と原則

失効は「**その identity が今後この境界を越えられない状態**」を作る運用である。境界は二層あり、失効も二段で考える。

1. **Cloudflare_Access のセッション**（認証境界）— 失効すると Access が再認証を要求し、Entry `/`・`/s/{storeId}/`・`/s/{storeId}/ws` への到達を遮断する。**これは Access に委ねる**（アプリはセッションを持たない・要件9.1）。
2. **店舗 DO の投影 Roster**（認可境界）— 除去すると当該 identity は次回接続時に Roster ゲート（`isRostered`）で拒否される。**これは Provisioning_API で改定する**（要件9.2）。

**一時的に断つのか、恒久的に断つのか**で措置が変わる。

| 状況 | 措置 | 参照節 |
| --- | --- | --- |
| 紛失・離任が判明した直後（まず接続を止める） | **セッション失効**（Access）だけを先に行い、到達を遮断する | 第 1 章 |
| 恒久的に断つ（端末を戻さない・担当を外す） | **セッション失効 ＋ Roster 除去**の二段で恒久化する | 第 2 章 |

> **重要な確定挙動（要件9.2）**：Roster 除去は**次回再接続時に反映**される。名簿改定は次接続からゲートに効き、**生存中の既存 WS は維持される**（即時切断は per-store-provisioning の `deactivated`＝店舗の非活性化のみが担う確定挙動であり、生存中 WS の即時切断は本 spec のスコープ外）。厨房 WS の再接続頻度により実効窓は小さい。**「今すぐ既存接続を切る」ことは Roster 除去では保証されない**——即時に断ちたいときはセッション失効（第 1 章）を先に行う。

### 失効の実効上限は二つで決まる（要件9.5・[Q-session] 依存）

紛失 iPad の**実効失効の時間上限**は、次の二つの積で決まる構造を持つ。

- **whereami 再認証が店舗ネットワーク内でのみ成立すること**（店外に持ち出された iPad は再認証できない＝在圏を失えば新規セッションを取れない）。
- **Access_Application のセッション寿命**（既存セッションが失効するまでの最大時間）。

ゆえに**セッション寿命を明示設定しない限り、要件9.1 の遮断保証の時間上限が定まらない**。セッション寿命の設定手順は第 4 章に置く。**具体値は [Q-session] 未決**であり、確定後に本書の該当箇所へ記入する（現時点では未決として明記する）。

## 1. セッション失効（Access・到達の遮断・要件9.1）

紛失・離任が判明したら、**まず**当該 identity の Cloudflare_Access セッションを失効させ、到達を遮断する。

### 1-A. 対象 identity の特定

| 対象 | identity（正準 email） | 特定方法 |
| --- | --- | --- |
| 店舗共用 iPad（whereami 経由） | 合成 email `staff-{店舗コード}@yamaokaya.com` | 紛失端末が属する店舗コードから合成 email を組み立てる（`identity-roster-registration.md` 第 3 章の逆引きと同じ店舗コード） |
| 人間ユーザー（EntraID 経由） | 本人の実 email | 離任者の実 email |

> 合成 email は**店舗単位**であり端末個体を区別しない。同一店舗に複数の共用端末があるとき、当該合成 email のセッション失効は**その店舗の全共用端末**に及ぶ（在圏内の端末は再認証で回復する。紛失端末は店外で在圏を失い再認証できない）。

### 1-B. Cloudflare_Access 上でセッションを失効させる

Cloudflare One（Zero Trust）ダッシュボードの **My Team → Users** で対象 identity を選び、**セッションの失効（Revoke session）**を実行する。実行後、当該 identity は次回アクセス時に Access の再認証を要求される。

- **whereami 経由の合成 email**：再認証は「店舗ネットワーク内に居る事実」でのみ成立する（ゼロタッチ）。店外に持ち出された紛失端末は在圏を失うため再認証できず、Entry `/`・WS へ到達できない。
- **EntraID 経由の実 email**：再認証は EntraID のログインを要する。離任者のアカウントが EntraID 側で無効化・条件付きアクセスで除外されていれば、Access 側の再認証も成立しない。

> セッション失効の具体的な UI 操作・API は Cloudflare の現行仕様に従う（本書は「何を達成するか」を定める。手順詳細は Cloudflare One ダッシュボードの表示に合わせて実施する）。**アプリ側には失効の受け皿を作らない**（要件10.4）。

### 1-C. 遮断の確認

- 失効後、当該 identity で Entry `/`・`/s/{storeId}/`・`/s/{storeId}/ws` へ到達しようとすると Access の再認証画面に誘導される（在圏外・アカウント無効なら成立しない）。
- **セッション失効だけでは Roster は変わらない**。恒久的に断つときは第 2 章の Roster 除去を併せて行う。

## 2. 恒久的失効（セッション失効 ＋ Roster 除去・要件9.2 / 9.3）

端末を戻さない・担当を外すなど**恒久的に断つ**ときは、第 1 章のセッション失効に加えて、Provisioning_API で当該 identity を該当 Roster から除去する。

### 2-A. 除去先 Roster の特定

登録時（`identity-roster-registration.md` 第 1 章の決定表）の裏返しで特定する。

| identity 種別 | 除去先 Roster | 経路 |
| --- | --- | --- |
| whereami 合成 email `staff-{店舗コード}@yamaokaya.com` | 当該店舗の **店舗 Roster**（`Store.storeRoster`） | `GET`→`PUT /admin/stores/{storeId}` |
| EntraID 実 email（当該店舗専任） | 当該店舗の **店舗 Roster** | `GET`→`PUT /admin/stores/{storeId}` |
| EntraID 実 email（チェーン全店担当） | 所属チェーンの **チェーン Roster**（`Chain.chainRoster`） | `GET`→`PUT /admin/chains/{chainId}` |

- 合成 email → `storeId` の特定は `storeCode` の**文字列完全一致による逆引き**（`identity-roster-registration.md` 3-A）で行う。
- 実効 Roster は **店舗 Roster ∪ チェーン Roster** の和集合（`effectiveRoster`）。**チェーン Roster に載っている identity を店舗 Roster から消しても遮断されない**。逆も同様。**当該 identity が実際に載っている Roster を除去する**（両方に載っていれば両方から除去する）。

### 2-B. Roster 除去は「除去前状態の保持」を最優先にする（要件9.3）

Provisioning_API に**単一要素の削除（DELETE）エンドポイントは無い**。除去は **PUT の全置換 / 配列置換**で行う——**現状を読み出し、対象 identity を除いた残りの全量を送る**。この意味論が要件9.3 の「除去失敗時は除去前状態を保持する」を構造的に満たす（PUT が受理されなければイデアは一切変わらない）。

#### 店舗 Roster からの除去

1. **現状を取得**：`GET /admin/stores/{storeId}` で当該店舗のイデア全体（`storeRoster` を含む）を取得する。控えた `storeRoster` が**除去前状態**（万一の復旧原本）。
2. **対象を除いた全量を組む**：`storeRoster` から対象 identity を**正準形（trim + 小文字化）で一致するもの**を除いた配列を作る。
   - 除去対象も現状の要素も正準形で突き合わせる（登録が正準化済みでも念のため正準形で比較する）。
   - 除去対象が現状に**存在しない**とき：既に除去済み。PUT を送らず、記録にその旨を残して完了とみなす。
3. **全量で PUT**：
   ```
   PUT /admin/stores/{storeId}
   Authorization: Bearer {ADMIN_TOKEN}
   Content-Type: application/json

   {
     "storeRoster": ["{対象を除いた残りの正準化済み identity...}"]
   }
   ```
   - **残り全量を送る**（`storeRoster` を省略すると意図しない置換になる）。全員を除去して空名簿にするときは `"storeRoster": []` を明示する。
4. **受理を確認**：レスポンスが受理（`accepted: true` 相当）であること。受理なら収束（`recomposeProjection` → 当該店舗の StoreTimerDO への投影）が自動で走り、次回接続から新 Roster がゲートに効く。

#### チェーン Roster からの除去

1. **現状を取得**：`GET /admin/chains` で `chainId` を特定し、対象チェーンの現在の `name` / `chainRoster` を控える（除去前状態）。
2. **対象を除いた全量を組む**：`chainRoster` から対象 identity を正準形一致で除いた配列を作る。
3. **`name` を保持したまま全量で PUT**：
   ```
   PUT /admin/chains/{chainId}
   Authorization: Bearer {ADMIN_TOKEN}
   Content-Type: application/json

   {
     "name": "{既存の name}",
     "chainRoster": ["{対象を除いた残りの正準化済み identity...}"]
   }
   ```
   - `name` を省略しない（全置換ゆえ既存メタを失わないため）。
4. **受理を確認**：受理であること。

### 2-C. 除去失敗時の扱い（要件9.3・失効完了を主張しない）

PUT が受理されない（400 の値検証違反・401・ネットワーク失敗・タイムアウト等）とき：

- **除去前の Roster 状態はそのまま保持される**（PUT が通っていないためイデアは不変。2-B 手順1 で控えた除去前状態が現状と一致する）。**推測で再送を繰り返して別の名簿を書き込まない**。
- **失効未完了を運用者へ通知する**（下記の通知先へ）。
- **失効完了を主張しない**（記録・報告に「Roster 除去 完了」と書かない。第 3 章の記録に「Roster 除去 未完了（理由）」と残す）。
- セッション失効（第 1 章）が済んでいれば**到達は遮断されている**。恒久化の Roster 除去のみが未完了である旨を明示し、原因（token 失効・値検証・疎通）を解消してから再実施する。

> **通知先**：運用チャネル（運用者向けの周知手段）。本アプリ内に通知機構を新設しない（要件10.4）。系統性障害の監視（要件8）とは別で、これは**単一 identity の失効作業の未完了**の通知である。

### 2-D. 恒久的失効の確認（任意・`ACCESS_REQUIRED="1"` の段階）

- 当該 identity で `/s/{storeId}/ws` へ**新規**接続すると、Roster ゲートで 403 拒否され店舗状態を一切変更しないこと（要件6.5）。
- **既存の生存 WS はこの時点では維持される**（次回再接続時に拒否・要件9.2）。即時に断つ必要があるときはセッション失効（第 1 章）で到達を止める。

## 3. 失効の運用記録（要件9.4 / 10.4）

失効実施ごとに、監査可能性のため次を**運用側の記録媒体**（運用ランブック台帳・チケット・監査ログ）に残す。**アプリ内に永続キーを新設しない**（要件10.4）。

```
失効記録 = {
  対象 identity : 正準 email（例: staff-9920@yamaokaya.com / sato.taro@example.com）
  対象端末      : iPad 個体識別・店舗コード等（人間ユーザーの場合は「該当端末なし」）
  実施日時      : タイムスタンプ（タイムゾーン明記）
  失効理由      : 紛失 / 離任 / その他（自由記述）
  実施措置      : セッション失効 / Roster 除去 / その両方（未完了があればその旨と理由）
}
```

### 記録テンプレート（コピーして埋める）

```
- 対象 identity : 
- 対象端末      : 
- 実施日時      : 
- 失効理由      : 
- 実施措置      : [ ] セッション失効（Access）  [ ] Roster 除去（店舗 / チェーン）
                  未完了があれば: 
```

> **記載規律**：Roster 除去が未受理のときは「実施措置」に**完了と書かない**（要件9.3）。「Roster 除去 未完了（理由: …）」と正確に残し、後日の再実施で更新する。

## 4. セッション寿命の設定手順（要件9.5・[Q-session] 未決）

紛失 iPad の実効失効の時間上限（第 0 章）を定めるため、Access_Application のセッション寿命を **Cloudflare_Access 上で明示的に設定する**。

### 4-A. 設定箇所

Cloudflare One（Zero Trust）ダッシュボードの **Access → Applications → 対象 Access_Application → セッション期間（Session Duration）** で明示設定する。既定に委ねず、**明示的に値を投入する**（本 spec は「明示設定する」ことを要求する・要件9.5）。

- Pilot_Access_Application と本番の Access_Application の**双方**に設定する（構成次元を揃える・要件1.5）。
- セッション寿命の変更はアプリコードに影響しない（Access 側設定のみ・要件10.4）。

### 4-B. 具体値（未決・[Q-session]）

> **⚠ 未決事項 [Q-session]**：セッション寿命の**具体値は本 spec では確定しない**（要確認事項 Q-session・要件9.5）。
>
> - 短くするほど紛失 iPad の実効失効の時間上限は下がる（安全側）が、店舗の再認証頻度が上がる（whereami はゼロタッチゆえ在圏内なら再認証負荷は小さい）。
> - 長くするほど再認証は減るが、紛失時の遮断保証の時間上限が伸びる。
> - **確定したら本節に具体値と決定日を記入する**（例: `セッション期間 = XX 時間（決定日: YYYY-MM-DD・決定者: …）`）。それまでは**未決**として運用する。

### 4-C. 実効失効の理解（設定値の意味）

- 紛失端末（whereami 経由）は店外で**在圏を失う**ため、既存セッションが寿命で切れた後は再認証できない。**遮断の時間上限 = 現行セッションの残り寿命**（最悪ケースでセッション寿命の満了まで）。
- **即時に断ちたいときは寿命満了を待たず、第 1 章のセッション失効を実行する**（セッション寿命は「失効操作をしない場合の自然な上限」を定めるもの）。

## 5. 失効チェックリスト

失効作業ごとに以下を確認する。

### まず遮断する（一時・恒久 共通）

- [ ] 対象 identity（正準 email）を特定した（whereami=合成 email / EntraID=実 email）。
- [ ] Cloudflare_Access 上でセッションを失効させた（Revoke session）。
- [ ] 到達遮断を確認した（再認証誘導・在圏外/アカウント無効なら不成立）。

### 恒久的に断つ（追加・要件9.2 / 9.3）

- [ ] 除去先 Roster を特定した（店舗 Roster / チェーン Roster・当該 identity が実際に載っている側）。
- [ ] `GET` で**除去前状態を取得・控えた**（復旧原本）。
- [ ] 対象を**正準形一致**で除いた**残り全量**を PUT した（配列置換の意味論を踏まえた）。
- [ ] レスポンスが受理（`accepted: true` 相当）であることを確認した。
- [ ] （受理されなかった場合）除去前状態が保持されていることを確認し、**失効未完了を通知**し、**失効完了を主張しなかった**（要件9.3）。

### 記録（要件9.4 / 10.4）

- [ ] 対象 identity・対象端末・実施日時・失効理由・実施措置を運用記録に残した。
- [ ] Roster 除去が未完了なら「未完了（理由）」と正確に記録した（完了と書かない）。

### セッション寿命（要件9.5）

- [ ] Access_Application のセッション寿命が Cloudflare_Access 上で**明示設定**されていることを確認した（Pilot・本番の双方）。
- [ ] 具体値が [Q-session] 確定後であれば本書 4-B に記入済みであることを確認した（未確定なら未決として扱う）。
