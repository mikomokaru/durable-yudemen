# Synthetic_Monitor 監視設定ランブック（外形監視・三層構成）

> 対象 spec: `cloudflare-access-enablement` / タスク 9.1「Synthetic_Monitor を整備する」
> 種別: ［手続き］（コードで自動検証できない監視設定/運用タスク。実際の監視構成・アラート設定・プローブ配備は運用者が本ランブックに従い実施する。アプリコードは変更しない・要件10.1）
> 正本: `requirements.md` 要件8.1 / 8.2 / 8.3 / 8.6 / 8.7、`design.md` 節「D-3 Synthetic_Monitor（外形監視・要件8）」、Glossary「Synthetic_Monitor」

---

## 0. このランブックの位置づけ（必読）

本ランブックは、本番切替（タスク 8）で `ACCESS_REQUIRED="1"` を有効化したのち、**認証境界が作動し続けていること**を継続的に確認するための外形監視の設定・運用手順である。

Synthetic_Monitor という名称は合成監視（能動的な合成試行）に由来するが、**本 spec の監視の主軸は Workers Logs のパッシブ観測に置き、合成試行を主としない**（Glossary「Synthetic_Monitor」・design D-3）。監視は次の三層で構成する。

| 層 | 監視対象 | 手段 | 主/従 | 要件 |
| --- | --- | --- | --- | --- |
| (a) | whereami 経路の系統性障害 | Workers Logs パッシブ指標の閾値観測（合成試行なし） | **主** | 8.2 / 8.3 |
| (b) | 認証要求（静かな認証 OFF への退行） | 未認証直叩き＝403 の能動プローブ（既定 5 分周期） | 補助 | 8.7 / 8.3 |
| (c) | EntraID 経路（認証→店舗接続） | 低頻度（日次以下）確認または申告 | 低頻度 | 8.1 |
| — | 既存アセット経路の死活 | 認証なし到達で 5 秒以内正常応答 | 死活 | 8.6 |

### 監視の土台（前提・確認済み）

- **`observability.enabled = true` は `wrangler.jsonc` で有効化済み**（本リポジトリの `wrangler.jsonc` で確認済み）。層 (a) の Workers Logs パッシブ指標はこれを土台に用いる。追加のアプリコードを要さない。
- **店内端末のヘルスビーコンは採用しない**（要件8.2）。whereami 経路は店舗ネットワーク内でのみ認証が成立し外部からの合成試行は原理的に通れないため、24h 営業・常時接続の実機群が実トラフィックで全経路を検証する。系統性障害はそのパッシブ観測で検知できる。
- **アプリコードを変更しない**（要件10.1）。本ランブックの成果物は監視設定手順（markdown）のみ。監視の作動点はすべて Cloudflare 側の Logs／外部プローブであり、Worker／DO に監視用コードを足さない。

### 切戻し（タスク 9.2）との接続

層 (a) と層 (b) は、切戻し（要件1.3）の**検知入力**そのものである。すなわち系統性障害の検知入力は次の二つに限る。

- (a) whereami 経路の Workers Logs パッシブ指標が正常域を外れること（403 レート急騰・WebSocket アップグレード成功数の崩落）。
- (b) 未認証直叩きが 403 で拒否される作動が R8.7 の能動プローブで崩れること（403 以外の検出＝静かな認証 OFF への退行）。

いずれかを検出したら、切戻しランブック（`docs/access-enablement/rollback-runbook.md`・タスク 9.2）の手順に従い、検出から 5 分以内に `ACCESS_REQUIRED="0"` へ戻す。

## 1. 層 (a) — whereami 経路のパッシブ観測（Workers Logs・主軸・要件8.2 / 8.3）

**目的**: whereami 経路の系統性障害を、合成試行を行わず Workers Logs の実トラフィック指標の閾値観測で検知する。

### 1-1. 観測する指標（二つ）

| 指標 | 意味 | 異常の向き |
| --- | --- | --- |
| `/s/*/ws` の **403 レート** | 認可失敗（Roster 非一致・JWT 検証失敗）の発生率 | **急騰** = whereami 経路の系統的な認可失敗の候補 |
| **WebSocket アップグレード成功数** | 店舗 iPad が実際に WS を確立できている件数 | **崩落** = 全店で接続が確立しなくなった候補 |

- いずれも 24h 常時接続の実機群が実トラフィックで生成するログから得る。合成試行を発行しない（要件8.2）。
- 両指標のどちらかが正常域を外れたときを**系統性障害の候補**として記録する（design D-3・切戻しの検知入力 (a)）。

### 1-2. 設定手順（Cloudflare Workers Logs / Logpush）

- [ ] Cloudflare ダッシュボードで対象 Worker（`yude-men-timer`）の **Workers Logs** が有効であることを確認する（`observability.enabled = true` 済み）
- [ ] `/s/*/ws` へのリクエストのうち **HTTP 403** を返したものを抽出するクエリ／フィルタを定義する（パス `/s/` プレフィックス＋ステータス 403）
- [ ] **WebSocket アップグレード成功**（101 応答・接続確立）を抽出するクエリ／フィルタを定義する
- [ ] 上記二指標について、**正常域（ベースライン）** を切替後の平常運用データから定める（例: 403 レートの平常値・WS アップグレード成功数の営業時間帯ごとの下限）。ベースラインは営業時間帯・店舗数に応じて見直す
- [ ] 各指標に**異常閾値**を設定する
  - 403 レート: 平常値からの急騰（例: 直近ウィンドウの 403 比率がベースライン比で顕著に上振れ）
  - WS アップグレード成功数: 営業時間帯にもかかわらず下限を大きく下回る崩落
- [ ] 閾値超過時に運用者へ通知するアラート（メール／チャット等）を構成する（要件8.3・後述 §5）

> **注記**: 具体的な閾値の数値は平常運用データが蓄積してから確定する（切替直後は保守的な閾値で開始し、誤検知と見逃しのバランスを見て調整する）。本ランブックは「二指標を閾値観測し、正常域を外れたら系統性障害候補として通知する」構造を確定させる。

## 2. 層 (b) — 認証要求の能動プローブ（未認証直叩き 403・要件8.7 / 8.3）

**目的**: 「認証が要求されること」（＝静かな認証 OFF への退行がないこと）を短周期で検知する。層 (a) が「認証が通ること」を実トラフィックで見るのに対し、本層は「認証が要求されること」を能動的に見る（要件8.7）。

### 2-1. プローブの仕様

| 項目 | 値 / 方針 | 要件 |
| --- | --- | --- |
| プローブ内容 | 認証情報（Cookie / `Cf-Access-Jwt-Assertion`）を伴わない `/s/{storeId}/ws` への直叩き | 8.7 / 7.4(a) |
| 期待応答 | **HTTP 403**（WebSocket アップグレードせず・店舗 DO に到達しない） | 7.1 / 7.4(a) |
| 異常判定 | **403 以外**の応答（特に認証を経ない接続成立）を検出 | 8.7 |
| 周期 | **既定 5 分周期** | 8.7 |
| 実行場所 | 外部（IdP 非依存・EntraID / whereami のいずれの経路にも依存しない・外部から実行可） | 8.7 |

- プローブは Access の前段を経由しない外部からの直リクエスト（例: 外部 uptime 監視サービス・スケジュール実行されるヘッドレスクライアント）で発する。IdP に依存しないため、テストアカウント・MFA・条件付きアクセスの脆さを持ち込まない。
- プローブ先の `storeId` は監視用に定めた実在のテスト用スラッグ等を用いる（DO 到達前の 403 を確認するため、Roster 登録の有無に依存しない）。

### 2-2. 設定手順

- [ ] 外部の周期実行基盤（外部 uptime 監視サービス、または cron 相当のヘッドレス実行）を用意する
- [ ] 認証情報を付与せずに `/s/{storeId}/ws` へ WebSocket アップグレードを試行するプローブを **5 分周期**で構成する
- [ ] 応答が **403**（かつ店舗 DO 未到達）であることを成功、**403 以外**を異常として判定するロジックを設定する
- [ ] 403 以外を検出したとき運用者へ通知するアラートを構成する（要件8.3・§5）。これは切戻しの検知入力 (b)

> **重要**: 本プローブが 403 以外（特に接続成立）を返したら、それは認証境界が黙って OFF に退行した兆候である。切戻し（タスク 9.2）の直接のトリガとなる。

## 3. 層 (c) — EntraID 経路の低頻度確認（要件8.1）

**目的**: EntraID_IdP 経由の認証から店舗接続までの経路が通ることを確認する。ただし対話型ログインゆえ短周期のヘッドレス自動化は行わない（テストアカウント・MFA・条件付きアクセスにより脆いため・要件8.1）。

### 3-1. 方針

- 切替時検証（タスク 7.4・Pilot / タスク 8.3・実店舗最終疎通）で 1 回成功を確認済みであることを前提とする。
- 以後は**日次以下の低頻度確認**または**運用者の申告ベース**で確認する（短周期の常時合成監視を行わない）。

### 3-2. 設定手順

- [ ] EntraID 経路の確認頻度を**日次以下**（例: 日次・週次、または本部・SV からの利用申告ベース）と定め、運用カレンダー／当番表に記載する
- [ ] 確認内容を定める: 人間ユーザー（本部・SV）が EntraID で認証し、Entry `/` の逆引きを経て担当店舗へ到達できること（`resolveEntryDestination` の作動・要件3.3）
- [ ] 到達不能が申告または低頻度確認で判明したときの一次対処を定める: 個別 identity / 店舗の認可失敗は**全体 OFF の根拠としない**（要件1.7）。Provisioning_API 経由の Roster 修正で対処する（切戻し対象は系統性障害のみ）

## 4. 既存アセット経路の死活監視（認証なし bypass・要件8.6）

**目的**: Worker が生きて応答していることを、認証情報なしで到達できる単一の定義済み経路で確認する。

### 4-1. 方針（Q-health 確定・新設ゼロ）

- 専用 `/healthz` を**新設しない**。既存の静的アセット経路（例: `/favicon.svg`）を Access の **bypass 対象**（タスク 7.1・access-application-config-checklist §除外経路）とし、それを死活監視に用いる（要件2.4 / 8.6・design C-1）。
- アセット応答も Worker（`env.ASSETS.fetch`）経由ゆえ、当該経路の正常応答は Worker の死活を証明する。新設コードがゼロのため要件10.1 の差分制限と衝突しない。

### 4-2. 設定手順

- [ ] Access 側で監視用の既存アセット経路（例: `/favicon.svg`）が **bypass 対象**（認証なしで到達可）になっていることを確認する（タスク 7.1 の除外経路設定と整合）
- [ ] 当該経路へ**認証情報なし**で到達し、**5 秒以内に正常応答**（2xx）を受領することを死活確認成功とするプローブを構成する（要件8.6）
- [ ] 5 秒以内に正常応答を受領できないとき運用者へ通知するアラートを構成する（§5）

---

## 5. 通知（要件8.3）

以下のいずれかを検出したとき、運用者へ通知する。

- [ ] 層 (a): whereami 経路のパッシブ指標（403 レート・WebSocket アップグレード成功数）が**正常域の異常閾値を超過**したとき（要件8.3・切戻し検知入力 (a)）
- [ ] 層 (b): 能動プローブが **403 以外**を検出したとき（要件8.3 / 8.7・切戻し検知入力 (b)）
- [ ] 死活監視: 既存アセット経路が 5 秒以内に正常応答を返さないとき（要件8.6 の不成立）
- [ ] （参考・タスク 8.4 / 9 と連携）タイマー機能の観測結果が認証無効時と異なる（回帰あり）とき（要件8.5）

通知先・通知手段（メール／チャット／オンコール）は運用体制に合わせて構成する。層 (a)・(b) の通知は切戻し（タスク 9.2）の起動点となるため、切戻し実施者へ確実に届く経路とする。

---

## 6. 採用しないもの（引き算・要件8.2）

- **店内端末のヘルスビーコン**は採用しない。whereami 経路は店舗ネットワーク内でのみ認証が成立し外部からの合成試行が原理的に通れないため、24h 常時接続の実機群のパッシブ観測（層 a）で系統性障害を検知する。
- **whereami 経路への合成試行**は行わない（層 a はパッシブ観測のみ）。
- **EntraID 経路の短周期ヘッドレス自動化**は行わない（対話型ログインゆえ脆い・層 c は低頻度確認／申告）。

---

## 7. スコープ境界（触らないもの・要件10）

- 監視のためにアプリコード（Worker / DO / engine / domain）へ**監視用コードを足さない**（要件10.1）。監視の作動点は Cloudflare Workers Logs（`observability.enabled = true` 済み）と外部プローブに閉じる。
- セッションの継続・失効は Cloudflare Access に委ねる。監視のためにセッションストア・失効ロジックを新設しない（要件10.4）。
- 個別 identity / 店舗の認可失敗は監視の系統性障害判定に含めない。全体 OFF の根拠とせず Roster 修正で対処する（要件1.7・層 c）。
